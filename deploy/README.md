# Установка из доверенной копии проекта

Для отдельного VPN-сервера используйте [документ «Разворачивание Hysteria на внешнем сервере»](docs/hysteria2-server.md).

На Debian ARM64 с systemd запустите из корня проекта:

```sh
sudo bash deploy/install.sh
```

Установщик временно скачивает и проверяет по SHA-256 Go 1.27.3 и архив sing-box 1.14.4 для ARM64, собирает контроллер из этой копии проекта и настраивает службы `hestia` и `hestia-sing-box`. Если компилятор и внешний доступ на целевой системе нежелательны, используйте [переносимый комплект](docs/installer.md). Для проверки на ВМ можно передать доверенный бинарник параметром `--controller-binary` и официальный архив параметром `--sing-box-archive`. При необходимости установщик добавляет системные утилиты через APT.

На чистой машине без профиля установка создаёт селектор `bootstrap` с единственным выходом `deny`. Входов для клиентского трафика нет. Для применения своего профиля передайте `--config stand.json`. Ссылки на файлы разрешаются относительно каталога этого профиля. Профиль храните вместе с нужными файлами доступа. Обработанная конфигурация sing-box может содержать ключевой материал. В `/etc/hestia` она доступна только root, а служба читает приватную копию через systemd credentials. Снимок доступности читает только root и служебная группа контроллера.

Повторная установка без `--config` сохраняет настройки оператора. Явный `--config` применяет новый профиль. Установщик проверяет оба конфигурационных файла до замены, переносит файлы атомарно и перезапускает службы. При неудачном запуске или проверке он восстанавливает предыдущие файлы и состояние служб. Предварительно установленные пакеты Debian остаются в системе.

При загрузке шлюза служба `hestia-binding-recovery.service` восстанавливает последнюю подтверждённую конфигурацию при наличии незавершённой операции. Затем `hestia-binding-watch.path` начинает следить за журналом незавершённой операции и `hestia-sing-box` загружает конфигурацию через systemd credentials. Если процесс применения завершается до подтверждения, служба `hestia-binding-watch.service` дожидается освобождения блокировки и восстанавливает предыдущую конфигурацию. Поддержка записи и условия применения описаны в [спецификации привязки списка](../docs/list-binding.md).

Самопроверка в конце установки занимает до шести секунд. Она сверяет владельца слушающего сокета на `127.0.0.1:9090`, содержимое загруженной конфигурации sing-box, состояние двух служб, запись о выбранном выходе в журнале именно текущего запуска и выбор управляющего API. Эта проверка читает локальное состояние. Доставку TCP, UDP и DNS до удалённых пиров проверяйте отдельно.

Установщик также поставляет необязательную службу `hestia-dns.service`. Администратор задаёт точный адрес маршрутизатора и отдельно включает форвардинг. Конфигурация, права процессов и проверка UDP/TCP описаны в [инструкции DNS](../docs/dns-settings.md).

```sh
systemctl status hestia hestia-sing-box
journalctl -u hestia -u hestia-sing-box -b
```

## Обновление существующего hestia-prod

Перед обновлением выберите каталог состояния рабочего стенда:

```sh
export LIMA_HOME=/private/tmp/hestia-vm-run/lima-state
export LIMACTL=/private/tmp/hestia-vm-run/bin/limactl
```

Имена сценариев `stage1-*.sh`, цель `make stage1-fresh` и префикс резервных копий сохранены для совместимости; целевая ВМ называется `hestia-prod`.

По разрешению владельца запустите `bash deploy/stage1-awg-update.sh` без аргументов для обновления с сохранением текущего профиля. Сценарий проверяет имя ВМ и адрес, сохраняет заменяемые файлы в `/var/backups/hestia-stage1-awg-*`, обновляет приложение и сверяет контрольные суммы конфигурации и маршруты по умолчанию. В ходе обновления службы шлюза перезапускаются. Пакет включает модуль `hestia-dns.service`. При первой установке модуль остаётся выключенным. Настройки и списки доступны через панель, а фактические наблюдения появятся после [подключения DNS-службы](../docs/dns-settings.md#как-подключить-службу-в-изолированной-сети).

## Чистая установка на hestia-prod

Из корня рабочей копии на Mac выполните:

```sh
make stage1-fresh
```

Команда собирает текущие локальные исходники контроллера, панели и Angular, а также закреплённые версии инструментов AmneziaWG. Нужны запущенная ВМ, Go 1.27.3, npm и доступ к зависимостям. Для личного стенда команда находит Lima в `/private/tmp/hestia-vm-run`. Другой путь можно указать через `LIMACTL` и `LIMA_HOME`.

При каждом запуске службы шлюза кратковременно останавливаются. Содержимое `/etc/hestia`, включая сохранённые VPN-профили, и состояние `/run/hestia-awg` удаляются. Команда применяет `deploy/scheme3/guest-profile.json` с группой `default` и выходом `keenetic-direct`. После запуска служб она проверяет панель на `192.168.1.133:8080` и оба API. При ошибке после сброса повторите команду после устранения причины.

## Экспериментальный пакет Keenetic

Сборка создаёт `keenetic-arm64-experimental` и Entware-пакет `.ipk` для KN-1012 с KeeneticOS 5.2 Beta 3 и архитектурой `aarch64-3.10`. 7 ноября 2026 года установлен пакет `20261107-123735-f9fea441ebfd`. `opkg` подтвердил установленную версию, профиль и конфигурация прошли проверки, supervisor ответил по IPC; панель и API групп/физической инвентаризации проверены из LAN. SHA-256 и результаты: [свидетельство исправления API](../experiments/keenetic-ipk-packaging/evidence/api-repair-20261107-123735/check.txt). Это подтверждает пакетный lifecycle и чтение инвентаря, но не клиентскую маршрутизацию. Обновление не имеет транзакционного отката.

Перед распаковкой `preinst` запускает Go preflight из control-архива. Он требует запуск от root, `/bin/uname -m = aarch64`, Entware `opkg` с архитектурой `aarch64-3.10`, успешный token-auth RCI `GET /rci/show/version` и совпадение модели/версии KN-1012 с закреплённым профилем preflight. Token должен быть отдельно размещён в `/opt/etc/hestia/keenetic-rci-token`, принадлежать root и быть недоступным группе/остальным. IPK токен не содержит. `/opt` должен быть защищён от записи другими пользователями и иметь минимум 512 MiB свободного места.

`postinst configure` запускает `/opt/etc/init.d/S99hestia configure-package`; init проверяет managed profile, конфигурации controller/sing-box, возможности BusyBox и состояние процессов, затем поднимает supervisor, router, controller, panel и binding watcher. Успешный install hook требует readiness marker и подтверждённые статусы ролей через root-only IPC. Этот путь вместе с IPC, preflight и loopback панели проверен при установке 7 ноября 2026 года; запись опыта содержит команды, обнаруженные несовместимости и ограничения.

Для доступа к панели из LAN задайте root-only `/opt/etc/hestia/panel-listen` со значением `<LAN-IP>:8080` и выполните `/opt/etc/init.d/S99hestia restart`. На проверенном KN-1012 LAN-IP — `192.168.1.1`, поэтому адрес панели — `http://192.168.1.1:8080/`. Конкретный частный IP обязателен: wildcard bind запрещён, и HTTP Host должен совпадать с адресом слушателя. Панель не имеет аутентификации; доступ ограничивается доверенной LAN-сетью, порт нельзя публиковать в WAN.

Проверенная установка не подтверждает приём клиентского трафика: RoutePolicy/dataplane и DNS не проверялись, AWG и Wi-Fi/WISP отключены, а upgrade не имеет автоматического транзакционного отката при ошибке `postinst`. Для использования как рабочего шлюза нужны отдельные спецификации и прогоны маршрутизации/DNS, подтверждённый план восстановления пакета и отдельное разрешённое окно.
