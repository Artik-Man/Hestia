# Постоянная служба на ARM64

Проверяем, может ли работающий процесс Гестии следить за снимком доступности, переключать группы и сохранять действующие маршруты при ошибке во входном файле. Испытание запускает unit systemd. Стенд изменяет только файл состояния атомарной заменой. Селекторы sing-box изначально выбирают `deny`; единственным источником изменений селекторов во время прогона служит Гестия.

| Фаза | Ожидаемое наблюдение |
|---|---|
| Холодный запуск | Гестия синхронизирует обе группы, выбирает FI-1 и RU. |
| FI-1 отключён | Тот же PID переключает только финскую группу на FI-2. Новые TCP и UDP используют прежний FakeIP. |
| Ошибочная привязка доменного списка | Служба сообщает об ошибке и сохраняет действующий FI-2. |
| Оба FI недоступны | Финский селектор принимает `deny`. Пакеты по старому FakeIP и внешние DNS-запросы блокируются; контроль через RU отвечает. |
| Физические выходы восстановлены | При том же состоянии `deny` трафик и DNS всё ещё заблокированы. Обновление снимка возвращает маршрутизацию через FI-2. |
| Служба остановлена, снимок изменён | Новый экземпляр читает актуальный файл, выбирает FI-1 и сохраняет рабочий RU. |

## Повторный запуск

Нужна изолированная [Debian ARM64-ВМ со стендом sing-box](../fakeip/README.md), запущенная с systemd как PID 1. Соберите бинарник из корня проекта, перенесите его и файлы проекта в гостевую систему, сохраняя их взаимное расположение:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go -C backend build -o /tmp/hestia ./cmd/hestia
```

В гостевой системе из корня копии проекта выполните:

```sh
out=$(mktemp -d)
sudo bash experiments/controller-service/lab.sh /tmp/hestia "$out"
sudo cat "$out/verification.txt"
```

Стенд использует временный экземпляр поставляемого unit-файла. Его дополнительные настройки задают пространство тестового шлюза, временные пути бинарника и снимка, а также интервал 200 мс. После проверки служба остановлена и удалена из временной конфигурации systemd. Для независимой проверки сохранённого прогона на машине с Python 3 и tcpdump выполните:

```sh
python3 -B experiments/controller-service/verify.py experiments/controller-service/evidence
```

## Наблюдения на Debian ARM64

4 ноября 2026 года systemd 252 на Debian с ядром `6.1.0-53-cloud-arm64` запустил Гестию в сетевом пространстве шлюза. Один PID прошёл шесть стадий от первичного применения до восстановления. В журнале осталось сообщение об ошибочной конфигурации, и клиент в этой фазе продолжал получать ответы через FI-2. После SIGTERM служба остановилась; новый экземпляр загрузил снимок, заменённый во время остановки, и вернул FI-1.

В непрерывном захвате локального управляющего API есть пять PUT к финскому селектору и ровно один к российскому. Начальный выбор обоих селекторов был `deny`, поэтому запись RU требовалась только при старте. В последующих переходах служба опрашивала статусы и меняла только селектор с отличающимся выходом. Журнал решений сопоставлен с этими записями. На сетевом стенде проверены 24 попытки клиента, включая блокировку трафика и внешнего DNS для FI при работающем RU, затем блокировку при восстановленных физических линиях. Клиент разрешил исходный финский домен только однажды.

Доступность задаёт сценарий. Время реакции зависит от интервала опроса и доступности API. Доменные маршруты, DNS и защита выхода `deny` заранее настроены в сетевом пространстве. Этот прогон охватывает локальный IPv4-трафик sing-box и новые потоки клиента.
