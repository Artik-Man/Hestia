# Полный отказ группы с активным адресным исключением

Исходники проверки: [tests/lab/steer-deny](../../tests/lab/steer-deny/). Отчёт и свидетельства остаются здесь. Перед повторным запуском применяйте [правила выбора стенда](../../docs/virtual-machines.md); исторические имена ВМ не являются указанием создать или запустить их.

При неудачном порядке правил sing-box сообщает, что селектор группы закрыт, но исключение ещё направляет UDP до X на FI2. Холодному запросу домена FI предшествует внешний DNS-запрос через FI1. Это воспроизведено в изолированной Debian ARM64. Для исправления внешняя проверка FI теперь предшествует и резолвингу реального адреса, и обработке адресного исключения. После допуска второе локальное SOCKS-входящее соединение попадает во внутренние правила FI. У внутреннего DNS транспорт использует селектор обычного выхода FI. [Отрицательный контроль](evidence/negative/verification.txt), [положительная серия](evidence/positive/verification.txt).

| Фаза защищённого стенда | FI TCP по FakeIP и прямому IP | FI UDP по FakeIP и прямому IP | Внешний DNS для нового FI-имени | RU TCP, UDP и DNS |
|---|---|---|---|---|
| Оба выхода доступны, исключение включено | FI1 | FI2 | FI1 | RU |
| Оба выхода признаны недоступными | Блокировка | Блокировка | Ни одного пакета | RU |
| Доступен только FI2 | FI2 | FI2 | FI2 | RU |
| Оба выхода восстановлены | FI1 | FI2 | FI1 | RU |

Физические интерфейсы оставались подняты, маршрут по умолчанию шёл через RU. Домены FI и RU имели общий реальный IPv4 `203.0.113.77`. Поэтому случайный выход тестового трафика был бы виден на одном из трёх интерфейсов. В отдельный интервал отправили только четыре новых FI-потока и запрос холодного FI-имени. На всех трёх WAN-захватах оказались контрольные метки самих захватов. Пакетов к порту сервиса и внешнему DNS было ноль, включая TCP SYN. В соседнем интервале TCP, UDP и холодный DNS разрешённой RU-группы успешно прошли через RU. После частичного восстановления имя FI впервые запрошено через FI2, включая ответ сервера, при нулевом трафике к сервису и DNS через FI1. Синтетический сервер возвращал тот же адрес, что и в остальных фазах. [Захваты и журнал](evidence/positive), [подтверждение блокировки](evidence/positive/blocked-gate.json), [выбор FI2 после частичного восстановления](evidence/positive/partial-gate.json).

Контроллер создал активное исключение сам по измерениям через `hestia steer`. После конечной серии измерений процесс остановился, а существующий файл исключений продолжал действовать. Готовность группы передавалась отдельными снимками через `hestia guard`. Проверены 28 новых потоков защищённой конфигурации и 22 в контроле обхода. В пределах каждого прогона PID sing-box и содержимое исключения были постоянны. Использовался sing-box 1.14.4 и ядро Linux ARM64 6.1.0-53-cloud. Границы опыта — синтетический IPv4, известные группы, новые потоки и доверенное сетевое пространство для локального SOCKS-входа. [Профиль стенда](evidence/positive/sing-box.json), [версия бинарника](evidence/positive/controller.sha256).

Для повторения соберите ARM64-бинарник Гестии и перенесите его с каталогом экспериментов на выделенную Debian ARM64-ВМ. Нужны sing-box 1.14.4, TUN, iproute2, iptables, Python 3, curl и tcpdump. Обе команды выполняются в госте из корня проекта, каждый выходной каталог должен быть пуст.

```sh
sudo bash tests/lab/steer-deny/lab.sh ./hestia negative /var/tmp/deny-control
sudo bash tests/lab/steer-deny/lab.sh ./hestia positive /var/tmp/deny-protected
```

В строках `PASS negative` проверяется ожидаемое воспроизведение утечки. Для независимого повторного разбора сохранённой серии запустите `python3 tests/lab/steer-deny/check.py verify experiments/steer-deny/evidence/positive positive` на Linux с tcpdump.
