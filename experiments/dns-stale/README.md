# Выдача старого A при временном отказе DNS

Две серии на Debian ARM64 используют одни и те же имена, реальные UDP DNS-пакеты и один экземпляр sing-box в каждой серии. Строгий режим включается по умолчанию. Во второй серии предел аварийной выдачи задан равным 24 с после окончания исходного TTL в 2 с. Для каждого имени клиент сохранил FakeIP и продолжил открывать новые TCP- и UDP-потоки к нему. Во всех фазах дополнительно проверялся отдельный DNS-запрос LAN-клиента. [Критерии](ACCEPTANCE.md), [строгая серия](evidence/strict/verification.txt), [аварийная серия](evidence/stale/verification.txt).

| Условие после окончания положительного A | Строгий режим | Аварийное окно 24 с |
|---|---|---|
| UDP-запрос пришёл к резолверу, DNS-ответ отсутствует | SERVFAIL, TCP и UDP блокированы | LAN получил тот же FakeIP с TTL 0, оба новых потока дошли до старого A через FI |
| Авторитетный NXDOMAIN с SOA | NXDOMAIN, данных нет | Такой же NXDOMAIN, данных нет |
| Авторитетный NOERROR с SOA без A (NODATA) | NOERROR без A, данных нет | Такой же NODATA, данных нет |
| Тот же резолвер вернул SERVFAIL после NXDOMAIN/NODATA | SERVFAIL, старых данных нет | SERVFAIL, старое положительное значение не восстановилось |
| Повторный временный SERVFAIL по имени с сохранённым A | SERVFAIL | Старый A внутри первоначального окна, TTL 0 |
| Повторный SERVFAIL за пределами исходного срока | SERVFAIL | SERVFAIL, старый A больше не используется |
| Для FI-домена закрылась группа внутри аварийного окна | DNS и клиентские данные заблокированы | DNS и клиентские данные заблокированы |
| Реальный адрес поменялся на B и восстановился DNS | TCP и UDP дошли до B | TCP и UDP дошли до B |

Для проверки границы времени мы прекратили получать новые положительные ответы после исходного A, запросили старый A дважды и подождали до истечения `исходный expiry + 24 с`. Шесть выдач имели TTL 0 и один исходный срок окончания. Возраст на момент выдачи составил от 2,19 до 9,22 с после исходного TTL, первый отказ за пределами окна зарегистрирован через 24,23 с после него. Ещё не прошло 24 с с момента последнего аварийного ответа. Уже на этом этапе устаревшие данные не выдавались. Для проверки запрета FI отдельно заново получили положительный A, дождались окончания TTL и запретили FI внутри нового окна. В интервале только FI-запросов на обоих внешних интерфейсах не было ни внешних DNS-пакетов, ни пакетов к порту сервиса. Сразу после этого другое имя и его TCP/UDP-сервис работали через RU. После восстановления FI авторитетный сервер выдал B=`203.0.113.22` вместо A=`203.0.113.11`. Новые потоки дошли до B по изначальным FakeIP. [Тайминги](evidence/stale/events.jsonl), [DNS и решения](evidence/stale/decisions.log), [захваты LAN/RU/FI](evidence/stale).

Проверены по 32 новых потока в каждой серии, IPv4, класс IN, одиночные A-ответы синтетических DNS-серверов зоны `lab.test`. Условия подтверждены по реальным запросам и ответам, включая QR/RCODE, SOA, TTL и отсутствие ответа при сетевом тайм-ауте. Контрольные суммы компонентов совпадают между сериями. [SHA-256](evidence/stale/code.sha256). Прогрев в этом испытании выключен. DNSSEC, браузерное кэширование, возможность использования прежнего адреса публичного сервиса и длительность уже открытых соединений находятся за границами опыта.

Для повторения перенесите каталоги `experiments/dns-stale`, `experiments/dns-rotation` и `experiments/dns-geo` в отдельную Debian ARM64-ВМ с TUN, sing-box 1.14.4, iproute2, tcpdump, Python 3 и python3-dnspython. Из корня проекта выполните в гостевой системе:

```sh
sudo bash experiments/dns-stale/lab.sh strict /var/tmp/strict-dns
sudo bash experiments/dns-stale/lab.sh stale /var/tmp/stale-dns
```

Каталоги результатов должны быть пустыми. Для независимого разбора положительной записи используйте `python3 experiments/dns-stale/verify.py stale experiments/dns-stale/evidence/stale`. Из того же набора общих исходников повторно проверены [ротация A](evidence/regression-rotation.txt) и [прогрев популярных имён](evidence/regression-warm.txt).
