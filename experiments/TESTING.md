# Проверки экспериментов

Из корня репозитория создайте окружение Python 3.11 или новее, установите wheel dnspython 2.3.0 из PyPI с проверкой закреплённого SHA-256, и запустите модульные тесты:

```sh
python3 -m venv /tmp/hestia-experiment-tests
. /tmp/hestia-experiment-tests/bin/activate
python -m pip install --require-hashes --only-binary=:all: -r experiments/requirements-test.txt
make test-experiments
```

Команда находит все файлы `test_*.py` в дереве `experiments/` и запускает каждый через стандартный `unittest` отдельным процессом из каталога теста. Так соседние опыты могут использовать одноимённые модули `cache.py` и `fixture.py`. Пустой тестовый файл, ошибка импорта или падение теста завершает команду с ненулевым кодом. Эти тесты также входят в `make check` и выполняются в CI. Для полного `make check` нужны инструменты Go и shell, перечисленные в [правилах проекта](../AGENTS.md).

Сквозные сетевые эксперименты запускаются отдельно на изолированных Linux-стендах. Конкретный `lab.sh` и порядок проверки захватов указаны в README соответствующего опыта. Например, [проверка перезапуска DNS](dns-restart/README.md) требует именованной одноразовой Linux-ВМ ARM64, root, TUN, сетевых пространств имён, sing-box, iproute2 и tcpdump. Модульные тесты проверяют изолированную логику и анализ доказательств. Для подтверждения фактического маршрута пакета нужен сетевой прогон. Используйте только выделенный стенд, указанный в инструкции опыта.

Назначение `verify.py` зависит от опыта. В DNS restart он повторно анализирует сохранённые захваты, а в [list-binding](list-binding/README.md) отправляет запросы к работающему API и создаёт новые клиентские соединения. Для list-binding нужен запущенный стенд. CI запускает только модульные `test_*.py`.
