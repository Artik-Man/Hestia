# Смена группы списка через два WireGuard-подключения

Исходники проверки: [tests/lab/list-binding](../../tests/lab/list-binding/). Отчёт и свидетельства остаются здесь. Перед повторным запуском применяйте [правила выбора стенда](../../docs/virtual-machines.md); исторические имена ВМ не являются указанием создать или запустить их.

Проверяем, через какой выход проходит **новое TCP-соединение** после изменения привязки через панель, какой маршрут остаётся при отклонении запроса и как шлюз восстанавливается после гибели помощника в середине применения.

## Стенд

Отдельная Lima ВМ `hestia-binding-test` с Debian 12 ARM64, ядром `6.1.0-53-cloud-arm64`, systemd и sing-box 1.14.4. Установщик развернул службы Гестии из профиля v1. Панель работала отдельной системной учётной записью, входящей в группу `hestia-snapshot`. В sudoers для неё разрешена только команда `/usr/local/bin/hestia -apply-binding`. На хосте собраны Linux ARM64 бинарники Go 1.27.3 из рабочего дерева на основе `d4e5db1947565a5eb635c55b450bc97eac1f9ac9`. Идентификаторы фактически запущенных бинарников и окружения указаны в [манифесте](evidence/environment.txt).

В двух изолированных пространствах имён Linux работают независимые WireGuard-пиры, DNS и HTTP. Оба DNS отвечают одинаковым адресом `198.18.42.42`, а оба HTTP-сервера слушают порт `18080`. Ответ `alpha` выдаёт только сервер первого пира, `beta` — только второго. Каждый запрос создаёт новое SOCKS5-соединение с передачей имени шлюзу. У проверяемого списка две маски. Отдельная контрольная маска всегда привязана к первой группе. Исходные ключи генерируются внутри гостя и остаются там.

## Результат

| Действие | Ожидание и наблюдение |
|---|---|
| Открыть новые соединения по обеим маскам списка | Перед изменением оба сервера назначения наблюдаются как `alpha`. Контроль также возвращает `alpha`. |
| Отправить запрос с чужим Origin или с `Sec-Fetch-Site: cross-site` | Оба запроса вернули 403. Пять файлов управляемой установки сохранили свои SHA-256, трафик остался на `alpha`. |
| Привязать список к `group-beta` | Ответ 200 содержал действующую группу. По обеим маскам получен `beta`, по контролю — `alpha`. Обе исходные маски сохранились. |
| Повторить запрос со старой ожидаемой группой или указать неизвестную группу | Ответы 409 и 404. Пять файлов и маршруты не изменились. |
| Отклонить запуск sing-box с новой привязкой | Тестовый `ExecStartPre` прочитал переданный службе credential и отказал только варианту с `group-alpha`. PUT вернул 503. Предыдущие пять файлов побайтово восстановлены, экспорт снова совпал с действующим профилем. Оба новых соединения прошли к `beta`, контроль — к `alpha`. |
| Снять привязку | Получен 200 с пустым идентификатором группы. Маски сохранились. Новые соединения прошли по группе по умолчанию к `alpha`. |
| Прервать помощник до подтверждения | При активном журнале незавершённой операции новое соединение уже достигло `beta`. В этот момент помощник получил SIGKILL, HTTP-клиент получил 503. Служба наблюдения сама восстановила все пять файлов и прежний маршрут. Новые соединения по обоим именам списка снова достигли `alpha`. Между аварией и проверкой дополнительного PUT и перезагрузки не было. |

Наличие журнала и успешная доставка запроса к `beta` до ответа означают, что кандидат может пропускать новые соединения в окне проверки. Неудачный HTTP-ответ не исключает временного использования кандидата. Журнал процесса восстановления и измеренный интервал относятся к одному запуску на ВМ. Метод запускает новые TCP-соединения через SOCKS. Он не проверяет UDP-клиентов, сохранение старых соединений, TUN на физическом шлюзе или внешних VPN-провайдеров. [Установка](evidence/installer.txt) · [Переходы и отказ старта](evidence/verification.txt) · [SIGKILL и восстановление](evidence/crash.txt).

Первый вариант инъекции ссылался на файл в `/var/tmp`. Служба с `PrivateTmp=yes` не видела его при запуске ни кандидата, ни прежней конфигурации. Тогда файлы были восстановлены, обе службы остановились, журнал сохранился, чтение снимка вернуло 503. Этот прогон не подтверждал восстановление маршрута. После переноса тестового обработчика в `/run` повтор проверил отказ только нового поколения. Панель изменяет установленную конфигурацию и экспорт из неё. Входной файл профиля, который оператор когда-то передал установщику, сохраняет исходное содержание.

## Повторение

Используйте согласованный изолированный Linux ARM64-стенд по действующим правилам ВМ. Создание новой ВМ требует отдельного разрешения; прежний профиль доступен в [историческом комплекте](../README.md#историческая-подготовка-вм). Инструменты `wireguard-tools`, `dnsmasq-base`, `curl`, `sudo`, `iproute2` и Python 3 нужны в госте. Пример запуска с хоста из корня проекта:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go -C backend build -o /tmp/hestia-binding ./cmd/hestia
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go -C backend build -o /tmp/hestia-binding-panel ./cmd/hestia-panel
(cd frontend && npm ci && npm run build)
```

Передайте в гостевую ВМ в один рабочий каталог оба собранных файла, каталоги `deploy/`, `tests/lab/list-binding/`, `frontend/dist/hestia/browser/` и официальный архив `sing-box-1.14.4-linux-arm64.tar.gz`. Установщик проверяет его по закреплённой SHA-256. Далее выполняйте в этом каталоге гостя:

```sh
sudo apt-get install -y --no-install-recommends wireguard-tools dnsmasq-base
sudo bash tests/lab/list-binding/peers.sh
sudo bash deploy/install.sh --config /var/tmp/hestia-binding-lab/profile.json \
    --controller-binary ./hestia-binding --sing-box-archive ./sing-box-1.14.4-linux-arm64.tar.gz
sudo bash tests/lab/list-binding/panel.sh ./hestia-binding-panel ./frontend/dist/hestia/browser
sudo python3 -I tests/lab/list-binding/verify.py
sudo python3 -I tests/lab/list-binding/verify.py --crash
```

Оба прогона должны завершиться строкой `PASS`. Первый оставляет список без привязки. Второй начинает с этого состояния и возвращает его. Временные drop-in удаляются по завершении проверки. Рабочие ключи и конфигурации sing-box из гостя в отчёт не переносят.
