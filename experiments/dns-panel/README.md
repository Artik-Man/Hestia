# Настройки DNS, запросы роутера и прогрев

**Вопрос.** Можно ли через страницу одновременно управлять ручными именами и автоматическими исключениями, сохранить правки после перезагрузки и подтвердить прогрев входящими и исходящими DNS-запросами?

**Среда.** 5 ноября 2026 года, macOS ARM64, Go 1.27.3, Chromium через Playwright. Проверена рабочая копия на базе `84952fe`. HTTP и DNS слушали только loopback. В браузерной проверке с настоящим Go API новая временная директория политики и случайный HTTP-порт выделяются для каждого запуска. В сетевом тесте роль роутера выполняет тестовый клиент, а роль резолвера подключения — локальный UDP-сервер. Производственные обработчики UDP/TCP, планировщик, кэш и публикация отчётов работают с ними через сокеты.

| Проверка | Ожидаемый и наблюдаемый результат |
|---|---|
| Playwright, рабочая страница + Go API | После повторной загрузки подтверждены срок хранения и окно аварийной выдачи. Страница сохранила ручное имя и исключение для одного домена. Перезагрузка подтвердила обе записи. Исправление и снятие исключения сохранили ручное имя. Второй редактор получил конфликт ревизии и смог перечитать изменения. |
| Playwright, ширина 360 пикселей, контролируемые ответы API | Видны три раздела в согласованном порядке. Проверены клавиатура, исключение и возврат популярного имени, различение пустого списка и недоступных наблюдений. |
| Два клиентских запроса одного имени через UDP и TCP | Резолвер выхода получил один запрос A. Служба учла оба клиентских обращения, второе обслужила из кэша. |
| Ручное имя при действующем исключении | Планировщик отправил запросы A и AAAA. Фоновые обновления не повысили пороговый счётчик. Снятие исключения вернуло популярное имя в автоматический список. |
| Истечение TTL и перезапуск | Новый клиентский запрос к имени с истёкшим TTL получил изменившийся адрес. Для ещё действующей записи после перезапуска сохранились адрес и исходное время истечения. |

[Результат Playwright](evidence/playwright.txt) · [Протокол DNS с детектором гонок](evidence/loopback.txt) · [Тесты службы](../../backend/internal/dnsservice/integration_test.go)

**Что исправлено при проверке.** Первое сохранение отображённых исходных значений создаёт первую версию политики. Добавлен браузерный сценарий, проверяющий подтверждение этого перехода. Смена политики из второй вкладки теперь проверяется также на настоящем API. В DNS-службе отдельно проверяются отзыв разрешения во время открытия сокета и переоценка путей после изменения конфигурации.

**Воспроизведение из корня проекта.** Для браузерного прогона нужны зависимости из `frontend/package-lock.json`, Chromium Playwright и Go. При использовании локальной сборки Chromium укажите исполняемый файл в `CHROME_BIN`.

```sh
go -C backend test -race -count=1 -run '^TestDNSWorkerIntegration$' -v ./internal/dnsservice
cd frontend
npm ci
npx playwright install chromium
npm run build
npm run test:browser
```

**Границы.** Полный набор проверил код на локальной машине. Приложения также собраны для Linux ARM64. Запуск установленного systemd-модуля, изоляция реальных выходов и пересылка с физического маршрутизатора требуют отдельного стендового прогона. Стендовая ВМ и настройки домашнего маршрутизатора не менялись.

Для следующего разрешённого прогона подготовлен [сценарий Linux ARM64](verify.py). В каталоге комплекта должны находиться статические бинарники `hestia` и `hestia-panel` из данной версии проекта, согласованный `sing-box` и `deploy/profile.py`. На выделенной Linux-ВМ команда `sudo unshare --net python3 verify.py /путь/к/комплекту` создаёт изолированную сеть без внешнего маршрута, временные конфигурации и chroot. Наблюдений от этого сценария в результатах выше нет.

## Проверка фонового обновления на stage1, 5 ноября 2026

На установленной ревизии `0c9b759` тестовая ВМ обращалась к DNS роутера. На входе Гестии зафиксированы пять запросов к google.com. При N=5, X=24 ч и Y=10 мин ожидалось, что имя войдёт в прогрев, а фоновое обновление сохранит клиентский счётчик. После тайм-аута фоновой попытки служба получила положительный ответ AAAA через keenetic-direct от 8.8.8.8 с TTL 127 с. В снимках до и после этого успеха было по пять обращений. Проверено одно успешное обновление AAAA. Для воспроизведения наблюдения при активном имени прочитайте `curl -fsS http://192.168.1.133:8080/api/dns/warm`, дождитесь новой строки в `journalctl -fu hestia-dns.service --grep='DNS warm name=google[.]com '` и сравните следующий снимок. [Свидетельства с отметками времени](evidence/stage1-google-warm.txt).

**Чёрный список на stage1.** При тех же настройках Playwright исключил популярное имя без ручной записи. Ожидались исчезновение из автоматического списка и прекращение фоновых попыток. Имя исчезло в ревизии 1 и осталось в исключениях. За 10 мин 24 с в журнале нет новых записей прогрева google.com. Внутри интервала systemd дважды перезапустил службу, что сбрасывает спрос. Для изолированной проверки отмены уже назначенного обновления нужен прогон с непрерывно работающим планировщиком и подсчётом запросов на тестовом резолвере. Для повторения сначала подтвердите успешный автопрогрев, исключите имя в панели и сравните отчёт и журнал спустя полный интервал Y.

## Регрессия работающего планировщика и панели

Локальный прогон рабочего дерева на базе `0c9b759` проверяет, прекращает ли действующий планировщик отправку после исключения. Виртуальные часы Go позволяют пройти несколько интервалов без перезапуска процесса. Число отправок за 28 минут в чёрном списке осталось прежним. После снятия исключения планировщик возобновил обновления по двум исходным обращениям и остановился при истечении первого из них. При повторном запрете FI клиент получил обновлённый адрес RU из кэша, а запрос имени с обязательным FI вернул SERVFAIL. [Протокол локального прогона](evidence/automatic-regression.txt).

Браузерный сценарий проверяет те же списки с настоящей DNS-службой и HTTP API на loopback. Три клиентских запроса создают спрос. После исключения и восстановления через интерфейс отчёт содержит исходные три обращения. Этот прогон проверяет DNS и панель в изолированном окружении. Для воспроизведения выполните из корня проекта:

```sh
go -C backend test -race -count=1 -v -run '^(TestAutomaticExclusionResumeAndWindowExpiry|TestScheduledRefreshUsesEarlierOfIntervalAndTTL|TestSplitWarmRepeatedRevocation)$' ./internal/dnsresolver
(cd frontend && npm run test:browser:dns-api)
```

Тот же Playwright-сценарий отправил отдельный UDP-запрос дважды с одного порта и с одинаковым идентификатором. После первой передачи панель показала 100 % попыток без замеченного повтора, после второй — 50 % (один повтор на две передачи). Тест с настоящим UDP-входом отдельно проверяет содержимое ответов, число клиентских обращений и число запросов к резолверу. [Сценарий Playwright](../../frontend/tests/browser/dns-worker.mjs) · [Проверка UDP-службы](../../backend/internal/dnsservice/integration_test.go).
