# Настройки DNS, запросы роутера и прогрев

**Вопрос.** Можно ли через страницу одновременно управлять ручными именами и автоматическими исключениями, сохранить правки после перезагрузки и подтвердить прогрев входящими и исходящими DNS-запросами?

**Среда.** 5 ноября 2026 года, macOS ARM64, Go 1.27.3, Chromium через Playwright. Проверена рабочая копия на базе `84952fe`. HTTP и DNS слушали только loopback. В браузерной проверке с настоящим Go API новая временная директория политики и случайный HTTP-порт выделяются для каждого запуска. В сетевом тесте роль роутера выполняет тестовый клиент, а роль резолвера подключения — локальный UDP-сервер. Производственные обработчики UDP/TCP, планировщик, кэш и публикация отчётов работают с ними через сокеты.

| Проверка | Ожидаемый и наблюдаемый результат |
|---|---|
| Playwright, рабочая страница + Go API | После повторной загрузки подтверждены срок хранения и окно аварийной выдачи. Страница сохранила ручное имя и исключение для одного домена. Перезагрузка подтвердила обе записи. Исправление и снятие исключения сохранили ручное имя. Второй редактор получил конфликт ревизии и смог перечитать изменения. |
| Playwright, ширина 360 пикселей, контролируемые ответы API | Видны три раздела в согласованном порядке. Проверены клавиатура, исключение и возврат популярного имени, различение пустого списка и недоступных наблюдений. |
| Два клиентских запроса одного имени через UDP и TCP | Резолвер выхода получил один запрос A. Служба учла оба клиентских обращения, второе обслужила из кэша. |
| Ручное имя при действующем исключении | Планировщик отправил запросы A и AAAA. Фоновые обновления не повысили пороговый счётчик. Снятие исключения вернуло популярное имя в автоматический список. |
| Истечение TTL и перезапуск | Новый клиентский запрос к имени с истёкшим TTL получил изменившийся адрес. Для ещё действующей записи после перезапуска сохранились адрес и исходное время истечения. |

**Что исправлено при проверке.** Первое сохранение отображённых исходных значений создаёт первую версию политики. Добавлен браузерный сценарий, проверяющий подтверждение этого перехода. Смена политики из второй вкладки теперь проверяется также на настоящем API. В DNS-службе отдельно проверяются отзыв разрешения во время открытия сокета и переоценка путей после изменения конфигурации.

**Воспроизведение из корня проекта.** Для браузерного прогона нужны зависимости из `frontend/package-lock.json`, Chromium Playwright и Go. При использовании локальной сборки Chromium укажите исполняемый файл в `CHROME_BIN`.

```sh
go test -race -count=1 -run '^TestDNSWorkerIntegration$' -v ./internal/dnsservice
cd frontend
npm ci
npx playwright install chromium
npm run build
npm run test:browser
```

**Границы.** Полный набор проверил код на локальной машине. Приложения также собраны для Linux ARM64. Запуск установленного systemd-модуля, изоляция реальных выходов и пересылка с физического маршрутизатора требуют отдельного стендового прогона. Стендовая ВМ и настройки домашнего маршрутизатора не менялись.

Для следующего разрешённого прогона подготовлен [сценарий Linux ARM64](verify.py). В каталоге комплекта должны находиться статические бинарники `hestia` и `hestia-panel` из данной версии проекта, согласованный `sing-box` и `deploy/profile.py`. На выделенной Linux-ВМ команда `sudo unshare --net python3 verify.py /путь/к/комплекту` создаёт изолированную сеть без внешнего маршрута, временные конфигурации и chroot. Наблюдений от этого сценария в результатах выше нет.
