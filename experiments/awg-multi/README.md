# Одновременные выходы WireGuard и AmneziaWG

Проверяем, могут ли две группы работать через разные туннели с одинаковыми внутренними адресами. При потере второго peer первый должен сохранить установленную TCP-сессию, а второй не должен вывести отмеченный IPv4/IPv6-пакет в обычную сеть.

Опыт запускается только на выделенной ВМ Lima `hestia-load-01` (hostname `lima-hestia-load-01`). В проверке 4 ноября 2026 года использовано ядро Debian ARM64 `6.1.0-53-cloud-arm64`, рабочая копия Гестии на базе `44bb04d`, userspace `amneziawg-go v3.1.20260828`, утилита `awg 3.1.20260812` и sing-box 1.14.4. Внутри новых PID, mount и network namespaces сценарий поднимает два локальных peer. Каждый имеет одинаковый внутренний адрес `10.77.0.1`, служит DNS и HTTPS, возвращает собственное имя. У профилей одинаковые `10.77.0.2/32` и `AllowedIPs = 0.0.0.0/0`. Для обоих семейств адресов существует рабочий внешний маршрут, чтобы блокировку можно было отличить от отсутствия сети. Временные секреты и TLS-сертификат создаются в приватном tmpfs. Доверие к тестовому сертификату задаётся только для процесса стенда.

В первом прогоне оба runtime достигли readiness, две проверки вернули имена ожидаемых peer. При остановке и повторном запуске второго профиль первого сохранил один TLS-сокет. Основная таблица IPv4 не изменилась, запрос маршрута с меткой второго туннеля вернул отказ для IPv4 и IPv6. В дополнительном прогоне проверили запуск WG без `PersistentKeepalive` и AWG c `PersistentKeepalive = 25`, параметры после handshake сохранились. На шаге проверки групп sing-box отказался загружать конфигурацию без явного DNS-резолвера. [Промежуточное свидетельство](evidence/initial.txt).

В заключительном прогоне предварительная проверка отклонила чужое правило `priority 800 from all lookup main` до создания манифеста и интерфейса. После его снятия правила с приоритетами 1000 и 1001 для входящих интерфейсов, как в схеме 3, не помешали запустить два выхода. После привязки DNS-резолвера к каждому активному выходу сгенерированная конфигурация запустилась в sing-box 1.14.4. Через первую группу клиент получил `tunnel-a`, через вторую — `tunnel-b`. Клиент отдавал имя через SOCKS, а нужное имя разрешал только DNS соответствующего peer. После остановки второго туннеля его группа прекратила отвечать; через живой внешний интерфейс прошли два разрешённых контрольных UDP-пакета (IPv4 и IPv6) и ни одного отмеченного запрещённого пакета. Затем замена второго профиля на недоступный peer завершилась ошибкой handshake в установленный срок. После возврата рабочего профиля второй туннель восстановился. Клиент группы A сохранил TLS-соединение во время остановки, неудачного запуска и восстановления второго туннеля и получил 108 ответов на том же TCP-сокете. [Журнал окончательного прогона и SHA-256 проверенного кода](evidence/groups-20261104.txt).

Для воспроизведения скопируйте в приватный каталог на `hestia-load-01` программу `hestia` для Linux ARM64, `amneziawg-go`, утилиту `awg`, бинарник sing-box с его `libcronet.so`, файлы этого стенда и `deploy/profile.py`. На ВМ выполните из этого каталога:

```bash
sudo env LD_LIBRARY_PATH="$PWD" unshare --mount --net --pid --fork --mount-proc \
    bash ./lab.sh "$PWD/hestia" "$PWD/amneziawg-go" "$PWD/awg" "$PWD/sing-box"
```

Стенд использует процессные экземпляры runtime. За пределами этого опыта остаются загрузка ВМ через systemd, обновление установленной версии и импорт через панель.

4 ноября по запросу владельца обновили установленную Гестию на `hestia-stage1` с одним рабочим профилем `awg-home`. Первая попытка выявила неполное снятие маршрутов старым runtime и восстановила прежнюю службу. После исправления миграции обновление сохранило `awg-home` на `awg0` в той же группе с приоритетом 1. Именованная служба запущена, API вернул `ready`, штатная проверка шлюза прошла. Основные маршруты совпали до и после. Второй профиль на личной ВМ не импортировали, перезагрузку не выполняли.
