# Проверка физических подключений

Исходники проверки: [tests/lab/physical-connections](../../tests/lab/physical-connections/). Отчёт и свидетельства остаются здесь. Перед повторным запуском применяйте [правила выбора стенда](../../agents/virtual-machines.md); исторические имена ВМ не являются указанием создать или запустить их.

Имена ВМ в описании приведены к принятой 6 ноября 2026 года схеме [prod/dev/client](../../AGENTS.md#виртуальные-машины). Исходные имена в свидетельствах и путях резервных копий сохранены.

5 ноября 2026 года на выделенной ВМ `hestia-dev` проверяли, какие подключения можно испытать с действующим ядром. Ядро `6.1.0-53-cloud-arm64` предоставляет Ethernet-адаптер virtio `eth0` с активным линком. Второй интерфейс — `lo`. В гостевой системе отсутствуют модуль `mac80211_hwsim`, беспроводной адаптер, `iw`, `hostapd`, `wpa_supplicant` и `nmcli`. Поэтому радиосоединение с точкой доступа и передачу трафика по Wi-Fi на этой ВМ проверить нельзя. [Инвентаризация стенда](evidence/load1-environment.txt).

Воспроизвести инвентаризацию на этой ВМ можно командами:

```sh
uname -srmo
ls /sys/class/net
readlink -f /sys/class/net/eth0/device
cat /sys/class/net/eth0/carrier
/sbin/modinfo -n mac80211_hwsim
```

Собранный для Linux ARM64 обработчик `hestia -physical-list` прочитал реальные устройства из sysfs. Профиль стенда связывал один выход с `eth0`, второй — с отсутствующим `eth-missing`. Обработчик вернул для `eth0` признаки `present=true` и `online=true`, для отсутствующего интерфейса оба признака равны `false`. Имена выходов соответствовали привязкам. В ответе отсутствовал `lo`, список Wi-Fi был пуст. Сценарий запускался с временными `/etc` и `/run` внутри отдельного пространства монтирования. [Точный хеш сборки и публичный ответ](evidence/inventory.txt).

Для повторения на выделенной ВМ передайте ARM64-бинарник и `inventory.sh` в один временный каталог. Выполните в нём:

```sh
sudo unshare --mount bash ./inventory.sh ./hestia
```

В Chromium сборка Angular прошла десять браузерных тестов с синтетическим REST API. Вручную заданный Wi-Fi использовал выбранные `wlan1`, диапазон 5 ГГц и SSID. После перезагрузки профиль сохранился; изменение на 2,4 ГГц отправило запрос без пароля, а подтверждённое удаление убрало запись. Отдельно проверено поведение шлюза без радиоустройства. Проверка браузера подтверждает формирование запросов и отображение данных. [Журнал браузерных проверок](evidence/browser.txt).

Для воспроизведения в каталоге `frontend` выполните `npm run build`, затем `CHROME_BIN=/путь/к/chrome npm run test:browser`.

На той же ВМ распаковали Debian NetworkManager 1.42.4 в `/tmp`. Утилита `nmcli --offline` прочитала реальные сгенерированные keyfile-профили для 2,4 и 5 ГГц. При повторной сериализации сохранились диапазон, SSID с пробелами и специальными символами, пароль WPA, правило исходящего интерфейса, отдельная таблица маршрутов и запрет использования DHCP DNS шлюзом. Службу NetworkManager не запускали. В том же прогоне отдельные тесты с подменой команд проверили откат, удаление, отклонение файлов другого владельца и появление чужого активного подключения во время сохранения. [Версия, хеш и журнал](evidence/offline-keyfile.txt).

Воспроизведение офлайн-проверки с доступным `nmcli` на Linux:

```sh
HESTIA_NMCLI_OFFLINE=/usr/bin/nmcli go -C backend test -count=1 -v ./internal/physical
```

## Повторный прогон 6 ноября 2026 года

На `hestia-dev` после установки модульной сборки на базе `66bb2fa` проверен настоящий helper `-physical-list` с отдельными приватными `/etc` и `/run`. Ожидались присутствующий и активный `eth0`, отсутствующий `eth-missing`, отсутствие доступного Wi-Fi; фактический результат совпал, exit 0. [Свидетельство](../dev-validation/evidence/network/physical-inventory.txt), [общий протокол](../dev-validation/README.md). Использована команда `sudo unshare --mount --propagation private bash tests/lab/physical-connections/inventory.sh /путь/к/hestia`. Путь sysfs оставлен реальным; настройки интерфейсов не менялись. Сохранение/активация настоящего Wi-Fi и управление портами Keenetic не проверялись.

## Отключение VPN и автоматическое обновление — 13 ноября 2026 года

На macOS ARM64 локально проверены скрытие служебного входа в прямых и виртуальных подключениях, административное отключение VPN с сохранением параметров и опрос состояний. Подменённый API позволяет проверить интерфейс без доступа к Keenetic. Компилятор проверен на синтетических WireGuard/AWG/Hysteria-профилях: отключённые маршруты блокируются, нативный endpoint удаляется из активной конфигурации, приватные данные сохраняются для восстановления; перенос и порядок групп не снимают отключение.

Go-тесты, `go vet`, 63 проверки deploy (7 пропусков по условиям окружения), 27 frontend unit-тестов, линтер и production-сборка прошли. Браузерные сценарии подключений проверяют переключение всех типов VPN, ошибки подтверждения и опрос раз в 3 секунды: незавершённые запросы не перекрываются, черновик и последний список сохраняются при 503, повторный сбой не создаёт поток уведомлений. Браузерная проверка качества подтверждает автоматическое обновление раз в 5 секунд без кнопки и сохранение черновика настроек. [Версия и свидетельства](evidence/admin-toggle-polling-20261113.txt). Реальная доставка пакетов на устройстве не измерялась, обновление на Keenetic не устанавливалось.

Повторение: `make test test-installer docs-check`; `cd frontend && npm run lint && npm test && npm run build && node --test tests/browser/quality.mjs`; для подключения — сценарии ToggleSwitch и polling в `tests/browser/profile-import.mjs`. Общий `make check` ограничен отсутствующим ShellCheck и Python-модулем `dns` для DNS lab-тестов.

## Исправление переключения Laurel — установка `0.1.16`, 13 ноября 2026 года

На установленной `0.1.15` запрос выключения Laurel (AWG3.1) вернул HTTP 409: фоновый опрос конкурировал с транзакцией за блокировку. Локально воспроизведены ещё два условия: отказ административного включения при недоступном peer и зависание UI при задержанном ответе, в том числе после отката.

Исправление приостанавливает связанные чтения на время операции, обрабатывает краткий конфликт без ошибки чтения и проверяет результат конкретной попытки по UUID. Включение требует исправных сетевых guard, но допускает временно недоступный peer; доступность и административное состояние остаются разными. Проверки создания/редактирования профиля и отката сохраняют строгие требования.

По поручению владельца в общий IPK `0.1.16` также включены изменения журнала из параллельного чата. До установки прошли проверки исходников, 19 браузерных сценариев подключений, 27 unit-тестов, компилятор профилей и race tests. После установки supervisor готов, конфигурации валидны, данные профиля и default routes сохранились. В браузере на самом Keenetic Laurel выключился за 5,977 с и включился обратно за 23,770 с в той же вкладке — без перезагрузки и ошибок. Оба результата подтверждены API-квитанциями. Исходные состояния всех VPN восстановлены; переключатель автообновления журнала включён по умолчанию.

[Свидетельство, версия пакета и границы вывода](evidence/vpn-toggle-fix-20261113.txt). Резервная копия и rollback `0.1.15` сохранены в root-only каталоге. Пропускная способность и физический egress этим прогоном не измерялись.
