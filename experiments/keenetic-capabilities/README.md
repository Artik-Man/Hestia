# Подготовка диагностики Keenetic KN-1012

## Вопрос и статус

Можно ли подготовить локальный комплект, позволяющий начать проверку предпосылок работы Гестии на KN-1012, не меняя состояние роутера?

6 ноября 2026 года завершена локальная подготовка по [спецификации](../../docs/features/keenetic-diagnostics.md). До возвращения владельца подключений к роутеру не было. После его явного разрешения выполнены загрузка диагностического комплекта и инвентаризация на KN-1012. Диагностический бинарник работает; совместимость полного приложения и сетевых функций пока не подтверждена. Настройки сети и службы не изменялись, ВМ не использовались.

## Среда и версия

Сборочная машина — macOS ARM64; Go 1.27.3, Python 3.14.7, Node 26.8.2, npm 12.2.1. Исходная ревизия — `ca2bb3a7d36ce0414e318311ebb3429dc33098e4`, ветка `keenetic`; новые исходники и фактические хеши фиксируются манифестом диагностического комплекта. shfmt 3.11.0 и ShellCheck 0.11.0 используются локально.

Целевое устройство по ранее сохранённым сведениям: KN-1012, KeeneticOS 5.2 Beta 2, aarch64, Entware на USB 8 ГБ. Эти сведения в текущем этапе не перепроверялись.

## Ожидаемый результат

Локально собраны диагностический бинарник Linux ARM64 и экспериментальный комплект приложения, сохранены манифесты и контрольные суммы. Автотесты проверяют ограниченность инвентаризации и честные статусы. Установка `.ipk` и платформенные адаптеры не входят в комплект.

## Воспроизведение локальной подготовки

Из корня проекта:

```sh
python3 scripts/build-keenetic-diagnostics/run.py
make build
make fmt
make check
```

Предпосылки полной сборки и закреплённые runtime-входы — в [инструкции](../../scripts/build/readme.md). Формат и запуск диагностики — в [инструкции комплекта](../../scripts/build-keenetic-diagnostics/readme.md). Команды этого раздела не передают файлы на устройства.

## Фактические результаты

Локальная подготовка завершена. Готовые файлы находятся вне Git в `dist/`:

- `dist/keenetic-diagnostics/20261106-keenetic-inventory-1.tar.gz` — диагностический комплект, 2 313 360 байт;
- `dist/artifacts/20261106-173656-ca2bb3a7d36c/keenetic-arm64-experimental.tar.gz` — экспериментальное приложение, 58 340 247 байт;
- рядом с каждым архивом расположен файл `.sha256`; распакованные каталоги сохранены для проверки.

Хеши архивов и размеры записаны в [artifacts.json](evidence/artifacts.json). Для каждого файла из манифестов проверен SHA-256 как в исходном каталоге, так и внутри созданного архива. Для диагностики также прошла `shasum -a 256 -c SHA256SUMS`. Бинарник определён как статический ELF AArch64. Манифесты честно фиксируют исходную ревизию и `dirty: true`: сборка выполнялась из рабочего дерева с новыми исходниками, их хеши сохранены. Обе сборки локальные, установка не выполнялась.

## Инвентаризация на KN-1012 — 6 ноября 2026 года

Владелец разрешил перенос диагностического комплекта в отдельный временный каталог и запуск инвентаризации. Использован ранее подтверждённый SSH-доступ с обязательной проверкой известного ключа хоста. На роутере создан приватный каталог `/opt/tmp/hestia-diagnostics.sqtO9h`; архив и распакованные файлы проверены SHA-256 до исполнения. [Передача и контрольные суммы](evidence/router-inventory-20261106/03-transfer-and-checksums.json).

Первый успешный запуск кода проекта на физическом устройстве — `--help`, 19:04:05 МСК (16:04:05 UTC), код завершения 0. [Свидетельство](evidence/router-inventory-20261106/04-first-execution-help.json). Этот факт завершает разрешённый период прямой работы в `master`; текущая работа ведётся в `keenetic`. Запуск диагностики не означает установку рабочей службы Hestia.

`--version` подтвердил `20261106-keenetic-inventory-1`; `--inventory` завершился с кодом 0 в 19:04:51 МСК. [Версия](evidence/router-inventory-20261106/05-version.json), [исполнение и исходный вывод](evidence/router-inventory-20261106/06-inventory-execution.json), [отчёт JSON](evidence/router-inventory-20261106/inventory.json).

Инвентаризация ищет утилиты только в `/opt/bin`, `/opt/sbin`, `/usr/bin`, `/usr/sbin`, `/bin`, `/sbin`. Все 13 функциональных возможностей оставлены `not_tested`.

Первый SSH-вызов из песочницы был запрещён средой выполнения ([журнал](evidence/router-inventory-20261106/01-preflight.json)); разрешённый повтор со снятием ограничения установил соединение. Подготовительный вызов вернул 127 из-за отсутствия необязательной команды `timeout`, остальные проверки места и инструментов прошли ([журнал](evidence/router-inventory-20261106/02-preflight-authorized.json)). Время SSH-операций ограничивалось локально; запуск диагностики завершился штатно.

Файлы оставлены в `/opt/tmp/hestia-diagnostics.sqtO9h/20261106-keenetic-inventory-1`, отчёт — `inventory.json` внутри этого каталога; локальная копия сохранена в свидетельствах. SHA-256 отчёта на роутере и локально совпал: `050cf970599401c83d10d46c0101a9c409c112270fd2ea5abf3efbfd38977abd` ([проверка](evidence/router-inventory-20261106/07-report-checksum.json)). Независимый тестировщик подтвердил идентичность комплекта, коды завершения, версию, схему JSON и сохранение 13 статусов `not_tested` ([заключение](evidence/router-inventory-20261106/validation.txt)). Постоянные службы, VPN, маршруты и настройки не создавались и не менялись. Для воспроизведения после согласования доступа: сверить `SHA256SUMS` в этом каталоге, выполнить `./bin/hestia-keenetic-diagnostics --version`, затем `./bin/hestia-keenetic-diagnostics --inventory`, сохранив stdout в новый файл на машине оператора.

Следующий вопрос — доступность runtime и средств перехвата/маршрутизации на этой прошивке. Для него нужна отдельная ограниченная проба с восстановлением временных ресурсов; успешная инвентаризация её не заменяет.
