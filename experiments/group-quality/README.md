# Переключение всей группы по двум контрольным адресам

Исходники проверки: [tests/lab/group-quality](../../tests/lab/group-quality/). Отчёт и свидетельства остаются здесь. Перед повторным запуском применяйте [правила выбора стенда](../../docs/virtual-machines.md); исторические имена ВМ не являются указанием создать или запустить их.

На изолированной Debian ARM64 контроллер получал противоречащие административному приоритету измерения и менял основной выход FI. Клиент обращался по TCP и UDP к третьему адресу Z (`203.0.113.77`), которого нет в настройках измерителя. В каждой из пяти фаз проверяли прямой IPv4, ранее настроенный путь через FI с FakeIP и явное правило RU с отдельным FakeIP для того же Z. Новые TCP- и UDP-потоки подтверждены ответами удалённого сервера и захватами на трёх выходах. [Протокол](evidence/verification.txt).

| Фаза | Что показали пробы | Куда пошли новые FI-потоки до Z |
|---|---|---|
| Начальные условия | Обе цели доступны через оба выхода | FI1 |
| Потери на FI1 | FI1 выборочно теряет UDP до X и Y, FI2 доставляет | FI2 |
| Пути восстановлены | Потери вышли из окна, качество равно | FI2 |
| Общий отказ X | X не отвечает ни через один выход, Y доступен через оба | FI2 |
| Потери на FI2 | Обе цели показывают преимущество FI1 | FI1 |

В общей сложности проверены 38 реальных раундов, 152 маркированные пробы и 30 новых клиентских потоков. За полное окно отказа X обе стороны потеряли все 10 проб к X и приняли все 10 к Y. В интервале доступен ответ управляющего API о FI2. Захват loopback содержит запрос чтения, ни одного запроса записи селектора. Российский домен сохранил RU во всех фазах. [Журнал решений](evidence/decisions.jsonl), [состояние при отказе X](evidence/shared-decision.json), [захват API](evidence/shared-api.pcap).

В этом стенде X и Y — два разных IPv4 одного контролируемого узла. Отдельные правила потерь дают два различимых источника измерений по IP, но физическая независимость удалённых серверов здесь не проверялась. Окно 2 с, интервал 200 мс, минимум 5 пар, преимущество 15 процентных пунктов и три последовательных подтверждения выбраны для короткой проверки. При первых внесённых потерях прошла 1,10 с до завершения всех клиентских проверок FI2. При обратном преимуществе до подтверждения всех клиентских путей FI1 прошло 1,16 с. В рабочей сети время зависит от окна, целей и частоты проб. [Конфигурация](evidence/measure.json), [время событий](evidence/events.log), [хеш проверенной сборки](evidence/controller.sha256).

Для повторения перенесите ARM64-бинарник и каталог `tests/lab/` на одноразовую Debian ARM64-ВМ, где установлены sing-box 1.14.4, TUN, iproute2, Python 3, iptables, curl и tcpdump. В госте запустите из корня проекта:

```sh
sudo bash tests/lab/group-quality/lab.sh ./hestia /var/tmp/group-quality
```

Для повторной независимой проверки сохранённых захватов выполните на Linux `python3 tests/lab/group-quality/check.py verify experiments/group-quality/evidence`. Стенд использует отдельные пространства сети клиента, шлюза и сервера. Маршрут по умолчанию шлюза направлен через RU, а пробы явно закреплены за FI1 и FI2.

## Повторный прогон 6 ноября 2026 года

На `hestia-dev` повторён опыт с текущим бинарником на базе `66bb2fa`, SHA-256 `a59e9ae9848f197273441699a1dcd645a3aa21d6dae61cebebacfa83e92cd208`. В приватной сети текущий Go `guard/balance` выполнил 38 раундов, 152 независимо прослеженные пробы и 30 новых потоков. Проверены переключения FI1→FI2 и FI2→FI1, сохранение RU и отсутствие переключения при полном отказе X через оба пути при исправном Y. Результат — exit 0, [журнал](../dev-validation/evidence/network/group-quality.txt). Команда из раздела воспроизведения выполнялась через [runner](../../tests/lab/dev-validation/network.sh) с приватными mount/net/PID и `/run`, ограничением 600 секунд. [Среда и общий протокол](../dev-validation/README.md). Это текущий Go-контроллер и локальный путь пакетов; автономная производственная политика исключения для одного UDP-назначения этим опытом не утверждается.
