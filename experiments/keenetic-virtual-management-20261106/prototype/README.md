# Ограниченный прототип lifecycle Keenetic-профиля

`profile-lifecycle-remote.sh` — удалённый POSIX shell-шаблон для одной обратимой проверки `up/down` только у уже существующих профилей `Solar (Moscow)` и `Poppuri`. Он не создаёт профиль, не читает конфигурацию, ключи и endpoint, не отправляет тестовые потоки и не сохраняет configuration. Результат отличает подтверждение административного состояния от соединения с peer.

Шаблон намеренно fail-closed: ID и тип профилей, а также парсер точных полей `show interface <id>` пока имеют маркеры `UNVERIFIED`/`TODO`, поэтому запуск сейчас отклоняется до удалённого вызова `ndmc`. После получения read-only inventory парсер сверяется с фактическим форматом, значения ID/type привязываются к двум точным разрешённым меткам, затем делаются исходный снимок файла и SHA-256. Исполнять разрешается только после согласования с root, проверки SSH host key, SHA-256 `/bin/ndmc`, маршрута управления в обход обоих профилей и подтверждения команды на текущем KN-1012.

Сценарий до первого изменения проверяет исходные admin/connection состояния и запускает bounded watchdog возврата исходного admin state. В том же remote-сеансе он меняет состояние только одного профиля, отдельно опрашивает admin и connected/disconnected с конечными тайм-аутами, затем восстанавливает исходное состояние и повторно проверяет его. При потере SSH watchdog возвращает admin state после 90 секунд; ручная очистка срабатывает по EXIT/HUP/INT/TERM. Повторный `up/down` в watchdog соответствует исходному состоянию. Никакое `system configuration save` не вызывается.

Device-side `interface <id> down/up` описан в официальных справочниках CLI Keenetic; в них `down` сохраняет административный state в настройках. Доступные материалы для другой модели/версии не подтверждают точную грамматику или поведение установленной KeeneticOS 5.2 Beta 3 на KN-1012, поэтому проверка по материалам остаётся только справочной. Одна попытка относится только к native Keenetic profile lifecycle и не доказывает Hestia runtime, создание профиля, новый peer, клиентский транзит либо fail-closed.

Запуск (только после закрытия всех ворот и фиксации снимка/хеша): передать проверенный файл по SSH с `StrictHostKeyChecking=yes` и выполнить `sh -s <label> <captured-admin-state> <captured-connection-state>`. Полная SSH-команда будет внесена в отчёт после подтверждения host-key path и передачи общего read-only inventory; сейчас её не запускают.
