## Conclusion and limits

The RCI-aware package is now installed and ready. The exact tuple was again visible at `br0` but not observed on `opkgtun0` or in sing-box. The source-to-Policy2 mapping and mark/table/RPDB/FIB configuration are now captured in the same trace as configured expectations. This still does not establish that the packet received `0xffffaac`, hit the Hestia RPDB rule, or was dropped. `not_observed` is not a drop verdict; the client timeout indicates no HTTPS response arrived, but not where or why.

In the traffic UI this trace is an `unconfirmed` summary, not a `blocked` sing-box event. Other visible UDP rows to different destinations are not attributable to this TCP tuple. The trace itself persists successfully. The next packet-level step remains no-mutation discovery of a target-supported NDM counter/event or proven post-classification hook. Do not add Netfilter/NFLOG rules, load modules, or change policy/routes under this diagnostic scope.

## Reproduction commands

Router:

```sh
printf '%s' '{"protocol":"TCP","source":"192.168.1.124","sourcePort":49333,"destination":"1.1.1.1","destinationPort":443,"durationSeconds":15}' | /opt/bin/hestia -traffic-trace
```

Client, synchronized through the existing `lima-hestia-client` SSH alias:

```sh
CLIENT_LIMA_HOME=/private/tmp/hestia-vm-run/lima-state
CLIENT_SSH_CONFIG="$CLIENT_LIMA_HOME/hestia-client/ssh.config"
ssh -F "$CLIENT_SSH_CONFIG" lima-hestia-client \
  'sudo -n timeout 15 tcpdump -nn -l -i lima0 "(src host 192.168.1.124 and src port 49333 and dst host 1.1.1.1 and dst port 443) or (src host 1.1.1.1 and src port 443 and dst host 192.168.1.124 and dst port 49333)" > /tmp/hestia-client-trace-49333.log 2>&1 & capture_pid=$!; sleep 5; curl -4 --interface 192.168.1.124 --local-port 49333 --connect-timeout 3 --max-time 5 --resolve one.one.one.one:443:1.1.1.1 -sS -o /dev/null https://one.one.one.one/cdn-cgi/trace; curl_status=$?; wait "$capture_pid" || true; cat /tmp/hestia-client-trace-49333.log; echo curl_exit=$curl_status'
```
