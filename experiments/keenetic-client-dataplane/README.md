# TUN-вход Hestia через OpkgTun на Keenetic

## Вопрос

Может ли KN-1012 с KeeneticOS 5.2 Beta 3 представить вход Hestia как NDM-интерфейс `OpkgTun0`, открыть его закреплённым sing-box 1.14.4 через `/dev/net/tun`, и добавить этот интерфейс в политику так, чтобы клиентская маршрутизация оставалась выборочной и fail-closed?

В этом первом proof проверены создание, подключение и очистка. Клиентская policy `hestia-client` и пользовательский трафик не затрагивались.

## Среда и версия

- Устройство: Keenetic Giga KN-1012, KeeneticOS `5.02.B.3.0-2` (5.2 Beta 3), kernel `4.9-ndm-5`, `aarch64`.
- Установленный Hestia пакет: `20261108-133906-46ed33ac8d30`; использован его sing-box 1.14.4 через Entware loader.
- Тестовый интерфейс: `OpkgTun0` / Linux `opkgtun0`; NDM адрес `172.31.250.1/32`, адрес sing-box `172.31.250.2/30`, MTU 1500. Подсеть предварительно не была занята.
- Временная конфигурация содержала только TUN inbound, `auto_route: false` и `block` outbound. Конфиг и NDM объект создавались на время опыта; `system configuration save` не вызывался.
- Временная policy `HestiaProof20261108` не содержала назначенных устройств. Политика `hestia-client`, список клиентов и VPN-выходы не менялись; клиентский трафик не генерировался.

## Ожидаемый и фактический результат

Ожидалось, что NDM сможет создать и поднять интерфейс без изменения main default route, sing-box сможет открыть его по Linux-имени, а временные объекты можно будет удалить.

Результаты ограниченной пробы:

- NDM принял создание `OpkgTun0`, адрес `/32`, MTU 1500, `security-level public` и `up`. Не включались `ip global auto`, `ip route default` или `system configuration save`.
- sing-box 1.14.4 запустился с `interface_name: opkgtun0`, назначил адрес из своей конфигурации и поднял линк. Main default route оставался на исходном интерфейсе; IPv4 rules до и после совпали.
- После штатного завершения адрес sing-box удалялся, NDM адрес `/32` сохранялся. После `SIGKILL` адрес sing-box оставался на интерфейсе. Следующий sing-box процесс успешно повторно открыл тот же интерфейс после штатного stop и после аварийного завершения.
- В отдельной временной policy после разрешения `OpkgTun0` RCI выделил таблицу `4103`, но в ней было `0` default routes. Это прямой результат на KN-1012/5.2 Beta 3.
- `/opt/sbin/ip` на устройстве — BusyBox 1.37. Его команда `ip route add ... table 4103` отклонила `4103` как недопустимый аргумент. Установка тестового маршрута не состоялась; поэтому поведение route lookup и fail-closed в этом опыте не проверялось.
- Статический ARM64 netlink probe повторил опыт с table ID и mark, прочитанными из RCI. Для временной policy это были table `4104`, mark `ffffab0`, default route count `0`. Netlink добавил `unreachable default metric 32767` и `default dev opkgtun0 metric 1000` именно в table 4104; BusyBox `ip route show table all` подтвердил обе записи. Обе записи затем удалены. Это доказывает возможность добавить/удалить маршруты в таблице выше 255 без изменения `main`.
- Первый вариант RTM_GETROUTE probe не ставил `RTM_F_LOOKUP_TABLE`; ядро Linux 4.9 по умолчанию заполняет поле таблицы значением `main`. Затем probe был дополнен клиентским source `192.168.1.124` и ingress `br0`; read-only lookup с mark `ffffaad` вернул `table_id=254 device=nwg3`, хотя снимок таблицы 4102 показывал `default dev br0`. Прицельный RTM_GETRULE dump показал `lookup main` на приоритете 9 без suppress-prefix, а lookup `4102` для того же mark — только на приоритете 100; следующий fallback blackhole стоит на 101. Поэтому наблюдаемый маршрут согласуется с последовательным выбором `main` раньше policy mark rule. Пока не выяснено, почему Keenetic строит/использует эту последовательность и какой механизм NDM ожидает для выбора policy; адаптер, который только добавляет маршрут в таблицу, недостаточен. Fail-closed и применимость policy table не подтверждены. Свидетельство: [исходник RPDB Linux 4.9](https://github.com/torvalds/linux/blob/v4.9/net/core/fib_rules.c#L191-L234) и [route lookup Linux 4.9](https://github.com/torvalds/linux/blob/v4.9/net/ipv4/route.c#L2422-L2471).
- В последующем read-only снимке table `4104` и mark `ffffab0` снова присутствовали в активном RPDB; table содержала два destination-specific маршрута через `eth3`. Имя прежней тестовой policy `HestiaProof20261108` отсутствовало в `show ip policy`. Владение текущими объектами не установлено, поэтому старые table/mark нельзя повторно использовать; никаких изменений для этой проверки не выполнялось.
- Одна проба удалила NDM объект до остановки временного sing-box и оставила `opkgtun0` без carrier. Это было установлено как собственный остаточный тестовый интерфейс: NDM конфигурация, тестовый процесс и policy отсутствовали, на интерфейсе оставался только тестовый адрес. После закрытия процесса интерфейс удалён отдельным RTM_DELLINK по имени `opkgtun0`; финальная read-only проверка подтвердила его отсутствие. Маршруты были удалены до этого cleanup.
- Тестовая policy и `OpkgTun0` удалены. Повторная read-only проверка подтвердила отсутствие интерфейса и исходный системный default route. Никакая конфигурация не сохранялась.
- Для подготовки typed RCI reader выполнены только GET `/rci/ip/policy` и GET `/rci/show/ip/policy`. В первом ответе на этой сборке наблюдались объекты `PolicyN` с `permit[]` (`interface`, `enabled`) и статическим `route[]`; во втором — `table4`, `table6`, `mark`, `route4.route[]` и `route6.route6[]`. Сырые ответы и описания политик не сохранялись. Это подтверждает форму динамического сопоставления policy → mark/table, но не поведение UI и не выбор подключения в таблице.

Сводный обезличенный журнал: [evidence](evidence/ndm-singbox-handoff-20261108.txt).

## Границы вывода

Опыт подтверждает NDM/sing-box handoff, ограниченный lifecycle, отсутствие автоматического default route в отдельной policy без клиентов, возможность netlink-операций add/delete в динамической Keenetic policy table выше 255 и текущую форму read-only RCI policy/runtime responses. Текущие правила показывают `lookup main` на приоритете 9 без подавления default, а mark rule к table 4102 — на приоритете 100; исправленный input-route probe вернул main/nwg3. Поэтому Hestia должна доказанно перехватывать только marked ingress до `main`; использование NDM policy table напрямую может пропускать более специфические не-Hestia маршруты и не гарантирует fail-closed. Не подтверждены поведение интерфейса в UI, доставка пакетов Keenetic policy в TUN, возвратный путь, TCP/UDP forwarding, VPN-egress, fail-closed, DNS, IPv6, reboot recovery или сохранение подключения при обновлении пакета. После штатного stop и SIGKILL нужно сохранять порядок: сначала остановить sing-box, затем удалять NDM объект; обратный порядок оставляет интерфейс без владельца до отдельной очистки.

На KeeneticOS 5.0.7 также опубликован отчёт о пустой policy table для OpkgTun и необходимости добавить маршрут вручную. Наш прогон подтвердил отсутствие маршрута и на KN-1012/5.2 Beta 3. [Обсуждение Keenetic](https://forum.keenetic.ru/topic/27959-%D0%B0%D0%B2%D1%82%D0%BE%D0%BC%D0%B0%D1%82%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%B8%D0%B9-default-route-%D0%B4%D0%BB%D1%8F-opkgtun0-%D0%B2-%D0%BF%D0%BE%D0%BB%D0%B8%D1%82%D0%B8%D0%BA%D0%B0%D1%85-%D0%B4%D0%BE%D1%81%D1%82%D1%83%D0%BF%D0%B0/).

## Воспроизведение

Подключиться к роутеру через закреплённый SSH host key. Проверить отсутствие `OpkgTun0` и выбранной тестовой подсети, затем снять main default route и IPv4 rules. Создать NDM интерфейс без default route и без сохранения конфигурации; запустить закреплённый sing-box с TUN inbound, `auto_route: false` и `block` outbound. Повторить запуск после штатного завершения и после `SIGKILL`.

Для проверки политики создать временную policy без устройств, разрешить ей `OpkgTun0`, затем запросить `/rci/show/ip/policy` и зафиксировать только её table ID и число default routes. Попытка изменить только эту тестовую таблицу через установленный `/opt/sbin/ip` завершилась отказом BusyBox на ID 4103. Удалить временную policy и интерфейс. Не направлять клиентский трафик в ходе этого proof.

## Dynamic TUN без NDM object — 8 ноября 2026 года

Вопрос: становится ли sing-box-created TUN интерфейсом NDM, который можно выбрать в Keenetic policy? На KN-1012 временный sing-box 1.14.4 создал `opkgtun0` с адресом `172.31.250.2/30`, MTU 1500 и `auto_route=false`; outbound был только `block`. Имя отсутствовало в `ndmc show interface`, а `ndmc show interface opkgtun0` завершилась ошибкой парсера. Main default остался через `eth3`; правила маршрутизации совпали по хешу. После SIGTERM интерфейс и его маршруты исчезли, полные хеши IPv4/IPv6 routes и rules вернулись к исходным значениям. Клиентские policy и пакеты не затрагивались. Значит, одного dynamic Linux TUN недостаточно, чтобы показать интерфейс в NDM policy: используем созданный NDM `OpkgTun0` и подключаем к нему sing-box. UI и выбор в policy в этом опыте отдельно не проверялись. Бинарник запускался через `/opt/lib/ld-linux-aarch64.so.1 --library-path /opt/lib`, поскольку rootfs не содержит ожидаемый бинарником путь glibc loader `/lib/ld-linux-aarch64.so.1`. [Свидетельство](evidence/dynamic-tun-ndm-visibility-20261108.txt).

## Локальная реализация и review — 8 ноября 2026 года

Вопрос: достаточно ли локальной реализации для первой загрузки Keenetic IPK? Среда: macOS ARM64 разработчика, ветка `codex/keenetic-opkgtun-ingress`, исходный revision `e523f5481e66` плюс dirty source changes. Во время этой локальной проверки роутер и виртуальные машины не использовались. Ожидалось получить воспроизводимую сборку и проверить маршрутные переходы на host-модели; target netlink/syscalls и supervisor runtime должны были остаться явно непроверенными.

Результат: pure parser package marker вынесен в платформенно-независимый helper и покрыт поведенческими случаями для канонического формата, extra lines/tails, NUL, delimiter, signed/leading-zero numbers и границ PID/start-time/size. Code/security review этих изменений закрыт. Проверки `GOPROXY=off go -C backend test ./internal/services/entware`, Keenetic-tagged route/Entware/RCI tests, shell `sh`/`dash` syntax, `SHFMT=/tmp/hestia-shfmt make docs-check`, `make test-installer`, `make test-workflows`, 14 tests `python3 -B -m unittest test_build` и полная `make build` прошли. Последний Keenetic артефакт: `dist/artifacts/20261108-183030-e523f5481e66/keenetic-arm64-experimental`; manifest `dirty=true`, 601 source hashes, и source hashes для всех новых ingress/helper files и NDM hook совпали с текущими файлами. В IPK data archive присутствуют init script и `netfilter.d` hook. Build provenance allowlist дополнен неотслеживаемыми до коммита файлами реализации и parser tests. Полный `make check` остановился из-за отсутствующего `shellcheck`. Полный `make test` не прошёл несколько тестов, которым запрещён bind TCP/UDP loopback в sandbox (`operation not permitted`); `make test-lab` не прошёл тесты DNS из-за отсутствующего `dnspython`, при этом остальные lab modules прошли. Независимый review ранее выявил steady-state route churn и readiness обход через root IPC; оба локальных дефекта исправлены и покрыты route tests. Добавлен IPv4 `mangle` NDM hook с общим root-only `flock`: он синхронно вызывает supervisor reconcile (IPC deadline 16 секунд, CLI timeout 18 секунд), а если supervisor недоступен — напрямую запрашивает guard-only reconcile из RCI. При `opkg` maintenance S99 сначала останавливает supervisor и ждёт освобождения того же lock. Маркер содержит boot ID, PID `opkg`/`opkg-cl`, найденный обходом родительской цепочки `prerm`, и process start-time ticks; hook и Go reader проверяют канонический формат, точные file metadata (`0600`, root-owned regular file, одна hard link, до 128 байт) и активную process identity. NDM документация описывает 24-секундный предел hook queue. Такая схема может поставить blocking routes до запуска Hestia только если hook срабатывает после доступности `/opt`/RCI и до forwarding; target ordering при boot/policy change ещё не измерялся. Открыты fail-closed границы при ошибке RCI и одновременно неудачных guard mechanisms, а также смене policy без подтверждённого NDM barrier. Управление NDM `OpkgTun` lifecycle не реализовано. Поэтому клиентский dataplane не проверен; следующий практический шаг — ограниченная целевая проверка без привязанных устройств в тестовой policy.

## Реальная Linux проверка route-netlink — 8 ноября 2026 года

В ARM64 Linux namespace на `hestia-dev` запущен весь `keeneticroute` test binary с opt-in интеграционным тестом и настоящим kernel route netlink. Подтверждены add/read/delete для маршрутов таблицы 30001, IPv4 lookup/terminal rules, IPv6 block rule и неизменность main table; временные dummy links удалены до выхода из namespace. После прогона отдельная read-only проверка VM подтвердила исходные links/routes/rules без Hestia артефактов. По ходу выявлены и исправлены parser несовместимости Linux 6.1: kernel опускает `FRA_PRIORITY` для priority 0, возвращает нейтральный `FRA_SUPPRESS_PREFIXLEN=UINT32_MAX` и добавляет `FRA_PROTOCOL` metadata. Последний прогон прошёл. Свидетельство и команды: [Linux netlink integration test](evidence/linux-netlink-hestia-dev-20261108.txt). Это не подтверждает Keenetic kernel 4.9/NDM, policy delivery или packet dataplane.

## Проверка RPDB ownership marker на KN-1012 — 8 ноября 2026 года

Одноразовый ARM64 netlink probe отправил правило с `FRA_PROTOCOL=253`, уникальными priority/mark/table и несуществующим input interface `hestia-probe`. KN-1012 ответил ACK на add и exact delete, но upstream Linux 4.9 не определяет `FRA_PROTOCOL`; неизвестный атрибут нельзя считать сохранённой меткой владения. Правило удалено, исходные хеши IPv4/IPv6 routes и rules совпали с baseline, probe и его каталог удалены. До загрузки IPK нужно добавить persistent ownership proof для RPDB rules либо подтвердить иной уникальный selector, который target kernel сохраняет. Исходник воспроизведения — [fra-protocol-probe.go](prototype/fra-protocol-probe.go); собрать ARM64 бинарник: `GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -o /tmp/fra-protocol-probe experiments/keenetic-client-dataplane/prototype/fra-protocol-probe.go`. [Свидетельство](evidence/rpdb-protocol-marker-20261108.txt).

## Persistent ownership registry: rule-only проверка на KN-1012 — 8 ноября 2026 года

Вместо неподдерживаемого kernel marker реализован приватный persistent registry точных RPDB identities. Kernel rule считается принадлежащим Hestia только если identity есть в registry; запись создаётся после netlink ACK, а перед удалением убирается из registry, чтобы ошибка kernel delete не позволила позже присвоить чужое правило. На KN-1012 отдельный ARM64 тест добавил селектор `priority 7`, `fwmark 0x0ffffffe/0xffffffff`, `iif lo`, `lookup 34094`, проверил `Owned=true`, удалил его штатным `DeleteRule` и подтвердил пустой registry. Таблица перед пробой была пуста; selector не совпадал с LAN ingress `br0`; клиентская policy и пользовательские пакеты не затрагивались. Снимки IPv4/IPv6 routes и rules после теста совпали с исходными baseline hashes. [Свидетельство](evidence/target-rpdb-ownership-20261108.txt).

Полная `IngressPolicy.InstallGuard`/`Remove` проверка на KN-1012 пока не выполнена. В текущем сеансе read-only SSH preflight к `root@192.168.1.1` завершился `Permission denied (password)`, поэтому новый target test не загружался и не запускался. Повторять без доступного авторизованного канала нельзя. После восстановления доступа сначала сверить модель/версию и все маршруты/правила, затем выполнить отдельную guard-only пробу с существующим `br0`, проверить возврат снимков и лишь после этого оценивать готовность пакета.

Пределы вывода: это не подтверждает работу supervisor или Linux netlink на Linux runtime, правильный порядок RPDB на KN-1012, dataplane, возвратный путь, AWG egress, TCP/UDP forwarding или отсутствие утечки через WAN. Проверки воспроизводятся командами из корня `GOPROXY=off go -C backend test -tags keenetic ./internal/network/keeneticroute ./internal/services/entware ./pkg/keeneticrci` и `make build`.

## Подготовленный целевой опыт: динамический OpkgTun

**Статус:** не выполнялся; требуется отдельное разрешение владельца на доступ и временное изменение KN-1012. Предыдущий proof проверял заранее созданный временный NDM объект, но не динамический вариант.

Вопрос: создаст ли закреплённый sing-box TUN inbound интерфейс `opkgtunN`, который Keenetic покажет как `OpkgTunN`, без NDM-конфигурации? Проверить только на свободном имени, выбранном по свежей read-only инвентаризации. Снять исходные RCI interface/policy и Linux link/address/route/rule snapshots. Запустить отдельный sing-box процесс с одним TUN inbound, `interface_name=opkgtunN`, `auto_route=false`, уникальным тестовым адресом и единственным `block` outbound. Не менять NDM policy, не назначать клиентов, не добавлять системный default route, не задавать `ip global auto` и не вызывать `system configuration save`; внешние пакеты не отправлять.

Во время процесса проверить появление имени в Linux и Keenetic RCI/UI, наличие интерфейса среди разрешённых policy connections и отсутствие изменений `main` default route. Затем остановить процесс штатно, повторить динамический тест с `SIGKILL` только после подтверждения, что имя всё ещё свободно, и сравнить состояние. Удалять только артефакты, однозначно созданные этим тестовым процессом; при неизвестном владельце любого остатка остановиться и сохранить снимок для разбора. Успех — NDM распознаёт динамический интерфейс без сохранённой конфигурации, основной маршрут не меняется, а остановка/аварийный останов дают воспроизводимое и безопасное состояние. Отдельный тест выбранной policy при отсутствующем TUN остаётся no-client фазой и требует собственного снимка/rollback.

## Исходный снимок тестового клиента — 8 ноября 2026 года

Проверены адреса и kernel routes ВМ `hestia-client` через read-only `limactl shell`; команды не отправляли сетевых проб и не подключались к Keenetic. У ВМ два IPv4 default route: предпочтительный `192.168.1.1` через `lima0` (`192.168.1.124`, metric 100) и дополнительный `192.168.5.2` через `eth0` (`192.168.5.15`, metric 200). Затем просмотр конфигурации Lima подтвердил, что `eth0` — provisioned Lima NIC по MAC mapping в `cloud-config.yaml`, а `lima0` — явно настроенный bridged NIC на `en0`. Точный host-side forwarding path для DHCP gateway `192.168.5.2` не исследован. Для leak-test надо учитывать оба выхода и отдельно показать, что контрольный клиентский поток не ушёл через Lima NIC. Свидетельства: [baseline routes клиента](evidence/hestia-client-baseline-20261108.txt), [Lima network configuration](evidence/hestia-client-lima-network-config-20261108.txt).

## Установка standalone `keen-mvp` и видимость OpkgTun — 8 ноября 2026 года

Отдельный Entware IPK `keen-mvp` версии `0.1.0-2` установлен на KN-1012. `postinst` создаёт принадлежащий пакету NDM `OpkgTun0`, назначает `ip global auto`, а Go-процесс открывает Linux `/dev/net/tun` как `opkgtun0` и оставляет сервис запущенным. После исправления `global: no` на `global: yes` NDM показывает `defaultgw: no`, Linux link присутствует, а хеш основного IPv4 default route совпадает с исходным. Keenetic сообщил о пересчёте global priority. Установка выполнялась без сохранения конфигурации, без policy и без назначенных клиентов. Копия IPK удалена из `/opt/tmp`; пакет оставлен установленным. Визуальное появление в WebUI ещё проверяет владелец. [Свидетельство, hashes пакетов, команды и границы](evidence/keen-mvp-install-20261108.txt).

Product Owner подтвердил WebUI отображение по адресу `http://192.168.1.1/otherConnections`: карточка `Keen-MVP`, тип `OpkgTun`, подпись «Резервное соединение». Это подтверждает видимость интерфейса в UI; выбор подключения в policy отдельно не проверялся. Программа не читает пакеты из TUN, не создаёт policy route/guard и не доказывает fail-closed.

8 ноября Product Owner создал policy `Hestia MVP 2`, разрешил `Keen-MVP` и временно добавил `hestia-client`, затем вернул клиента к прежней policy до установки Hestia guard. Read-only runtime показывает `Policy3`, table `4103`, mark `ffffaaf` и destination routes через `Wireguard1`; default route через `OpkgTun0` не найден. Это не подтверждает полного permit list, отсутствия fallback или поведения client lookup. Клиентские потоки не отправлялись.

Для следующего handoff локально подготовлено явное правило OpkgTun inbound → единственная группа только из готовых AmneziaWG-коннекторов; её `defaultExit` может быть `deny` или одним из этих AWG-коннекторов. `keen-mvp 0.1.0-3` больше не открывает TUN FD; sing-box должен стать единственным FD owner. Транзакционное действие `/opt/bin/hestia -enable-keenetic-ingress` добавлено в Keenetic CLI. Обе локальные профильные проверки, Go build checks и полная сборка Keenetic IPK прошли; новый IPK ещё не устанавливался. ## Установка Hestia OpkgTun на KN-1012 — 9 ноября 2026 года

Keenetic IPK `20261109-094953-e523f5481e66` установлен на KN-1012. Перед установкой read-only RCI подтвердил, что 4 policy не разрешают `OpkgTun0` и не содержат статических маршрутов через него; сохранённый Hestia профиль не использует его как VPN underlay. Для исключения двойного владельца удалён `keen-mvp 0.1.0-3`. Первая `opkg install` распаковала новый пакет, но postinst не дождался supervisor readiness и оставил Hestia в `unpacked`; в журнале во время старта были отказы проверки `managed Hestia process remains active` и отменённые операции. После завершения транзакции повторная `/opt/bin/opkg configure hestia` прошла успешно. Финальная проверка: package `install user installed`, supervisor ready, managed profile valid, OpkgTun `global yes`/`defaultgw no`, IPv4 default route hash unchanged, LAN API и `/api/awg-underlays` отвечают HTTP 200; API содержит `keenetic-opkgtun`. [Подробные условия, команды, причина и границы](evidence/install-hestia-opkgtun-20261109.txt).

Обновление не меняло Keenetic policies и назначения клиентов; ни одна policy не разрешает OpkgTun. Внешние запросы и клиентский TCP/UDP путь не испытывались, поэтому эта установка подтверждает пакет, supervisor, NDM ownership, API и VPN-underlay candidate, но не клиентский dataplane или fail-closed.
