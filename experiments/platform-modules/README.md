# Проверка выделения платформенных модулей

Вопрос: сохраняет ли разделение системных операций, хранения и сети действующее поведение Linux? Контракт — [модули платформы](../../docs/features/platform-modules.md), последовательность — [дорожная карта Keenetic](../../docs/keenetic-roadmap.md).

## Среда и исходный прогон

6 ноября 2026 года. Исходная версия `37eaf06`, Go 1.27.3. Тесты собраны с `CGO_ENABLED=0 GOOS=linux GOARCH=arm64` на macOS ARM64 из отдельного `git archive` и выполнены на проектной ВМ `hestia-binding-test` (Debian ARM64, Lima VZ, 2 CPU, 2 ГБ памяти). У ВМ отсутствуют монтирования host-каталогов и bridge в домашнюю сеть. Личная ВМ и роутер не использовались.

Ожидание: исходные тесты проходят, включая Linux-специфичный код. Факт: все собранные тестовые пакеты завершились успешно, суммарный exit 0. [Свидетельство](evidence/linux-baseline.txt). Каждый бинарник запускался из соответствующего каталога исходников с `-test.count=1 -test.timeout=3m`, от непривилегированного пользователя. Это регрессионные тесты с локальными fixtures и подменами; они не доказывают реальный перехват трафика или работоспособность на Keenetic.

Воспроизведение: извлечь нужную ревизию `git archive`, выполнить в `backend` команду `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go test -c -o <каталог-бинарников>/ ./internal/... ./cmd/... ./tools/...`, скопировать исходники и бинарники на явно выбранную изолированную Linux ARM64-ВМ. Запускать каждый `<имя-пакета>.test` из каталога этого пакета. Пакеты без тестов фиксируются отдельно сборкой.

## Повторный прогон

Повторный прогон 6 ноября 2026 года завершился успешно: 22 пакета тестов Linux ARM64, exit 0. Проверен снимок backend `de42711cabaea22a0c53f7d1523ea688032615c28841b7d0171a51448747afa9` (SHA-256 отсортированных существующих файлов backend: путь, NUL, содержимое, NUL). [Результаты и пропуски](evidence/linux-final.txt). Снимок относится к изменениям поверх `37eaf06`; код после этого прогона не менялся.

Отдельно выполнены на исходных и новых бинарниках реальные loopback-проверки SOCKS TCP/UDP через sing-box 1.14.4, журнала sing-box и raw ICMP IPv4/IPv6. Все прошли, [свидетельство](evidence/linux-optional.txt). Для ICMP и привязки сокетов тест quality запускался через `sudo -n`; назначения ограничены loopback. Команды: `HESTIA_QUALITY_TEST_SING_BOX=/usr/local/lib/hestia/sing-box <quality.test> -test.v -test.run='Test(RawEchoLoopback|RealSingBoxLoopback)$' -test.count=1` и `HESTIA_TEST_SING_BOX=/usr/local/lib/hestia/sing-box <trafficcapture.test> -test.v -test.run=TestLocalSingBoxJournal -test.count=1`.

На Mac прошли `make fmt`, `make check`, `make build`, `make generate-api` без изменения генерируемых файлов, frontend format/lint, 23 unit-теста, production-сборка, 18 браузерных тестов и DNS panel/worker Playwright. Первый sandbox-прогон не смог открыть локальные TCP/UDP fixtures; повторный полный прогон с доступом к loopback прошёл. Независимый тестировщик повторил 16 пакетов адаптеров и потребителей с `-count=1`, exit 0. Ревью кода и безопасности не выявили блокирующих замечаний.

Не выполнен только необязательный тест разбора keyfile настоящим `nmcli`: утилиты нет в выбранной ВМ. Тесты Linux NetworkManager-адаптера с fixtures проходят. Browser-тесты, пропущенные обычным Linux-прогоном, выполнены отдельно на Mac. Проверка настоящих Ethernet/Wi-Fi, TUN, маршрутизации клиентского трафика и systemd не подменяется этими результатами и остаётся предметом интеграционных испытаний. Keenetic не проверялся. Изменения не мигрируют данные; откат выполняется отменой коммита.
