# Разрешение для нового потока после истечения TTL

Стенд проверяет, что клиент с прежним FakeIP может открыть новый поток к домену после изменения реального адреса. Для опыта положительный резолвер обслуживает два входа одной процедурой выбора победителя. Вход клиентского DNS возвращает FakeIP, а внутренний запрос sing-box на `127.0.0.1:1055` получает реальную A-запись.

До истечения срока входы используют выбранный адрес и TTL с вычетом прошедшего времени. После истечения любой из входов запускает новую волну запросов через разрешённые выходы. Проверка доступности FI выполняется и перед выдачей результата. При запрете единственной явно назначенной группы шлюз возвращает SERVFAIL. Реальное разрешение для нового потока не выдаёт новый FakeIP и не создаёт клиентского посещения.

Для одного канонического имени и одного набора разрешённых групп одновременные запросы ждут одной волны. Первый пригодный положительный ответ формирует новый выбор. Остальные завершаются в фоне, их источник, адрес и TTL записываются в журнал. Запоздавший кандидат не меняет уже возвращённый выбор. Отдельно переиспользовать непобедившие ответы в этом эксперименте не требуется. TTL 0 разрешает выдать ответ текущего запроса, но следующий запрос потребует разрешения снова.

Оба конца работают только с IN/A, одним прямым IPv4-адресом и контролируемыми именами. Число имён стенда конечно. Кэш хранится в памяти, без лимита по количеству имён и без периодической очистки, поэтому запуск на произвольном клиентском трафике выходит за пределы опыта. Здесь не проверяются CNAME, несколько адресов, AAAA, DNSSEC, резервная выдача истёкших записей или прогрев. Для старых уже открытых соединений опыт не определяет поведение.

В изолированной среде с dnspython выполните `python3 -B -m unittest discover -s experiments/dns-rotation -p test_cache.py`. Регрессии охватывают точную границу TTL, совместное обновление двух клиентов, ответ старой волны после нового победителя и запрет явно назначенной группы во время запроса.

Перед отправкой каждого внешнего запроса обработчик повторно проверяет допустимость соответствующего выхода. При изменении состояния после отправки он также проверяет группу перед выдачей ответа. DNS-клиент сверяет источник датаграммы с адресом и портом ожидаемого резолвера и проверяет соответствие ответа исходному запросу при обычном запуске и при `python -O`.
