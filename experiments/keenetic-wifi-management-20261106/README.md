# Управление Wi-Fi и WISP на Keenetic

## Вопрос и статус

Какие операции управления WISP доступны на KN-1012 с KeeneticOS 5.2 Beta 3 и как его работа влияет на локальную Wi-Fi-точку доступа в том же диапазоне?

На 6 ноября 2026 года завершён локальный аудит. Аппаратный тест не выполнялся. Владелец предложил использовать уже сохранённый в Keenetic профиль телефонной точки доступа; пароль не запрашивать и повторно вводить не требуется. Владелец уточнил: ожидаемая SSID — `White paper`, описание сохранённого профиля — `iPhone`. Сохранять только две булевы проверки точного совпадения, не сами строки из устройства. Локальные SSID и их настройки не менять.

## Этап 1 — ограниченное чтение

1. Сверить SSH host key и SHA-256 `/bin/ndmc` с [предыдущим отчётом](../keenetic-rci-readonly/README.md); при несовпадении остановиться.
2. Использовать общую потоковую инвентаризацию `show interface`, которую выполняет агент Ethernet. Вывести только Wi-Fi station/WISP: interface ID/type, `connected`/`state`/`link` и два булевых результата совпадения SSID с `iPhone` и `White Paper`. ID можно оставить для точечного адресного запроса. SSID, секреты, IP/MAC, описания, другие интерфейсы и сырой вывод не сохранять и не показывать.
3. Если сохранённый профиль не виден или безопасно сопоставить его невозможно, записать «не наблюдается» и остановиться. Не выполнять `show ru`/`show running-config` и не подбирать альтернативные команды.
4. [Справочник CLI Keenetic](https://help.keenetic.com/hc/article_attachments/360026456159/cli_manual_kng_re.pdf) описывает `show site-survey <name>` как отображение доступных сетей без изменения настроек и приводит `WifiMaster0`/`WifiMaster1` как радиоинтерфейсы. План команд: `/bin/ndmc -c 'show site-survey WifiMaster0'` (2,4 GHz), затем `/bin/ndmc -c 'show site-survey WifiMaster1'` (5 GHz). Команда выполняет радиосканирование; документация не гарантирует отсутствие краткого влияния на передачу.
5. До скана подтвердить маршрут ответа SSH и убедиться, что управление не пойдёт через переключаемый VPN. Если управление остаётся на Wi-Fi, заранее учесть риск его краткого прерывания; выполнять только ограниченную команду и не запускать следующую полосу после ошибки/тайм-аута/потери статуса. Перед/после каждой полосы читать только состояния соответствующего `WifiMaster`, AP и station. Сканировать последовательно, без параллельной активации VPN/WISP.
6. Парсер в памяти сохраняет по каждой полосе число распознанных строк, булево точное совпадение SSID `White paper` и только канал/качество совпавшей сети. SSID, BSSID/MAC, каналы и имена прочих сетей не сохранять. Неудачные/неоднозначные строки дают parse status unknown, а не «сеть не найдена». Если вывод не содержит отметки времени, пометить свежесть как неподтверждённую и не называть результат свежим активным сканированием.

## Этап 2 — существующий профиль, после координации архитектора

Сохранённая WISP-станция уже была подключена до этого исследования, поэтому переключение `down/up` не было нужно для сканирования и не выполнялось. Общая CLI-документация описывает `interface {name} no up` и `interface {name} up`; имя целевого 5GHz station теперь подтверждено. Возможность этих команд отключить/включить именно сохранённый профиль на установленной сборке пока не испытывалась. WISP уже показывает `defaultgw=false`, wired WAN — `defaultgw=true`, но это только исходный снимок.

Проверку цикла состояния можно планировать только после подготовки независимого wired управления самим роутером. На предыдущем снимке управляющий Mac маршрутизировал соединение по Wi-Fi (`wired_management=false`). Владелец затем подключил этот Mac кабелем к LAN port 1. Повторный фильтрованный локальный route check после этого кабеля завершился `unknown` в песочнице, а запрос повышенного доступа не был запущен из-за тайм-аута автоматической проверки. Поэтому наличие кабеля пока не подтверждает wired management route. Наличие проводного WAN `GigabitEthernet1` само по себе не защищает локальную SSH/UI-сессию при помехе радиомодулю. До проверки маршрута root не следует переключать станцию.

Минимальный план после получения независимого проводного пути:

1. Убедиться, что сохранённая телефонная точка доступа `White paper` включена и управление доступно по проводу. Повторно подтвердить target ID и исходные состояния station/default gateway.
2. Выполнить только для существующего `WifiMaster1/WifiStation0`: `ndmc -c 'interface WifiMaster1/WifiStation0 no up'`; проверить точечный `show interface` и wired WAN `defaultgw`.
3. Восстановить сразу же `ndmc -c 'interface WifiMaster1/WifiStation0 up'`; повторно проверить station `connected/link/state`, булевы match values, `defaultgw` и `priority`, а также wired WAN. Не менять SSID/ключи/локальную AP, порядок WAN или другие настройки.
4. Если отключение профиля теряет управление, использовать независимый проводной путь для восстановления `up`; не выполнять тест без такого пути. Не сохранять конфигурацию целиком и не перезагружать устройство.

Сейчас этот цикл не является готовым к выполнению: маршрут управления после подключения кабеля неизвестен, хотя текущий routed default gateway — проводной WAN. Результат и границы последнего локального запроса находятся в [обезличенном evidence](evidence/attempt-20261106T203724Z-local-management-route.json); истёкшая проверка доступа без запуска команды — в [отдельной записи](evidence/attempt-20261106T203600Z-local-route-escalation-review.json). Сканирование разрешалось отдельно и завершено выше.

После координации допустимый ограниченный прогон использует только существующий профиль, совпавший с разрешённой SSID и описанием профиля:

1. Зафиксировать исходное состояние целевого профиля и интерфейс ID. Для текущего WAN и WISP сохранить только `defaultgw` (булево) и `priority` из точечного `show interface {name}`, а также работающий проводной путь управления. Безопасного способа гарантировать неизменный default route одним включением WISP пока не подтверждено.
2. Не создавать/редактировать профиль, не вводить новый пароль, не менять локальную AP, каналы, WAN-приоритет или прочие подключения. Если владелец уже подтвердил достаточный приоритет текущего WAN и архитектор разрешил ограниченную пробу — включить только целевой профиль через документированное `interface {id}` / `up`.
3. Повторно прочитать только точечные статусы и булево `defaultgw`/`priority` текущего WAN и WISP. Если WISP стал предпочтительным default route, сразу выключить только его (`interface {id}` / `no up`), проверить возврат исходного default route и прекратить прогон.
4. Только если default route не изменился, выполнить ограниченную контрольную пробу через WISP и телефонную точку доступа; одного статуса подключения недостаточно.
5. Наблюдать локальную AP и тестовый клиент до/во время/после: доступность, краткие разрывы, канал/полоса. Ожидаемое влияние ограничено диапазоном, общим с WISP; зафиксировать фактическое, не экстраполировать на другой диапазон.
6. Восстановить исходное состояние профиля: если он был выключен, снова выключить; если уже был включён — не менять. Проверить статус, прежний `defaultgw`/`priority` и проводной доступ. Не менять настройки локальной AP.

### Критерии

- Целевой сохранённый профиль сопоставлен без записи его имени/пароля.
- Любое разрешённое изменение касается только этого профиля; состояние до/после подтверждено.
- Исходный интерфейс с `defaultgw: yes` сохраняет эту роль, а предпочтительный маршрут не переходит на WISP.
- Проводное управление сохраняется, а фактический интернет-выход подтверждён контрольным потоком.
- Влияние на локальных Wi-Fi-клиентов и полосу/канал наблюдалось до/во время/после.
- Исходное состояние профиля восстановлено.

При несовпадении SSID, неясном статусе, потере проводного управления или необходимости затронуть локальную AP/другие подключения остановиться и сохранить только обезличенный результат.

Доступ к управлению не прерывался. Сырые результаты не сохранялись.

Поэтому общий размер списка и присутствие SSID `White paper` неизвестны, не равны нулю и не выводятся из частично распознанной выборки.

Текущие файлы сканера и status reader сохранены в [снимках исходников](evidence/source-snapshots/manifest.json); хеши совпали с планом повтора. В обоих запусках строго закреплён SSH host key; перед каждым радиозапросом SHA-256 `/bin/ndmc` совпал с `6e6b0bee69e1270160a16711b6a64f4e036b9b984d8eb80acdf76403c243121e`. Сырые stdout/stderr, SSID и BSSID соседних сетей, IP/MAC и секреты не сохранялись. В этой задаче выполнялся локальный аудит, чтение официальных руководств и ограниченные read-only запросы к KN-1012: status для 5GHz station, текущего WAN и радио-объектов до/после; два последовательных survey запуска и один разрешённый повтор для каждой полосы. Каждый вызов проходил строгую проверку SSH host key и SHA-256 `/bin/ndmc`; survey exit 0. ВМ и изменения конфигурации не запускались.

Управление WISP через CLI/RCI и полный список scan-результатов для обеих полос не подтверждены. Для повторного сбора сначала нужен другой узкий способ получить исчерпывающий список и сопоставить целевой SSID без утечки других сетевых данных; в этой задаче survey больше не повторять. Текущая успешная WISP station уже была up, поэтому включение/выключение профиля и поведение после восстановления не тестировались.

### Подготовлен Go schema probe, не запускался

Для следующего разрешённого read-only исследования добавлена `backend/cmd/keenetic-rci-survey-schema`. Она через общий `keeneticrci.Client` вызывает `POST /rci/show` с одной командой `site-survey` для allowlist радиомодуля `WifiMaster0` или `WifiMaster1`. В вывод попадают HTTP-метаданные, digest и ограниченная схема JSON: массивы — с количеством элементов, поля — только из небольшой allowlist; SSID, BSSID/MAC и значения полей не выводятся. Команда не сохраняет сырой ответ.

Команда основывается на [официальном справочнике KN-1012, раздел HTTP API и `show site-survey`](https://storage.googleapis.com/docs.help.keenetic.com/cli/4.3/en/cli_manual_kn-1012.pdf): action-команды не меняют настройки, `POST /rci/show` выполняет их с JSON-параметрами, а `show site-survey <interface>` читает доступные сети. Go-клиент теперь разрешает только этот точный путь как объявленный read-only POST; изменение состояния на этом запросе не разрешается. Сам запрос `site-survey` после подготовки инструмента не отправлялся, поскольку он запускает радио-сканирование; до такого прогона требуется отдельное разрешение владельца и проверка актуального безопасного окна.

Сверка с HTTP API приложением этого руководства подтвердила форму вызова: action выполняется через `POST /rci/show`, а массив сохраняет порядок и форму подкоманд. Подготовленный Go-клиент отправит ровно один элемент `[ {"site-survey": {"name": "WifiMaster0"}} ]` либо то же для `WifiMaster1`. Документация показывает табличный вывод CLI, но не публикует JSON-схему RCI-ответа `site-survey`; поэтому существующий probe намеренно сохраняет только ограниченную структуру JSON и digest, а не пытается интерпретировать результаты сканирования. Это подтверждает синтаксис запроса по документации, но не его работу с token-auth на установленной KeeneticOS 5.2 Beta 3.

План запуска из `backend/` после разрешения:

```sh
go run ./cmd/keenetic-rci-survey-schema --radio WifiMaster0
go run ./cmd/keenetic-rci-survey-schema --radio WifiMaster1
```

### Ограниченный Go reader состояния WISP — локальная реализация

В `backend/pkg/keeneticrci.WISPConnector` добавлено чтение `GET /rci/show/interface` через общий аутентифицированный клиент. Reader отбирает только station ID вида `WifiMasterN/WifiStationN` с типом `wifistation` и извлекает link/state, connected, default gateway и priority. SSID, description, пароль, адреса и все прочие поля не входят в возвращаемую структуру; некорректные или противоречивые повторные записи дают ошибку схемы, а не частичный статус.

Эта реализация подготовлена по обезличенным CLI status snapshots, где наблюдались целевой ID, тип и перечисленные поля. Она **не проверена** против HTTP RCI JSON схемы на KN-1012, не интегрирована в REST-модель, не сопоставляет RCI ID с kernel device и не читает site-survey. Wi-Fi/WISP изменение состояния остаётся запрещено до отдельного контракта и целевой проверки. Никаких запросов или изменений на устройстве в рамках локальной реализации не выполнялось.

### Go-команда проверки WISP status reader, подготовлена

Добавлена `backend/cmd/keenetic-rci-wisp-status`. Команда использует `keeneticrci.WISPConnector` и общий token-auth клиент, выполняет один read-only `GET /rci/show/interface`, выдаёт только allowlisted operational status и не печатает токен или исходное RCI тело. Она собрана в обычном и Keenetic research build, но на KN-1012 не запускалась; поэтому неизвестная HTTP JSON схема остаётся открытым вопросом. После отдельного разрешения команда запускается локально так:

```sh
cd backend
go run ./cmd/keenetic-rci-wisp-status --token-file ~/.config/hestia/keenetic-rci-token
```
