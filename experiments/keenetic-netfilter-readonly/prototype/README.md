# План read-only инвентаризации Netfilter

Этот документ задаёт узкие запросы для последующего выполнения на KN-1012. Сейчас он является планом: никаких команд на роутере ещё не запускали. Выполнять его можно только после явного сообщения координатора об открытии gate.

## Обязательные предусловия

1. Использовать только рабочее дерево `/private/tmp/hestia-kn1012-rci-readonly` и ветку `codex/keenetic-kn1012-rci-readonly`.
2. Сверить существующую запись SSH host key с закреплённым отпечатком `SHA256:u5mFSUOHtvmfjURyMmAe8N2BVONvSiTAoV7OLn2Czoo`; задействовать строгую проверку host key. При отсутствии или несовпадении ключа не подключаться.
3. Сначала выполнить только вычисление SHA-256 для каждого требуемого целевого бинарного файла, записать путь и хеш, а затем запускать только тот же существующий файл для `--help`/`-h` или `--version`/`-V`. Если безопасная проверка хеша или идентичности файла невозможна, бинарник не запускать.
4. Сохранять точную команду, время UTC, источник/путь и версию или SHA-256, очищенный результат, код завершения и ошибки. В вывод не включать адреса/домены домашней сети, идентификаторы клиентов, полные таблицы или несвязанные системные данные.

## Разрешённые запросы

- Прочитать `/proc/version` и `/proc/modules`, оставив в свидетельстве только строки, имена или совпадения, относящиеся к `xt_TPROXY`, `xt_socket`, `nf_tproxy` и `NFT_TPROXY`.
- Прочитать доступные метаданные установленного набора модулей для текущего release ядра (например, записи `modules.builtin` и `modules.dep`, если они существуют и читаемы), отфильтровав только точные релевантные имена. Не перечислять и не сохранять остальную файловую систему.
- Прочитать `/proc/net/ip_tables_targets` и `/proc/net/ip_tables_matches`, если файлы присутствуют, сохраняя только строки `TPROXY` и `socket`.
- Определить через shell builtin `command -v` наличие уже существующих `iptables`, `ip6tables`, `iptables-legacy` и `ip6tables-legacy`. Не считать само наличие команды признаком поддержки расширения.
- Для существующих утилит сначала сверить SHA-256 их точного файла, затем запросить только справку/версию и проверить, перечислены ли `TPROXY` как target и `socket` как match. Не передавать утилите команды создания/изменения правил и не использовать `-A`, `-I`, `-D`, `-F`, `-X`, `-t` либо `-j` без запроса справки конкретного расширения.

## Условия остановки

Остановиться без запасного способа при: закрытом gate; несовпадении/неизвестности host key; невозможности проверить бинарный хеш; необходимости установить пакет или загрузить модуль; отказе чтения; необходимости посмотреть сетевые таблицы, адреса, соединения или трафик; либо если для выяснения поддержки потребовалось бы создать правило, сокет или пакет. Не использовать netfilter rule test, `modprobe`, `insmod`, `rmmod`, `iptables-save`, `ip6tables-save`, `nft list ruleset`, capture-инструменты и сканирование портов.

## Интерпретация

Загруженный модуль либо запись в proc-списке показывает только наблюдавшуюся доступность компонента на момент чтения. Запись в метаданных модуля показывает наличие файла/описания в комплекте, но не то, что компонент можно загрузить в текущем ядре. Справка расширения у существующего бинарника показывает, что данная сборка утилиты знает соответствующее расширение, но не доказывает, что цель/модуль ядра успешно работает. Это исследование не проверяет путь пакета и не подтверждает TPROXY перехват трафика.

## Запрос справки расширений

Если целевой бинарник найден и его SHA-256 предварительно зафиксирован, запрашивать только справку соответствующего расширения и версию:

- `iptables -j TPROXY -h`
- `iptables -m socket -h`
- `ip6tables -j TPROXY -h`
- `ip6tables -m socket -h`
- соответствующие уже существующие `iptables-legacy`/`ip6tables-legacy` команды — только если они обнаружены через `command -v`.

Это справочные вызовы; никаких правил не добавлять. Для каждого исполняемого файла зафиксировать SHA-256 до первого вызова и не вызывать бинарник повторно, если файл или хеш изменились. Запрос версии (`--version`) также допустим после проверки хеша.
