# Настройки прогрева и срок жизни записей

Запуск опыта требует явного выбора режима:

```sh
python3 -B experiments/dns-warm/cache.py gateway --config warm.json --down /run/hestia-lab/fi-down
```

Пример `warm.json`: `{"min_visits":3,"window_seconds":8,"refresh_seconds":1}`. Для каждого канонического имени и типа IN/A порог N считается по запросам на клиентском DNS-входе за интервал `(сейчас − X, сейчас]`. Повтор датаграммы с тех же IPv4-адреса, исходного порта и DNS transaction ID в пределах окна не считается ещё одним посещением. Обращение sing-box к внутреннему резолверу для нового TCP/UDP-потока и собственная попытка планировщика не добавляют посещений.

При достижении N шлюз обновляет только те контексты, из которых уже был получен положительный адрес для клиентского обращения. Для общего имени с разными ответами через RU и FI оба результата сохраняют резолвер, интерфейс и исходный срок действия. Явное финское имя обновляется только через FI. Каждая попытка перепроверяет текущую допустимость выхода. Успех выбранного источника обновляет рабочий адрес. Успех второго источника обновляет его отдельный кандидат: этот адрес можно переиспользовать при отсутствии действующего победителя, если группа разрешена и TTL ещё действует. Сбой обновления сохраняет предыдущий адрес до его исходного срока. При TTL 0 фоновая попытка для него не планируется.

Для живого кандидата очередная попытка назначается к более раннему из двух сроков — через Y или через 80% оставшегося TTL. Минимальный промежуток равен 250 мс. Без следующей успешной записи повтор после ошибки возможен через Y, пока имя ещё часто используется. Окно проверяется каждые 100 мс и непосредственно перед попыткой. При нехватке посещений попытки прекращаются. Ответ, полученный после потери активности или смены допустимой группы, не продлевает запись. Уже отправленная датаграмма может получить ответ позже.

Стенд поддерживает до 128 отслеживаемых имён, до 256 клиентских транзакций для имени в окне и до четырёх параллельных фоновых попыток. У количества внешних запросов есть общий предел 32. При нехватке места алгоритм вытесняет холодное имя или пропускает новый учёт; при заполнении журнала транзакций консервативно занижает частоту. У обычных выбранных записей отдельная граница в 512 записей. Ограничения относятся к экспериментальному планировщику шлюза с доверенными клиентами; полный UDP-сервис ещё не прошёл испытания под произвольной входной нагрузкой. DNS-прототип обрабатывает одну прямую A-запись, не хранит историю после перезапуска.

Из корня репозитория локальные регрессии запускаются командой `python3 -B -m unittest discover -s experiments/dns-warm -p test_warm.py`. Требуется dnspython.

Клиентское посещение учитывается только после проверки обычного DNS-запроса с одним вопросом IN/A. Датаграммы с установленным флагом ответа игнорируются, а другие операции DNS получают NOTIMP. Задача внешней фоновой отправки повторно проверяет идентичность отслеживаемой записи, разрешённый выход и порог N прямо перед обращением к резолверу. Если между планированием и отправкой окно истекло, исключительно фоновый запрос не уходит. Одновременное настоящее клиентское обращение может разрешиться обычным способом.

При повторном выборе набора разрешённых выходов шлюз может снова использовать уже существующее представление победителя. Поэтому каждый новый положительный ответ одного резолвера обновляет все представления, где для этого имени ранее был выбран тот же источник. Представления, использующие другой резолвер, сохраняют собственный адрес и срок. Это позволяет после запрета FI взять последнюю ещё действующую запись RU даже при наличии прежнего RU-ответа с более длинным TTL. При смене доступности FI во время выдачи FakeIP клиентский вход повторно проверяет группу и возвращает SERVFAIL, если она уже запрещена. Следующий внутренний запрос может использовать свежий допустимый RU-кандидат.
