# Повторное использование FakeIP после истечения DNS TTL на Keenetic

На Keenetic Giga KN-1012 sing-box 1.14.4 направил новые TCP- и UDP-соединения к новому loopback-адресу после истечения TTL синтетической реальной A-записи, сохранив числовой FakeIP клиента. Клиент не выполнял повторный FakeIP DNS-запрос. Опыт использовал только локальные процессы и адреса loopback.

## Вопрос и критерии

Проверялось, обновляет ли sing-box адрес назначения для нового потока, когда клиент повторно использует сохранённый числовой FakeIP после того, как истёк TTL реальной DNS-записи и синтетический DNS уже отвечает другим IPv4 адресом.

Критерии: (1) одинаковый сохранённый FakeIP до и после смены ответа; (2) маркеры начального TCP и UDP соединений от цели A; (3) после TTL — видимый новый upstream DNS A-запрос, TCP и UDP маркеры цели B; (4) прямые контрольные пробы показывают, что A остаётся доступной после смены DNS; (5) совпадают четыре хеша IPv4/IPv6 маршрутов и правил, принадлежащие процессам слушатели и процессы удалены.

## Среда и границы

- Физическое устройство: Keenetic Giga KN-1012, hardware `12108000`, KeeneticOS `5.02.B.3.0-2`, sandbox `draft`, title `5.2 Beta 3`, ядро Linux `4.9-ndm-5`, ARM64. Фактическая версия снята командой `ndmc -c "show version"` перед прогонами.
- Runtime: официальный sing-box 1.14.4 Linux ARM64, SHA-256 `d953af885f11d6b547c21a3c0ffe70796963afc802fab959d548311002b4908a`; запуск через существующий `/opt/lib/ld-linux-aarch64.so.1 --library-path /opt/lib`. Хеш исходного архива `dist/runtime/sing.tgz`: `436441f76ee2f7fe21b5b2d426d3cb261a480455a704865789ad533e4273ec26`.
- DNS-имя `service.fakeip-ttl.test.` получало FakeIP `198.18.0.2` с TTL 600. Loopback DNS upstream выдавал `127.0.0.1` с TTL 3 секунды в фазе A и `127.0.0.2` с TTL 3 секунды в фазе B; запросы AAAA получали корректный NOERROR/NODATA.
- Loopback порты: SOCKS `19310/tcp`, DNS ingress `19311/tcp,udp`, synthetic DNS `19312/tcp,udp`, TCP-маркеры `19313` на `127.0.0.1` и `127.0.0.2`, UDP-маркеры `19314` на обоих адресах. Перед каждым запуском порты проверялись свободными.
- FakeIP диапазон `198.18.0.0/24` использовался только внутри sing-box. Он не назначался интерфейсу и не добавлялся в маршруты. Конфигурация направляла только `.test` на loopback direct outbound, а прочие направления блокировала. Внешние DNS, WAN, клиентская сеть, системная конфигурация и службы роутера не использовались.

## Результат успешного прогона

Вторая попытка (`evidence/attempt-20261106T1940Z/`) завершилась с кодом SSH-команды 0. В 19:40:31 UTC helper выдал FakeIP `198.18.0.2`; TCP и UDP через SOCKS вернули маркеры цели A (`127.0.0.1`). В 19:40:36 UTC, после пяти секунд ожидания при TTL три секунды, синтетический upstream был переключён на B (`127.0.0.2`). Клиентский helper прочитал прежнее значение `198.18.0.2` из локального файла и явно отметил `without DNS lookup`. Прямые TCP/UDP проверки подтвердили доступность обеих целей после переключения.

Затем sing-box отправил свежие upstream DNS-запросы A и AAAA для восстановленного домена. Runner напечатал ошибочную строку `upstream_query_count=0`: его краткий grep считал устаревший шаблон. Сырые логи helper содержат шесть принятых запросов upstream (четыре AAAA и два A), включая A с ответом B; вывод основан на этих логах и журнале sing-box. A-ответ был `127.0.0.2`; новый TCP поток вернул `HSTIA-TTL-TCP-TARGET-B`, UDP поток — `HSTIA-TTL-UDP-TARGET-B`. В журнале sing-box видны `found fakeip domain: service.fakeip-ttl.test` и успешное DNS разрешение в B. Helper записал фазу и каждый ответ; исходные логи находятся в `evidence/attempt-20261106T1940Z/remote-output/`.

Четыре снимка маршрутов/правил до и после совпали:

После завершения точные PID sing-box и helper отсутствовали, слушателей на зарезервированных портах не было; временный каталог `/opt/tmp/hestia-r4-ttl-attempt2` удалён. Проверка сохранена в [cleanup](evidence/attempt-20261106T1940Z/cleanup.txt).

## Неудачная попытка и корректировка

Первая попытка (`evidence/attempt-20261106T1935Z/`) дошла до смены назначения для TCP: сохранённый FakeIP направил TCP на B. UDP затем завершился таймаутом. Прямые A/B контроли прошли, маршруты и правила не изменились, PID и слушателей после trap не осталось; каталог попытки удалён.

Диагностика выявила ограничение стендового DNS helper: он отклонял AAAA запросы, а resolver на стороне sing-box ожидал ответы обоих семейств. В исправленной версии helper отвечает на AAAA корректным пустым ответом и отдельно логирует тип и содержимое DNS ответа. Вторая попытка после этой коррекции прошла для TCP и UDP. Первая попытка сохранена как неуспешная; её вывод не используется как доказательство отказа механизма sing-box.

Точный исходный код, конфигурация, начальная фаза и runner каждой попытки скопированы в её `input-snapshot/`; их SHA-256 перечислены рядом. Для успешной попытки локальная сборка выполнялась командой `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath`. Запуск на устройстве выполнялся командой `sh ./device-run.sh` из отдельного приватного каталога после проверки host key, портов, удалённых хешей, `sing-box version` и `sing-box check`.

Helper и runner прошли `go vet`, статическую сборку Linux ARM64, `shfmt 3.11.0` и ShellCheck 0.11.0 ([команды и коды](evidence/local-validation.txt)). Изменённого продукта или постоянных настроек роутера нет.

## Границы вывода

Результат подтверждает только конкретный механизм sing-box 1.14.4 на KN-1012 для одного домена и двух новых потоков после TTL. Переключение фазы B выполнялось уже после TTL; сохранение A при смене upstream до истечения TTL не проверялось. Обе записи оставались в одной группе loopback direct. Не проверялись клиентская сеть, DNS interception, TUN/TProxy, несколько доменов, смена группы/выхода, существующие соединения, конкурентное разрешение, ошибки upstream и поведение при истечении TTL без нового потока.

При объединении исследований из текущей копии JSON в `prototype/` удалены только пробелы в пустой строке. Точные конфигурации аппаратных прогонов и их SHA-256 сохранены без изменения в `evidence/*/input-snapshot/`.
