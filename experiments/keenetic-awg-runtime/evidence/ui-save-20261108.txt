KN-1012 AmneziaWG UI save follow-up — 8 November 2026

Question: why does the provided AmneziaWG profile remain unavailable after it is saved through the Hestia panel?

Environment: Keenetic Giga KN-1012, KeeneticOS 5.02.B.3.0-2, Entware aarch64-3.10. Installed package before this diagnosis: 20261108-010057-46ed33ac8d30.

Observed through the panel: create/save returned the success message and the profile appeared in the VPN list. The sanitized public metadata for both saved attempts reported status `configured`; neither was advertised as available. The exact profile contents and all key material were excluded from this evidence.

The root-only AWG service log reported `AWG UAPI parent directory is not root protected`, followed by an uncommitted activation transaction. Read-only device inspection showed `/opt` root-owned mode 0755 and `/opt/tmp` root-owned mode 0777 without the sticky bit. BusyBox `stat -t` reported raw mode `43ff` after the correction below; Go's `os.FileInfo.Mode()` on the target represented that path as 0777 and did not expose `ModeSticky`. A Keenetic test binary for `TestEntwareParentIsProtected` passed after the implementation was changed to inspect raw `syscall.Stat_t.Mode`.

Correction applied on the router: `/opt/tmp` changed from 0777 to the standard sticky mode 1777. `ls -ld` then displayed `drwxrwxrwt`. This adds the sticky-directory protection and does not alter network settings or routes.

The IPK `20261108-011526-46ed33ac8d30` was then installed. After `/opt/tmp` changed to 1777, its raw mode was `43ff` and the target regression test passed. The AWG service progressed through parent validation but reported that UAPI did not become ready. A short isolated daemon run with no peer created its UAPI socket, while `awg show <temporary-interface> public-key` through the installed tools exited 1. The temporary daemon, TUN interface, socket, and log were removed; no profile data was used by this diagnostic.

Binary inspection identified the mismatch: the daemon listened under `/opt/tmp/hestia-awg-uapi-26b84f/runtime`, while the pinned `awg-tools` binary contained its default `/var/run/amneziawg/` path. Both local static ARM64 binaries were rebuilt so their common UAPI directory is `/opt/tmp/hestia-awg-uapi-26b84f/runtime/amneziawg`; source hashes in `scripts/build/runtime-lock.json` and the package path-consistency check were updated. The IPK `20261108-013154-46ed33ac8d30` was built with SHA-256 `6e948871b30d7a53491167205e0a57b3615de142442c28cd4769c40a66998d29`.

The first install attempt unpacked this IPK but postinst did not start the supervisor. Manual recovery through the package's `configure-package` init action brought the supervisor up; a subsequent `opkg configure hestia` completed and opkg reports `install user installed`. A fresh short test with a temporary interface confirmed `awg show <temporary-interface> public-key` succeeds through the installed daemon/tools pair (`UAPI_PATH_CHECK=PASS`). A second isolated test used generated throwaway keys and no endpoint: `awg setconf` and `persistent-keepalive` 1→0 both succeeded (`KEEPALIVE_TOGGLE=PASS`). Both tests removed their temporary TUN interfaces, sockets and config files; they did not use or print profile keys.

The first package `20261108-013154-46ed33ac8d30` was installed after recovery, but UI activation rolled back. The subsequent target build `20261108-015009-46ed33ac8d30` was uploaded with local SHA-256 `bd98e018fe620ef1b402bf43e2c9960efd67cfa7e6b15f43cc1afd9226e8fb5e`; the device hash matched before `opkg install`. Opkg reports this version as `install user installed`, the supervisor readiness check passes, and the panel remains reachable. A later diagnostic build `20261108-020256-46ed33ac8d30` also installed successfully; its independent restore deadline did not change the failure.

After `015009`, the UI save again rolled back; both profiles still report `configured` and show «Недоступно». The latest AWG service log again reported `cannot restore AWG peer keepalive`, while the controller log recorded refusal to tear down an unowned route. After rollback, AWG interfaces, selected-slot rules and routes in tables 202–209 were absent. In contrast, the installed `-awg-check` helper confirmed handshake for both saved profiles without changing routes. A second isolated target run used a temporary interface and the stored profile: `setconf`, probe keepalive, peer handshake and restoration of the saved keepalive all passed; no address or route was assigned, and the temporary interface/socket/config were removed. Exact IPv4 guard, IPv6 guard and tunnel route forms were also created and removed in empty table 202 and matched the parser.

The next diagnostic build `20261108-021415-46ed33ac8d30` added error categories for Entware command failures and invalid request arguments. After its installation, the UI attempt again rolled back. The new root-only AWG log reported `cannot restore AWG peer keepalive: invalid Entware request`, which localizes the failure to runtime validation rather than an `awg` process exit or timeout. The build `20261108-022035-46ed33ac8d30` added corresponding safe categories and was installed with SHA-256 `0da463241fd470a066476f29dca941aab041b0032a76aa831f468fe2e0b71409`. The subsequent UI attempt reproduced the same invalid-request category. Device metadata showed both stored profiles have keepalive range `25-35`; values of keys and endpoint were not read or printed.

The pinned AmneziaWG `awg-tools` parser uses `u16_range_from_string` for `PersistentKeepalive` in both profile parsing and `awg set ... persistent-keepalive`; the pinned userspace daemon stores that value as `AtomicUintRange` and schedules from the selected interval. The defect was Hestia's Entware-side validator, which accepted only one scalar. The validator now accepts a canonical uint16 scalar or an inclusive `min-max` range, rejecting malformed, inverted and out-of-range values. Regression tests cover the accepted profile form `25-35` and invalid ranges. This fix has not yet been packaged or installed. UI availability, actual marked egress, selected client traffic and reboot persistence remain unconfirmed. `/opt/tmp=1777` was set manually; persistence after reboot is unknown. No profile key or full configuration was written to this evidence.
