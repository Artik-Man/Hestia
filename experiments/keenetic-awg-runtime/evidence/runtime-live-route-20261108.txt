Наблюдение живого route policy AWG на KN-1012 — 8 ноября 2026

Среда
- Устройство: KN-1012, KeeneticOS 5.2 Beta 3, Entware aarch64-3.10.
- Пакет: 20261108-132630-46ed33ac8d30.
- Профиль повторно сохранён через панель Connections; секреты не записывались.

Наблюдения
- Во время живого процесса `awg0` правило IPv4 показывало `from all fwmark 0x202 lookup 202`.
- В table 202 присутствовали `default dev awg0 scope link metric 100` и fallback `unreachable default metric 32767`.
- `latest-handshakes` содержал ненулевую свежую отметку. Агрегированные transfer-счётчики RX и TX менялись; точные объёмы не сохранялись в отчёте.
- Через несколько секунд после этого публичный API сообщил `status=ready`, интерфейс `awg0` присутствовал, активный default в table 202 шёл через `awg0`; WAN default оставался через `eth3`.
- После следующего health failure runtime остановился; API перешёл в `error`, интерфейс исчез, table 202 осталась fail-closed. Ошибка — DNS с `handshake=recent`, `transfer=tx-changed`, `separate-https=failed`.

Вывод и ограничения
- Ядро установило ожидаемое правило mark и активный маршрут через `awg0`; в этом окне туннель передал данные в обе стороны и ненадолго прошёл readiness.
- Следующий периодический probe не получил DNS/HTTPS-ответ и текущая логика завершила runtime. Один live route-снимок не доказывает внешний public IP и не подтверждает пользовательский трафик из группы «Весь мир».
- `ip route get ... mark ...` на текущем Keenetic ip tool не дал результат, поэтому подтверждён путь через содержимое правила и таблицы, а не route-get запросом.
