# Совместимость awg-tools с Keenetic Giga KN-1012

## Вопрос и статус

Можно ли запустить pinned `awg-tools` на KN-1012 через имеющийся Entware loader или подготовить совместимый static ARM64 вариант? Ограниченная проверка завершена 6 ноября 2026 года.

Результат разделяется по способу поставки. Динамический Linux ARM64 `awg` из комплекта Hestia не запускается через Entware loader: устройство использует glibc 2.27, а бинарник требует `GLIBC_2.33` и `GLIBC_2.34`. Статическая сборка из закреплённого официального исходника успешно вывела версию и справку на самом устройстве. Это подтверждает совместимость только интерфейса командной строки в этих двух read-only режимах. Поддержка AWG daemon, UAPI, TUN и VPN не проверялась.

## Среда и артефакты

KN-1012 сообщил read-only preflight: hostname `Keenetic-G-8919`, Linux kernel `4.9-ndm-5`, `aarch64`. На устройстве обнаружен `/opt/lib/ld-linux-aarch64.so.1 -> ld-2.27.so` и `/opt/lib/libc.so.6 -> libc-2.27.so`.

Исходник: официальный `amnezia-vpn/amneziawg-tools` tag `v3.1.20260812`, commit `ee0f0a9aa34ff0a0da4b3433b9512781cfe02843`. Динамический бинарник из Hestia `20261106-170213-66bb2faafc3c` имеет SHA-256 `7b5d8177fba2ebe1454390c069f7385401f95449c6f680e03090d368d7f16a56`, ELF interpreter `/lib/ld-linux-aarch64.so.1`, dependency `libc.so.6`.

На устройстве в приватном `/opt/tmp` проверены два артефакта: динамический pinned binary и static ELF, собранный из того же pinned source Zig 0.17.1 для `aarch64-linux-musl`. Хеши, происхождение Zig, команды, выводы, коды завершения и очистка находятся в [свидетельствах](evidence/). Статический бинарник доступен вне Git в `dist/keenetic-awg-runtime/` для локального воспроизведения.

Официальный upstream release публикует Ubuntu 22.04 и Alpine 3.19 assets; workflow собирает их нативно на `ubuntu-latest` без ARM64 cross target. Готового официального ARM64/static артефакта в этом релизе не обнаружено. Проверенный static вариант является нашей временной сборкой из upstream, не официально опубликованным бинарником. [Release](https://github.com/amnezia-vpn/amneziawg-tools/releases/tag/v3.1.20260812), [workflow](https://github.com/amnezia-vpn/amneziawg-tools/blob/master/.github/workflows/linux-build.yml), [сборка прототипа](prototype/README.md).

## Ожидаемый результат

Для динамического binary ожидался успешный запуск через `/opt/lib/ld-linux-aarch64.so.1 --library-path /opt/lib`; если несовместимость libc останется — сборка pinned upstream source в static ARM64 и запуск только `--version`/`--help`. Любая команда VPN, чтение конфигурации/ключей, создание интерфейсов или изменение маршрутов исключены.

## Фактический результат

Первый запуск dynamic binary напрямую ранее завершался кодом 127: shell не находил interpreter `/lib/ld-linux-aarch64.so.1`. Существующий Entware loader найден. Повторный запуск через него, после подтверждения host/device SHA, дошёл до библиотек Entware, но завершился кодом 1 с ошибками недостающих symbol versions `GLIBC_2.33` и `GLIBC_2.34`. `--help` также не смог начаться.

Static ARM64 build использовал upstream commit выше и Zig 0.17.1; ELF file inspection сообщил `statically linked`. После сверки переданного SHA с host binary прямой запуск на KN-1012 завершился успешно: `--version` code 0, `amneziawg-tools v3.1.20260812`; `--help` code 0, справка выведена. Каждый из моих remote temp каталогов удалён. [Динамический запуск](evidence/loader-run.txt), [static build](evidence/static-build.txt), [static запуск и cleanup](evidence/static-router-run.txt). Независимый тестировщик сверил текстовые протоколы, хеши, commit и локальный ELF; проверка на устройстве не повторялась. [Заключение независимой проверки](evidence/validation.txt).

## Воспроизведение

См. [инструкцию сборки](prototype/README.md). Передавать static binary нужно с проверкой SHA-256 на хосте и устройстве в новом каталоге `/opt/tmp`. Ограничиться `--version` и `--help`; очищать только свой временный каталог. Воспроизводимый протокол конкретного запуска содержится в [evidence](evidence/static-router-run.txt).

## Границы вывода

Подтверждено: конкретная статическая сборка `awg-tools v3.1.20260812` начинает выполнение на KN-1012 и завершает только безопасные `--version` и `--help`. Не подтверждены: корректная работа всех команд, AmneziaWG userspace daemon, kernel UAPI, наличие совместимого AWG kernel module, TUN, handshakes, передача пакетов, firewall/policy routing, DNS, fail-closed, производительность, запуск службы или восстановление после отказа. Прямой запуск бинарника, его version/help, сам по себе не является доказательством поддержки VPN.

## Ошибка сохранения AmneziaWG из панели — 7 ноября 2026 года

Пользователь предоставил AmneziaWG `.conf` и разрешил попробовать сохранить его на KN-1012 через панель. В форме были заполнены профиль и имя; после подтверждения панель сообщила «Шлюз не подтвердил подключение. Проверьте доступность пира и повторите сохранение». Профиль не остался в API и runtime, supervisor был готов, временного binding marker не было; конфигурация и ключи не читались из устройства и не попали в отчёт.

Проверка причин на роутере показала, что `/opt/bin/awg --version` завершается сообщением `not found`, хотя файл существует. Системный ELF loader `/lib/ld-linux-aarch64.so.1` отсутствует. Текущая упаковка ошибочно использовала динамический Linux `awg`; это воспроизводит уже описанное выше ограничение загрузчика. Проверенная статическая сборка доступна локально и имеет SHA-256 `a04ad65d551c6524f89d5939a39f382be7d1e5b48c0d833b1809480fc07adaf3`.

Исправлена сборка: Linux продолжает брать `awg`, Keenetic bundle и `/opt/bin/awg` используют отдельный runtime input `awg-keenetic-static`; ожидаемый SHA-256 включён в lock и проверяется для обеих копий. Build unit test подтверждает корректный выбор и отклонение подменённой копии. Полная чистая сборка `20261107-233634-f59bd2060c31` завершилась кодом 0; `file` подтвердил обе копии Keenetic `awg` как статические ARM64 ELF с указанным hash. IPK с SHA-256 `0af8b04cf010eb94f0e70747932ebb5e37da6b01022d4ff91677c502389c98bc` установлен на KN-1012 после сверки хеша и создания root-only backup конфигурации/предыдущего IPK. `awg --version`, supervisor readiness и четыре LAN API проходят.

Повторное сохранение предоставленного владельцем профиля через UI всё ещё не подтвердило handshake и завершилось HTTP 503. Профиль не появился в API; binding marker и временный интерфейс отсутствуют; IPv4/IPv6 default route hashes совпали с непосредственно предшествующим обновлению состоянием. [Свидетельство целевой проверки](evidence/install-awg-static-20261107.txt). Доступность peer и корректность его удалённой конфигурации не установлены; поэтому причиной отказа может оставаться peer либо другая runtime несовместимость. VPN dataplane и успешное добавление профиля не подтверждены.

## Повторное добавление через панель и диагностика UAPI-каталога — 8 ноября 2026 года

После исправления snapshot-прав, Entware loader, empty-deny smoke check и формата IPv6 guard профили стали сохраняться через панель. Проверка публичной метаинформации показала статус `configured`, а панель — «Недоступно»: профиль сохранён безопасно, handshake ещё не подтверждён. Журнал AWG выявил отказ до запуска runtime: `/opt/tmp` принадлежал root, но имел режим `0777` без sticky bit, поэтому пользователь мог подменить дочерний каталог UAPI. Исправлять только программную проверку было бы небезопасно.

На KN-1012 `/opt/tmp` переведён в стандартный режим `1777`; `ls -ld` подтвердил sticky marker `t`, а BusyBox raw mode после изменения был `43ff`. Добавлена проверка raw `syscall.Stat_t.Mode`, поскольку `os.FileInfo.Mode()` в используемом Entware Go runtime не показывал sticky bit даже после смены режима. Кросс-собранный регрессионный тест `TestEntwareParentIsProtected` запущен на самом Keenetic и завершился `PASS`, включая отказ для writable-каталога без sticky bit. [Свидетельство диагностики и границы вывода](evidence/ui-save-20261108.txt).

После установки IPK `20261108-011526-46ed33ac8d30` и смены `/opt/tmp` на `1777` проверка родителя прошла, каталоги UAPI создавались, но AWG service завершился по тайм-ауту ожидания UAPI. Read-only сверка хешей подтвердила pinned daemon. Изолированный короткий запуск daemon без профиля создал socket; запрос `awg show <временный интерфейс> public-key` через установленный tools binary вернул ошибку, а проверка встроенных строк показала, что `awg-tools` всё ещё использовал `/var/run/amneziawg`. Тестовый процесс, интерфейс, socket и диагностический файл очищены; маршруты и сохранённые VPN-профили не менялись.

Причина установлена: daemon был собран с `ipc.socketDirectory=/opt/tmp/hestia-awg-uapi-26b84f/runtime`, а `awg-tools` — с upstream default `RUNSTATEDIR=/var/run`; их UAPI каталоги расходились. Оба локальных статических ARM64 runtime binary пересобраны на один каталог `/opt/tmp/hestia-awg-uapi-26b84f/runtime/amneziawg`. `scripts/build/run.py` теперь валидирует встроенные directory strings перед упаковкой, а runtime lock закреплён за новыми SHA-256. Keenetic IPK `20261108-013154-46ed33ac8d30` собран локально; SHA-256 `6e948871b30d7a53491167205e0a57b3615de142442c28cd4769c40a66998d29`.

Первая попытка его установки распаковала пакет, но `postinst` завершился с ошибкой запуска supervisor. Штатный `configure-package` затем поднял supervisor, а повторный `opkg configure hestia` завершился успешно. Сборки `20261108-015009` и `20261108-020256` были установлены с готовым supervisor, однако UI активация обеих откатывалась. Изолированная проверка обоих сохранённых профилей подтверждала handshake. На сборке `20261108-022035` безопасная диагностика показала `invalid Entware request` при восстановлении keepalive. В обоих профилях сохранено `PersistentKeepalive = 25-35`. Hestia parser принимает это как допустимый диапазон, но Entware validator ошибочно пропускал только одиночное число. Закреплённый AmneziaWG tools parser и UAPI поддерживают `u16_range`, поэтому диапазон нужно передавать целиком, без схлопывания к одному интервалу. Исправление разрешает каноническое целое или диапазон uint16 с проверкой `min ≤ max`; добавлены тесты на диапазон и malformed values. Новая сборка с этим исправлением ещё не установлена.

На устройстве сохраняются два профиля `AmneziaWG`, оба со статусом `configured`; интерфейса AWG и правил/маршрутов Hestia в выделенных слотах после rollback нет. UAPI daemon и инструменты отвечают согласованно, но актуальный handshake, egress, пользовательский трафик и восстановление после reboot ещё не подтверждены. Режим `/opt/tmp=1777` установлен вручную; его сохранение Keenetic после перезагрузки неизвестно. [Свидетельство диагностики](evidence/ui-save-20261108.txt). Секреты конфигурации не включены в свидетельства.

### Проверка heartbeat и повторной доступности — 8 ноября 2026 года

На установленной сборке `20261108-023504-46ed33ac8d30` runtime достиг публикации health marker, но завершался сообщением `AWG runtime health probe failed` во время следующего цикла. Код отправлял внешний DNS+HTTPS egress probe каждую секунду. Дополнительно проверка контроллера принимала только режим `0640`, хотя Keenetic runtime намеренно создаёт marker `0600 root:root`; это не позволяло контроллеру принять heartbeat Keenetic даже при его наличии.

Исправления в исходниках: контроллер выбирает допустимый режим marker по платформе (`0640` Linux, `0600` Keenetic); проверка egress запускается раз в 15 секунд, а heartbeat считается свежим до 35 секунд. Добавлен тест на закрытый режим Keenetic marker. Проверка `go test -tags keenetic -run 'TestKeeneticAWGHealthModeRequiresPrivateRootFile|TestAWGHealthRecordFreshness' ./internal/controller` прошла. Широкий набор Go-тестов контроллера не смог запуститься в sandbox: `httptest` не получил разрешение слушать локальный IPv6 порт. Darwin `go test -tags keenetic` для linux-only binding зависимостей тоже не является корректным кросс-build способом, так как не включает linux-файлы Entware. Следующий шаг — собрать Keenetic IPK, установить после root-only backup, убедиться, что heartbeat остаётся свежим после нескольких циклов, затем проверить клиентский трафик.

Keenetic IPK `20261108-024315-46ed33ac8d30` собран локально и установлен после резервного сохранения конфигурации, AWG профилей, правил и таблиц. Его локальный и целевой SHA-256 совпали: `6a82bc9519115821b8bb5a7c977284e3f61cc1c3e79728e295479f4e43397062`; supervisor снова сообщил готовность. Повторное сохранение через UI не завершилось доступным туннелем: публичный API показывает `status=error`, панель — «Недоступно». Таблица содержит только owned guards, интерфейса AWG нет, route manifest сохранён. Journal сообщает `activation-and-rollback`, а сервис маршрутов — отказ удаления нераспознанной записи таблицы. Точная transient запись и первая ошибка активации пока неизвестны. Штатный `-awg-retire` не изменил состояние, поскольку verifier отказался подтверждать offline router outbound. В течение 25 секунд наблюдения новые AWG default routes не появились; проверка пользовательского трафика не выполнена. [Целевое свидетельство](evidence/ui-save-20261108-024315.txt).

### Добавление провайдера в группу через UI — 8 ноября 2026 года

Пользователь сообщил, что «ПАКТ» всё ещё отсутствует в группах. Реализовано отдельное действие «Добавить ПАКТ в группу»: оно использует platform candidate из каталога RCI и не требует сохранять VPN-профиль. Linux-каталог при этом не получает Keenetic-only выход. Сборка `20261108-122003-46ed33ac8d30` с IPK SHA-256 `519b3d72fa654619db002c1b1e20ead65c3d77f5773cdc2ce163fac819779281` установлена на KN-1012.

Первая попытка через UI обнаружила две проблемы. Reorder-компилятор сравнивал кандидат с уже изменённым порядком outbound и отказывал для профиля, где добавлялся первый прямой интерфейс. После исправления staging проходил, но Smoke отклонял свежий snapshot из-за старого quality report с прежним списком выходов. В smoke устаревшие и не совпадающие по topology quality report теперь игнорируются для конфигураций без Hysteria 2; если профиль содержит Hysteria 2, актуальный report остаётся обязательным. Обе проблемы воспроизведены и устранены.

Последняя попытка на странице групп завершилась сообщением «Порядок применён шлюзом». API показывает в `default` выходы AmneziaWG-debug и ПАКТ, оба доступны; WAN default route остался через `eth3`. Supervisor готов и `.binding-pending` отсутствует. Поскольку AmneziaWG runtime всё ещё недоступен, контроллер выбрал ПАКТ как следующий здоровый выход по порядку группы. Это ожидаемый failover группы и не подтверждает работу VPN; текущий трафик группы может идти напрямую через провайдера, пока AmneziaWG недоступен. Сохранённое поле `defaultExit` не менялось. [Протокол проверки](evidence/group-uplink-20261108.txt).

Ожидаемый результат подтверждён для конкретного KN-1012: каталог отображает провайдера, UI позволяет добавить его в группу и успешно сохраняет изменение. Граница вывода — один роутер и одна конфигурация; handshake, VPN egress и клиентский трафик через AmneziaWG остаются отдельными невыполненными критериями основной AWG-цели.

### Повторная проверка handshake и сохранение неизменённого профиля — 8 ноября 2026 года

Владелец перенёс `AmneziaWG-debug` в группу «Весь мир» и сообщил, что профиль остаётся недоступным. На установленном IPK `20261108-122003-46ed33ac8d30` ограниченная проверка сохранённого конфига через `-awg-check` подтвердила временный handshake. Это не назначало IP-адрес и маршрут. Повторное сохранение того же профиля в панели завершилось успешно, но профиль остался «Недоступно». После операции supervisor был готов, публичный AWG статус — `error`, процесса runtime и интерфейса `awg0` не было, таблица 202 оставалась fail-closed; системный default route Keenetic не изменился. [Протокол](evidence/handshake-and-resave-20261108.txt).

Свежей попытки долговременного запуска после повторного сохранения не было: transaction planner игнорировал неизменившуюся AWG generation, хотя пользователь явно сохранял профиль повторно. Добавлено поведение, которое включает пере-сохраняемое готовое подключение в runtime restart plan даже при тех же байтах; сейчас выполняются тесты и сборка для повторного target-прогона. Временный handshake не подтверждает долговременный egress, а клиентский трафик остаётся непроверенным.

### Долговременный запуск и отказ периодической пробы — 8 ноября 2026 года

Установлен пакет `20261108-125012-46ed33ac8d30` (SHA-256 `fc22ee6d0918a11f634a747d343ccc9aa4c141b0fc476572bb86fa5951b18fc8`). После повторного сохранения неизменённого профиля новая логика действительно перезапустила AWG service. `awg0` появился; в таблице 202 был активен default через `awg0`, после чего сервис сообщил `AWG runtime health probe failed`, остановился и восстановил unreachable defaults. По порядку кода это значит, что запуск прошёл handshake и первичную marked DNS+HTTPS проверку, а отказ произошёл на следующем 15-секундном health tick. Сборка скрывала, какой именно этап упал, поэтому статус профиля остался «Недоступно». [Свидетельство](evidence/runtime-health-flap-20261108.txt).

Добавлена безопасная классификация следующего health failure (`DNS`, `HTTPS` или `HTTPS status`), чтобы найти нестабильный этап без записи endpoint или сырых ошибок. Эта диагностическая правка ещё не собрана и не установлена. Требуются повторные измерения, сохранение health-marker, фактический egress через peer и клиентский поток через группу «Весь мир».

### Разделение DNS, handshake и передачи — 8 ноября 2026 года

Последний установленный пакет `20261108-130054-46ed33ac8d30` на KN-1012 сейчас показывает `error`; интерфейса AWG нет, а таблица слота остаётся fail-closed. UI в одном чтении показывал кэшированное «Доступно», поэтому перед следующим выводом статус нужно обновить в панели и сверить с `-awg-list` на устройстве. Предыдущий живой запуск установленной диагностической сборки завершился категорией `DNS`; свежесть handshake и передача на этом health tick ещё не записывались.

В установленной диагностической сборке `20261108-131732-46ed33ac8d30` пользовательский профиль повторно сохранён через UI с подтверждением «сохранено». Через один health-интервал API показывал `error`, интерфейс AWG отсутствовал, таблица 202 содержала только `unreachable default`, а WAN default оставался через `eth3`. Новая запись в журнале: `AWG runtime health probe failed: DNS (handshake=recent, transfer=changed)`. Это подтверждает, что во время неудачной DNS-пробы handshake оставался свежим и хотя бы один transfer-счётчик изменился, но старый формат не различал RX от TX и не проверял HTTPS независимо. [Свидетельство](evidence/runtime-health-diagnostic-20261108.txt).

Сборка `20261108-132630-46ed33ac8d30` проверяет все IPv4 DNS-серверы профиля по очереди, записывает резервный resolver только по его номеру, сравнивает направления RX/TX без объёмов и при DNS-отказе делает отдельную bound HTTPS-пробу на последнем подтверждённом DNS-адресе. После повторного сохранения профиля журнал показал `handshake=recent`, `transfer=tx-changed`, `separate-https=failed`; текущий UI после обновления здоровья показал «Недоступно». API сообщил `error`, `awg0` отсутствовал, слот оставался fail-closed, WAN route не изменился. [Новое свидетельство](evidence/runtime-health-independent-https-20261108.txt).

Последующий live-снимок показал ожидаемое `fwmark 0x202 → table 202`, активный `default dev awg0` и изменение RX/TX; на короткое время публичный API стал `ready`. Затем следующий periodic probe снова завершился DNS failure, после чего runtime остановился и вернул status `error`/unreachable guard. Это показывает, что локальные rule и table применяются и туннель временно получает данные в обе стороны; короткий успешный интервал не подтверждает стабильный интернет-egress или выбранный клиентский поток. [Свидетельство live route](evidence/runtime-live-route-20261108.txt).

Обнаружена причина, по которой временный health failure оставлял профиль выключенным: service возвращал ошибку и завершался после одного неуспешного periodic probe. Локально изменён цикл: при таком отказе markers снимаются и группа считает выход недоступным, но runtime остаётся запущен и повторяет пробы; readiness публикуется обратно только после успешного bound DNS+HTTPS. Изменение пока не собрано и не проверено на роутере.
