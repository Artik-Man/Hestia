# Частичная потеря UDP до одного адреса

Проверка: достаточно ли постоянных измерений на **обоих** выходах, чтобы переключить только новые UDP-потоки к X при потерях около 10% на FI‑1? Мы повторно используем топологию и заранее подготовленное правило [предыдущего стенда](../scoped/README.md). Создание исключения для произвольного IP во время работы — отдельный эксперимент. Здесь группа FI, X = 203.0.113.77, Y = 203.0.113.78. Два FI-выхода и посторонний RU-выход — три отдельных veth. Для каждого клиентского запроса создаётся новый сокет. На реальных провайдерах, SSTP и плате этот тест не запускался.

## Как измеряем и принимаем решение

Шлюз посылает к одному UDP echo-сервису X по одной пробе через каждый FI-интерфейс одновременно; оба сокета привязаны через SO_BINDTODEVICE. На каждый ответ отводится 80 мс. Интервал начала пар внутри каждой фазы — 120 мс, независимо от успеха прошлой пробы. Размер сообщения, цель и таймаут для обоих путей одинаковы. Входной фильтр на стороне получателя теряет только UDP/X на FI‑1; он не меняет маршрут и не управляет выбором выхода. В реальной сети отсутствие ответа означает недоставку в пределах таймаута в любом направлении, а не достоверное указание на место потери.

После каждой пары контроллер сравнивает записи в скользящем окне (now − 3600 секунд, now]. Неполное окно допускается только после накопления не менее 100 пар. При равенстве остаёмся на текущем выходе. Переключение допускается при преимуществе не менее 5 процентных пунктов, не менее 5 дополнительных успешных ответов и двустороннем точном парном sign-test p ≤ 0,05. Статистика использует только пары с разным исходом. При смене решения контроллер отправляет PUT только для селектора udp-x и проверяет неизменность общего селектора finland. Возврат подчинён тому же сравнению: восстановления FI‑1 до уровня FI‑2 недостаточно.

**Это пример воспроизводимой политики эксперимента, а не утверждённые требования.** Короткая серия и автокорреляция потерь, многократные сравнения на каждой пробе и малое число независимых сетей не позволяют считать p гарантией надёжности или прогнозом частоты ложных переключений. Для эксплуатации необходимо отдельно проверить частоту проб, запас для таймаута с учётом RTT, задержку обнаружения на заполненном часовом окне и стоимость проб на множестве направлений. При одновременной полной недоступности обоих путей выбор «сохранить текущий» в этом компараторе не является механизмом блокировки: доступность группы и fail-closed должен обеспечивать отдельный слой. Тест не сравнивает скорость и не затрагивает открытые соединения.

## Воспроизведение

Отдельная ARM64-ВМ с [закреплённым образом Debian 12](../fakeip/vm/lima.yaml). Создать её через `limactl start --name hestia-loss --tty=false experiments/fakeip/vm/lima.yaml`. Передать каталог experiments с сохранением структуры (нужны partial-loss, scoped/config.json, scoped/probes.py и fakeip/traffic.py). Установить проверенный sing-box 1.14.4 через [provision.sh](../fakeip/vm/provision.sh); в ВМ также нужны iptables и curl. Внутри гостя:

```sh
(cd experiments/partial-loss && python3 -B -m unittest)
sudo bash experiments/partial-loss/lab.sh /tmp/loss-evidence
# Повторная проверка записанных результатов; root нужен, если каталог принадлежит root.
sudo python3 experiments/partial-loss/verify.py /tmp/loss-evidence
```

Каталог результатов должен быть новым или пустым. Для отдельного сравнения: `python3 experiments/partial-loss/policy.py HISTORY.jsonl fi1`; каждая строка содержит строго возрастающий ts (секунды эпохи) и два булевых поля fi1, fi2 (получен правильный ответ). live.py запускает измерения и меняет селектор, lab.sh создаёт и очищает изолированные пространства имён, verify.py читает сохранённый трафик и проверяет, на каком интерфейсе был каждый запрос. Вывод ядра и sing-box записывается в version.txt. По завершении остановить экспериментальную ВМ командой `limactl stop hestia-loss`.

| Фаза | Пар | Потери FI‑1 | Потери FI‑2 | UDP/X |
|---|---:|---:|---:|---|
| Исходное состояние | 100 | 0 | 0 | FI‑1 |
| Краткий всплеск | 3 | 3 | 0 | FI‑1 |
| После всплеска | 17 | 0 | 0 | FI‑1 |
| Каждая десятая проба теряется | 220 | 22 | 0 | FI‑2 с 51-й пары этой фазы |
| Восстановление | 100 | 0 | 0 | FI‑2 |

На момент переключения в окне накопилась 171 пара, потери 9 против 0 (из них 3 до начала длительного ухудшения). От начала этой фазы до пары, вызвавшей решение, прошло **6,00 с**; p = 0,00390625. Это время обнаружения в конкретном прогоне с неполным окном, не SLA и не время восстановления произвольного пользовательского соединения. На свежем старте и при полном часовом окне задержка будет другой.

[Журнал причин](evidence/decisions.jsonl), [сырые замеры](evidence/rounds.jsonl), [ответы клиенту](evidence/clients.jsonl), [счётчики фильтра](evidence/impairment.txt), [результат проверки](evidence/verification.txt). Верификатор сверил 880 исходящих UDP-проб и 9 свежих клиентских потоков с pcap на FI‑1, FI‑2 и RU, а ответы — с журналом получателя. TCP/X и UDP/Y оставались на FI‑1; UDP/X после переключения и после восстановления шёл через FI‑2. На RU эти запросы не попали. В обе стороны проверялся факт доставки по echo, а сам путь сверялся по исходящему трафику.

**Час не прошёл в реальном времени.** Тот же верификатор отдельно проиграл 440 реальных пар исходов с синтетическими метками через 36 с. Это даёт 100 пар в заполненном часовом окне. Первое переключение в replay — глобальная пара №141 (№21 фазы ухудшения); на конец все старые потери ушли из окна, последние 100 пар полностью успешны на обоих выходах, и FI‑2 сохранился. Такой replay проверяет истечение истории и отсутствие обратного переключения при равенстве, но не эксплуатационную устойчивость за реальный час.
