# Управление Ethernet-портами Keenetic: локальное исследование

## Вопрос и границы

Можно ли на KN-1012 обнаружить физические Ethernet-порты, связать их с логическими интерфейсами и управлять их ролями из автоматизируемого канала? Этот этап ограничен локальными документами и ранее сохранёнными свидетельствами: SSH, CLI, RCI и изменение сетевого состояния роутера не выполнялись.

## Подтверждённое

- На KN-1012 под KeeneticOS `5.02.B.3.0-2` подтверждён запуск `/bin/ndmc -c 'show version'`, `show system` и `show ip policy` через SSH. Последний вывод не сохранялся: фиксировались только длина и SHA-256. Эти результаты подтверждают транспорт и три перечисленных read-only запроса; ни один из них не подтверждает обнаружение физических портов или их настройку. См. [отчёт и свидетельства RCI/CLI](../keenetic-rci-readonly/README.md).
- Официальная инструкция Keenetic документирует для KN-1012 изменение режима Ethernet-порта (скорость/дуплекс, отключение), назначение свободного LAN-порта как WAN и обратное использование не задействованного WAN-порта как LAN через веб-интерфейс. Для переназначения LAN в WAN инструкция требует сначала отсоединить кабель провайдера; для возврата WAN в LAN рекомендует резервную копию конфигурации и удаление соответствующего wired ISP connection. Это документированные возможности пользовательского интерфейса, а не доказательство наличия таких же операций в `ndmc`, RCI или API.
- Документация CLI Keenetic приводит `show interface Home` как пример запроса в Web CLI, одновременно предупреждая, что Web CLI неполон и может отличаться от Telnet/SSH. Поэтому этот пример годится как кандидат на read-only проверку после отдельного разрешения, но не как подтверждение вывода физических Ethernet-портов.

Официальные источники: [роли и режимы сетевых портов для KN-1012](https://support.keenetic.com/hero/kn-1012/en/16485-changing-the-operating-mode-and-role-of-network-ports.html), [CLI Keenetic](https://support.keenetic.com/hero/kn-1012/en/18480-command-line-interface--cli-.html). Источники описывают пользовательскую процедуру и CLI в общем виде; аппаратное поведение на текущей установленной прошивке этим исследованием не проверялось.

## Не подтверждено

- Перечень разъёмов, их имена в CLI, RCI и Linux и связь «физический разъём → switch port → VLAN/bridge → интерфейс KeeneticOS/Linux».
- Доступность/полнота `show interface Home` на SSH-CLI конкретной сборки, чтение link state каждого физического разъёма и событие при вынимании кабеля.
- Наличие стабильного машинного read/write интерфейса для назначения порта провайдеру, изменения скорости/дуплекса и отключения/включения порта. HTTP RCI в предыдущем опыте вообще не проверялся.
- Фактический выход трафика через переназначенный порт, влияние на другие порты, VLAN, аппаратное ускорение и восстановление после ошибки.

## Минимальный следующий аппаратный опыт

### Ресурсы и границы

1. KN-1012 с зафиксированной точной сборкой и сохранённой владельцем резервной копией конфигурации; доступ по уже настроенному SSH с проверкой host key. Не использовать `hestia-prod` ВМ или менять её питание.
2. Один свободный и явно выделенный LAN-разъём, не обслуживающий домашний/рабочий сегмент. Провод от ISP должен быть отсоединён от роутера на всём протяжении переназначения порта.
3. Отдельный тестовый компьютер с Ethernet и прямым кабелем к выделенному порту. По возможности отдельный контролируемый upstream или изолированный L2-сегмент; никакой генерации трафика в чужую сеть.
4. До нового запуска архитектор должен получить у владельца точные разрешённые запросы и операции CLI/веб-панели, отдельное разрешение на изменение конфигурации и согласованное окно. Нынешнее поручение разрешает только локальную подготовку; прежнее разрешение на read-only запросы не расширяется автоматически.

### Порядок

1. Сверить точную версию устройства и SSH host key. Зафиксировать время, версию, название выделенного физического порта и снимок его исходного состояния из веб-панели. Конфигурацию целиком в отчёт не помещать; её резервную копию хранит владелец.
2. После отдельного разрешения выполнить только утверждённый read-only запрос `show interface Home` по SSH и сравнить его с интерфейсом веб-панели. Если CLI показывает только bridge/сегмент Home, так и записать: не выводить из него карту switch-портов. Для физической связи наблюдать тестовый порт в веб-панели при отключённом и подключённом тестовом кабеле; для каждой пробы оставить временную метку и состояние тестового линка.
3. Если цель проверки именно автоматическое обнаружение — остановиться после read-only фазы. Если отдельно разрешена проверка контроля, через штатный веб-интерфейс изменить только скорость/дуплекс выделенного LAN-порта на поддерживаемый фиксированный режим, подтвердить соответствие индикации/линка тестового компьютера, вернуть исходную автонастройку и повторно проверить линк. Эта операция проверит аппаратный контроль через GUI, но не пригодность CLI/RCI для Hestia.
4. Переназначение LAN↔WAN — отдельная, более рискованная ветка, не включённая в минимальный прогон. Проводить её только после отдельного решения владельца: применить официальную процедуру на свободном порту при физически отсоединённом кабеле провайдера, подтвердить получение адреса только от тестового upstream и затем вернуть исходную роль. Не менять роль рабочего WAN и не использовать домашний интернет как тестовый upstream.
5. В конце сверить восстановление исходной конфигурации/автонастройки и работоспособность тестового сегмента. При несовпадении остановиться; не пробовать дополнительные команды или повторную запись. Сохранить исходные успешные и неуспешные ответы без перезаписи, команды, коды возврата, снимки до/после и результат очистки. Удалить только собственные временные файлы.

### Критерии результата

- **Обнаружение подтверждено**, только если read-only ответ на зафиксированной сборке стабильно идентифицирует доступные интерфейсы и link state, а независимое подключение/отключение кабеля к выделенному разъёму меняет ожидаемое состояние. Отдельно указать, различает ли API сам физический порт или только bridge/сегмент.
- **Контроль через UI подтверждён**, если выделенный порт применяет заданный режим и после возврата имеет точное исходное состояние; это не считается доказательством программного контракта.
- **Автоматизируемый контроль подтверждён**, только если разрешённая операция CLI/RCI/API меняет ровно тестовый порт, результат читается обратно, а повторное применение и восстановление дают ожидаемое состояние. Не называть операцию подтверждённой до независимой проверки фактического линка.
- Любой побочный эффект на другой порт, потеря управления, несовпадение link state или невозможность восстановления означает остановку и неуспех опыта.

## Что нужно получить перед следующим шагом

Минимум: подтверждение выделенного физического LAN-порта и тестового компьютера/кабеля. Для read-only фазы также требуется точная граница разрешённых команд. Для изменения режима — явное разрешение на изменение выбранного порта и безопасное окно. Для проверки назначения WAN — отдельный изолированный upstream и отдельное разрешение; это не нужно для первого read-only опыта.

## Выполненная read-only инвентаризация 6 ноября 2026 года

Владелец разрешил ограниченное чтение состояния интерфейсов через существующий SSH. Никаких настроек, подключений и маршрутов не меняли; доступ к `hestia-prod` ВМ не использовали. Перед CLI-запросом проверяли host key с обязательным `StrictHostKeyChecking=yes` и pin `SHA256:u5mFSUOHtvmfjURyMmAe8N2BVONvSiTAoV7OLn2Czoo` для записи `[192.168.1.1]:222`. SHA-256 `/bin/ndmc` совпал с ранее записанным `6e6b0bee69e1270160a16711b6a64f4e036b9b984d8eb80acdf76403c243121e`.

Последний завершённый запрос: `/bin/ndmc -c 'show interface'` через SSH, завершился с кодом 0 около `2026-11-06T20:13:12Z`. Локальный runner сохранял в памяти необработанный вывод, но на диск записал только его длину, SHA-256, разрешённые поля и SHA-256 снимка runner. Сырой stdout/stderr, адреса, MAC, ключи, секреты, описания кроме точных утверждённых имён, счётчики и маршруты не сохранялись. [Санитизированный результат и снимок runner](evidence/attempt-20261106T201312Z-query-1/result-sanitized.json).

### Наблюдения

- `show interface` перечислил логический родитель `GigabitEthernet0` и дочерние интерфейсы типа `port`: `GigabitEthernet0/0` (индекс 0, link down), `GigabitEthernet0/1` (индекс 1, up, 100/full), `GigabitEthernet0/2` (индекс 2, up, 100/full), `GigabitEthernet0/3` (индекс 3, down). В выводе повторялись строки дочерних интерфейсов в отдельных ветках. Человеческих подписей `port 1`/`port 4` у этих объектов не было.
- `GigabitEthernet1/0` (индекс 0, тип `port`) имел link up и 1000/full. В его родительском блоке `GigabitEthernet1` видны поля `defaultgw=true` и `priority=65532`, а также вложенное `defaultgw=false`; поэтому этот снимок нельзя использовать как однозначное доказательство активного default route.
- `Home` отображался как `bridge`, link/state up. Это статус логического моста, а не состояние каждого физического LAN-разъёма.
- Подпись `Solar (Moscow)` была связана в одном интерфейсном блоке с `Wireguard2` (link/state/status down, defaultgw false, priority 65352). `Poppuri` была связана с `SSTP1` (link/state down, defaultgw false, priority 65528). Это подтверждает только отображённые CLI-поля, не работоспособность или возможность включить подключения.
- Вывод содержит `WifiMaster0` и `WifiMaster1` с link/state up, а также вложенные строки типа `accesspoint` и `wifistation`. Для двух строк SSID сравнение с пользовательскими значениями `iPhone` и `White Paper` дало `false/false`. В этих вложенных строках не было однозначного идентификатора WISP-профиля; их связь с конкретной точкой/станцией в сохранённой проекции неоднозначна, поэтому соответствие SSID/профилю не установлено.

### Ограничения вывода и повторение

На момент начального снимка соответствие физических гнёзд было неизвестно. Позднее официальная инструкция именно для KN-1012 установила порядок LAN-портов: первый — `GigabitEthernet0/0`, второй — `/0/1`, третий — `/0/2`, четвёртый — `/0/3`. После подключения ноутбука к физическому порту 1 поднялся только link `/0/0`; после отключения ноутбука он вернулся в down. Это согласуется с документацией и подтверждает наблюдаемую связь port1 ↔ `GigabitEthernet0/0` для этой конфигурации. Сама инструкция описывает расписание и соответствие номеров, но не заменяет независимой проверки остальных гнёзд.

Порт 4 (`GigabitEthernet0/3`) показывал link down в базовом, подключённом и отключённом снимках. Это означает, что активный Ethernet link не наблюдался в эти моменты; из этого нельзя заключить, что к разъёму физически не подключён кабель или устройство.

Точные команды, коды завершения, длина и хеш вывода, host-key/`ndmc` preflight, скрипт и санитизированные поля лежат в отдельных каталогах `evidence/attempt-*`. Неуспешные локальные попытки сохранены: `20:03:44Z` runner остановился до интерфейсного запроса из-за собственной ошибки allowlist; `20:09:51Z` остановился до SSH из-за поиска known_hosts под неправильным host token. Для первой ошибки сохранён точный наблюдавшийся traceback, но исходник runner той ревизии отсутствует; для успешной ранней пары запросов `20:04:28Z` исходный runner также не сохранился. Эти отсутствующие снимки не восстановлены. Runner и stdout структурной проекции присутствуют для попытки `20:10:12Z`; точный runner snapshot присутствует для финальной попытки `20:13:12Z`. Неудачные попытки не меняли состояние роутера.

Для повторения используйте [prototype/inventory.py](prototype/inventory.py). Скрипт проверяет port-222 host-key pin, затем `/bin/ndmc` SHA-256, посылает только `show interface`, имеет тайм-аут 30 секунд и сохраняет отдельный снимок исходника и санитизированное свидетельство для каждой попытки. Он не содержит команд изменения состояния.

Официальная инструкция для KN-1012 документирует портовую нумерацию и управление доступностью LAN-порта через расписание. Пример производителя привязывает расписание так: `interface GigabitEthernet0/2 schedule <имя>`; для port1 соответствует `GigabitEthernet0/0`. Включение/отключение в примере задают временными действиями `action start <минута> <час> <день-недели>` и `action stop <минута> <час> <день-недели>`. Чтобы удалить назначение, инструкция показывает `no interface GigabitEthernet0/2 schedule`; для port1 подставляется `GigabitEthernet0/0`. Конфигурацию требуется сохранять через `system configuration save`. Источник: [Work schedule for a network port — KN-1012](https://support.keenetic.com/hero/kn-1012/en/49450-work-schedule-for-a-network-port.html). Это расписание, а не немедленная команда `shutdown`; прямое моментальное включение/выключение интерфейса через CLI/RCI не подтверждено. На устройстве этот способ не применялся.

Кандидат на отдельный контрольный опыт: сначала read-only проверить, не назначено ли расписание на `GigabitEthernet0/0`, и сохранить безопасный снимок исходного состояния; затем выбрать уникальное временное имя расписания, подключить ноутбук к port1, проверить контролируемое отключение link и его возврат, снять временное назначение/само расписание и сохранить исходную конфигурацию. Нужны отдельная координация времени/окна и подтверждение альтернативного канала управления, так как временное отключение лишит ноутбук link на этом порту. Изменений в этом исследовании не выполняли; расписание и direct CLI control остаются непроверенными.

### Проверка после подключения ноутбука к порту 1

После того как владелец подключил ноутбук к физическому порту 1, выполнен read-only `show interface` с новым снимком runner, свежей проверкой host-key pin и SHA-256 `/bin/ndmc`. Команда завершилась с кодом 0 в `2026-11-06T20:22:01Z`; [свидетельство и точный снимок runner](evidence/attempt-20261106T202201Z-query-1/result-sanitized.json).

По сравнению с базовым снимком изменился только `GigabitEthernet0/0`: link `down` → `up`, согласованная скорость 1000/full. `GigabitEthernet0/1` и `GigabitEthernet0/2` остались up на 100/full; `GigabitEthernet0/3` остался down; `GigabitEthernet1/0` остался up на 1000/full. Это коррелировало с подключением ноутбука к физическому port1.

После отключения ноутбука выполнен ещё один read-only `show interface`, который завершился кодом 0 в `2026-11-06T20:22:49Z`; [свидетельство и точный снимок runner](evidence/attempt-20261106T202249Z-query-1/result-sanitized.json). `GigabitEthernet0/0` вернулся `up` → `down`; `/0/1` и `/0/2` остались up на 100/full, `/0/3` остался down, `GigabitEthernet1/0` остался up на 1000/full. В сочетании с официальной картой портов для KN-1012 это подтверждает port1 ↔ `GigabitEthernet0/0` по двум действиям владельца. Другие физические порты не переключали. Настройки устройства не менялись.

## Подготовка к публикации

Перед коммитом рабочие файлы `prototype/` отформатированы и проверены Ruff; shell-прототип проверен shfmt и ShellCheck там, где он есть. Это локальные проверки исходников; новые аппаратные прогоны не выполнялись. Неизменяемые снимки в `evidence/` сохранены в исходном виде: их хеши относятся к соответствующим попыткам, а не к отформатированным рабочим файлам.
