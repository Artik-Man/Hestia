# Выбор и отказ двух локальных выходов sing-box на Keenetic

## Вопрос и критерии

Проверить на Keenetic Giga KN-1012, может ли закреплённый sing-box автоматически выбрать один из двух локальных VLESS-выходов, перейти на резерв после остановки предпочитаемого выхода, вернуться после его восстановления и отказать TCP/UDP-потоку при остановке обоих выходов. Критерии полного опыта: отдельные TCP/UDP маркеры с атрибуцией к выходу; прямой контроль подтверждает доступность локальной цели; при двух остановленных выходах пользовательские счётчики маркеров не меняются; выполняется точечная очистка, а канонические хеши таблиц и правил совпадают до и после.

Владелец остановил работу после первой незавершённой аппаратной попытки. Поэтому выбор выхода подтверждён только для исходного состояния. Отказ предпочитаемого выхода, возврат после восстановления и блокировка при отказе обоих не проверялись.

## Среда и границы

- Keenetic Giga KN-1012, KeeneticOS `5.02.B.3.0-2` (5.2 Beta 3), Linux `4.9-ndm-5`, `aarch64`.
- sing-box 1.14.4, официальный ARM64 ELF SHA-256 `d953af885f11d6b547c21a3c0ffe70796963afc802fab959d548311002b4908a`; запуск через уже имеющийся `/opt/lib/ld-linux-aarch64.so.1 --library-path /opt/lib`. Проверенный архив SHA-256 `436441f76ee2f7fe21b5b2d426d3cb261a480455a704865789ad533e4273ec26`.
- Входы попытки 01 и их хеши сохранены в [`evidence/attempt-01/input-snapshot/`](evidence/attempt-01/input-snapshot/). Локальный статический harness SHA-256 `594040d18ccfbcfcad9345eda4de64c19dd5c0d9056e952cd3333173d7b0f459`.
- Проверки касались только числовых loopback-адресов и временных портов `19330–19339`. Интернет health-check не использовался; `urltest` был задан локальный URL `http://127.0.0.1:19334/health`. Маршруты, правила, firewall, интерфейсы, DNS, sysctl, пакеты и системные службы не настраивались.
- Временный каталог попытки `/opt/tmp/hestia-r4-exits-20261106-1930` удалён. Запущенных дочерних процессов после trap-cleanup не осталось; проверенные точные PID: `30768`, `30773`, `30774`, `30775`, `30776`.

## Попытка 01 — TCP прошёл, UDP остановил опыт

Попытка выполнена 6 ноября 2026 года, `19:40:28–19:40:40 UTC`, одним ограниченным SSH-запуском. Входы, команда, stdout/stderr, отфильтрованные runtime-журналы и запись очистки сохранены в каталоге `evidence/attempt-01/` и соседних файлах `attempt-01-*`.

Наблюдения:

- `sing-box version` сообщил 1.14.4; `sing-box check` для клиентской и обеих серверных конфигураций завершился успешно.
- Локальный прямой TCP/UDP-контроль получил собственные маркеры.
- `urltest` через локальный health URL измерил для выхода A `3–15 ms`, для B `84–102 ms`; тестовый ответ B намеренно задерживался на 80 ms. SOCKS/TCP вернул `EXIT-A-TCP-MARKER`, подтвердив фактическое исходное назначение клиентского TCP через A.
- SOCKS/UDP завершился таймаутом, код прогона — `12`. Журналы подтверждают вход UDP-пакета в VLESS A, но локальный UDP-ответчик пользовательского маркера не получил. До остановки выхода, переключения на B, восстановления A и проверки состояния «все выходы выключены» сценарий не дошёл.
- Перед запуском и после него SHA-256 IPv4 routes и IPv4/IPv6 rules совпали. Хеш `/proc/net/ipv6_route` различался между чтениями; сырая таблица не сохранялась, причина расхождения не установлена. Поэтому неизменность IPv6 routes по этой попытке не подтверждена.
- SSH-команда завершилась кодом 12. Trap остановил собственные процессы; последующее чтение уже существовавших логов завершилось кодом 0 и удалило только каталог этой попытки.

Полные локальные выводы: [`attempt-01-stdout.txt`](evidence/attempt-01-stdout.txt), [`attempt-01-stderr.txt`](evidence/attempt-01-stderr.txt), [`attempt-01-device-logs-filtered.txt`](evidence/attempt-01-device-logs-filtered.txt), [`attempt-01-log-retrieval-cleanup.txt`](evidence/attempt-01-log-retrieval-cleanup.txt). Host key при SSH был проверен строго; fingerprint — `SHA256:u5mFSUOHtvmfjURyMmAe8N2BVONvSiTAoV7OLn2Czoo`.

## Вывод и ограничения

Подтверждён только автоматический выбор A в исходном состоянии на одном Keenetic с loopback VLESS-выходами и локальным HTTP health-check. Это фактическая работа sing-box `urltest`, а не переключение, инициированное контроллером. Сбой UDP относится к тестовой конфигурации/пути, но точную причину первая попытка не установила. В текущем прототипе подготовлена непроверенная коррекция атрибуции через разные loopback source address (`127.0.0.1`, `127.0.0.2`); применять её результат как свидетельство нельзя.

Не подтверждены автоматический переход A→B, автоматическое возвращение на A, передача UDP-маркеров через выбранный выход и fail-closed при отказе обоих. Также не проверялись клиентский транзит, внешние VPN-серверы, WAN, производительность и политика Hestia. Прототип не является рекомендацией применять `urltest` как production-политику: URLTest выбирает по скорости конкретного контрольного URL; сопоставление таких измерений с независимыми критериями доступности и качеством пользовательских целей этим опытом не исследовалось.

Для продолжения потребуется отдельное решение владельца о возобновлении аппаратных прогонов. При объединении исследований обнаружено отсутствие комментариев перед функциями исторического `attempt-01-run.sh`. Его точные байты сохранены как текстовое свидетельство [attempt-01-run.sh.txt](evidence/attempt-01-run.sh.txt), включая [копию снимка](evidence/attempt-01/input-snapshot/attempt-01-run.sh.txt); содержимое и SHA-256 не менялись. Старые имена в командах и манифестах относятся к файлу на момент выполнения. Это архив неудачной попытки, а не поддерживаемый сценарий повторного запуска.

Контракты функций архивного сценария: `route_hashes` выводит хеши прочитанных маршрутов и правил; `ports_free` возвращает ненулевой код при обнаружении зарезервированного порта в таблицах сокетов; `cleanup` завершает и ожидает только записанные дочерние PID; `start_a` запускает собственный сервер A, сохраняет его PID и направляет журнал в файл. Ограничения способа проверки портов и `/proc`-хешей сохраняются вместе с результатом попытки.
