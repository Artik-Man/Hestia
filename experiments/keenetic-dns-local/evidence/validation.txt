# Независимая проверка свидетельств локального DNS

Проверяющий: Evidence2 (тестировщик). Проверены сохранённые свидетельства и локальная сборка; к роутеру и ВМ не подключался. Дата проверки: 6 ноября 2026 года.

## Финальный помощник и результаты второго прогона

- Хеши финальных локальных файлов совпадают с `final-artifact-sha256.txt`: исходник `dns-local.go` — `ba63801d1ec0e9b632dd74c18fb7379991c7748748caf13a72d8ebb7bafc5d99`; конфигурация `singbox-dns.json` — `367943b591400647d8ae03b969a9fbb7beed69cc276f394e6fdc3d2690e55419`; скрипт — `40504d9679259233bc510cd5ca25305abc30a57866440ba9f85e4eb37c9d5345`.
- Повторные `gofmt -d` и `GOTOOLCHAIN=local GOPROXY=off go vet ./experiments/keenetic-dns-local/prototype/dns-local.go` прошли без диагностики. Повторная статическая сборка Linux/ARM64 завершилась с SHA-256 `ac6b7710622310c7787a84d324a113978d81e2522922e900d20c59b228078faf`; хеш совпадает с `run-2/router-validation.txt`. `bash -n` для сценария также завершился с кодом 0.
- Финальная конфигурация отправляет DNS upstream только на `127.0.0.1:19250` (UDP и TCP), принимает запросы на `127.0.0.1:19251`, выбирает transport-specific upstream и включает `route.default_domain_resolver: synthetic-udp`. Её SHA в локальном файле совпадает с `router-validation-retry.txt`, где указан exit 0.
- У второго прогона есть отдельная удалённая проверка helper SHA, но нет отдельного remote SHA snapshot конфигурации или sing-box в его каталоге. Итоговый конфиг с SHA `3679…` был удалённо проверен в retry-записи и согласуется с run-2 log; сохранённая retry-запись не содержит команды/времени, связывающих её однозначно с моментом старта второго процесса. Sing-box SHA закреплён в общей проверке передачи и в предыдущем протоколе provenance, не снят заново в run 2.
- Во втором прогоне четыре записи `probe.log` подтверждают ответы UDP/TCP: A для `answer.dns-local.test.` с `192.0.2.42` и NXDOMAIN для `missing.dns-local.test.`. Логи содержат разные transaction ID; sing-box показывает DNS hijack и соответствующий UDP/TCP route. Ответчик получил две UDP пробы и три TCP запроса: дополнительный TCP A с upstream ID `1` не имеет соответствующей входящей операции в sing-box. Его источник не установлен; он остаётся отдельным наблюдением.
- Второй прогон показывает exit 0, завершение собственных процессов, отсутствие изменений четырёх хешей routes/rules. Итоговая cleanup-запись подтверждает отсутствие всех четырёх PID, закрытие обоих портов и удаление временного каталога.
- Hash-verified sing-box ELF `d953af885f11d6b547c21a3c0ffe70796963afc802fab959d548311002b4908a` и закреплённый архивный SHA `436441f76ee2f7fe21b5b2d426d3cb261a480455a704865789ad533e4273ec26` согласуются с предыдущим протоколом происхождения sing-box 1.14.4.

## Неустранённая неоднозначность первого прогона

- Первоначальные строки `run-1-artifacts.txt` присваивали первому успешному прогону конфигурацию SHA `51ca1a884cee9b51cf9b4ea6198c0b78dfc434180ed00bf61d12f34c9eccfa99`. Тот же SHA в `router-validation.txt` получил exit 1 с ошибкой отсутствующего `route.default_domain_resolver`, тогда как `run-1-sing-box.log` и `run-1-probe.log` показывают запущенный sing-box и успешные ответы.
- После проверки автор добавил erratum в `run-1-artifacts.txt` и README: прежний digest attribution признан ошибочным; `router-validation-retry.txt` подтверждает успешный check финальной конфигурации SHA `367943b5…55419`, вероятно применённой до run 1. Эта оговорка корректно оставляет точную конфигурацию в момент запуска недоказанной. Сохранённый `transfer-commands.txt` содержит только одну команду `scp` с конфигурацией, помощником и sing-box; нет команды повторной передачи исправленного файла или at-run config hash. Retry-файл содержит хеш/exit, но не команду/время. Поэтому SHA `3679…` для run 1 остаётся хронологическим выводом, не непосредственно подтверждённой идентичностью.
- Первый прогон использовал helper SHA `87e84a34e98ecbc99a81f53710a96c492d75e3f4737f944a6d3e6dc6896af482`; сохранённый ранний source hash — `c9c41d5e8e28c9b6d72ac55b35eaaa9c8860c5aefd59d0f6e556e83981652205`. Самого раннего исходника в текущем prototype нет, и его сборку невозможно повторить. Финальный helper/source — другая версия, с дополнительным transaction ID/counter logging; её сборка совпадает со вторым прогоном.
- Следовательно, второе испытание подтверждено как наиболее воспроизводимое. Материалы первого прогона содержат успешные наблюдения, но его конфигурационная идентичность противоречива, а helper source не сохранён. Не следует считать два запуска проверенными на одной и той же версии артефактов.

## Форма и границы доказательств

Раздельные probe, responder и sing-box логи сохраняют наблюдения; интерфейсные и шлюзовые строки sing-box заменены на маркеры редактирования. Route/rule представлены только хешами, поэтому можно проверить совпадение снимков, но нельзя независимо изучить их исходное содержимое. `router-execution*.txt` — выборочные статусные записи, а не полный неизменённый stdout/stderr удалённой команды с UTC-временными рамками. Повторного аппаратного прогона не проводил.

Результат ограничен локальным sing-box DNS на одной KN-1012 и синтетическим upstream на loopback. Системный DNS Keenetic, клиенты, порт 53, внешний DNS, VPN, IPv6 DNS и эксплуатационная готовность не проверены. Дополнительный TCP-запрос ответчика не приписан коду или процессу без доказательства.

## Локальные проверки

```sh
shasum -a 256 experiments/keenetic-dns-local/prototype/dns-local.go \
  experiments/keenetic-dns-local/prototype/singbox-dns.json \
  experiments/keenetic-dns-local/prototype/run-dns-study.sh
gofmt -d experiments/keenetic-dns-local/prototype/dns-local.go
GOTOOLCHAIN=local GOPROXY=off go vet ./experiments/keenetic-dns-local/prototype/dns-local.go
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 GOTOOLCHAIN=local GOPROXY=off \
  go build -trimpath -buildvcs=false \
  -o /private/tmp/hestia-dns-local-helper-validation \
  experiments/keenetic-dns-local/prototype/dns-local.go
bash -n experiments/keenetic-dns-local/prototype/run-dns-study.sh
```

## Итог

Локальная финальная сборка, второй прогон и его основные сетевые ответы согласуются. Сохранённые материалы не позволяют подтвердить, что первый прогон использовал конфигурацию, заявленную в его артефактной записи, или восстановить его точный helper. Перед использованием вывода «два успешных прогона» оставшуюся неопределённость run 1 нужно сохранить в отчёте и матрице.
