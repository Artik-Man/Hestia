# Локальный DNS sing-box на Keenetic Giga KN-1012

## Вопрос и критерии

Проверяет, может ли закреплённый sing-box 1.14.4 на конкретной KN-1012 принимать DNS по UDP и TCP на loopback высоком порту, передавать запросы только собственному синтетическому loopback DNS-ответчику и возвращать проверяемые ответы. Критерии второго цикла из [спецификации диагностики Keenetic](../../docs/features/keenetic-diagnostics.md#второй-цикл-локальных-исследований-runtime): A и NXDOMAIN для `.test` через оба транспорта, проверка идентификатора и содержимого, собственные ответчик и sing-box на loopback, без системного DNS и клиентского перехвата.

## Среда и границы

- Устройство: Keenetic Giga KN-1012, ARM64, KeeneticOS 5.2 Beta 2; ядро `4.9-ndm-5`. Версия sing-box: `1.14.4`; запуск через уже установленный `/opt/lib/ld-linux-aarch64.so.1` и `/opt/lib`.
- Дата: 6 ноября 2026 года; аппаратные прогоны — около 18:31 и 18:33 UTC.
- Архив sing-box SHA-256 `436441f76ee2f7fe21b5b2d426d3cb261a480455a704865789ad533e4273ec26`; локально проверены имена всех записей архива, на устройство перенесён только ELF с SHA-256 `d953af885f11d6b547c21a3c0ffe70796963afc802fab959d548311002b4908a`.
- SSH host key сверялся с существующей записью `known_hosts` при `StrictHostKeyChecking=yes`; отпечаток и настройки — [свидетельство](evidence/host-key.txt). После передачи проверены SHA-256 ELF, helper и конфигурации на устройстве.
- Прототип использовал только `127.0.0.1:19250` (UDP/TCP ответчик) и `127.0.0.1:19251` (sing-box direct inbound). В конфигурации DNS upstream адресом задан `127.0.0.1:19250`; других DNS-серверов нет, финальный upstream — тот же синтетический UDP endpoint. Запрашивались только `answer.dns-local.test.` и `missing.dns-local.test.`. A ответ содержал TEST-NET-1 адрес `192.0.2.42`; второго имени ответчик отвечал NXDOMAIN.
- Не менялись системный DNS, службы, постоянные файлы, маршруты, правила, firewall, VPN и пакеты. ВМ не использовались. Маршруты и правила сохранялись только как SHA-256; исходные записи таблиц не собирались.

## Фактический результат

Оба запуска завершились с кодом 0. Однако run 1 имеет пробел в идентификации конфигурации: SHA `51ca1a88…` относится к сохранённой неуспешной проверке, а `run-1-artifacts.txt` ошибочно приписывает его успешному прогону. Повторная проверка перед run 1 сохранила remote SHA `367943b5…` и код 0, но передача исправленного файла в сохранённом журнале команд не зафиксирована, а хеш конфигурации в момент старта не снимался. Поэтому применение SHA `367943b5…` в run 1 — правдоподобно, но не доказано; сохранённые сведения не позволяют окончательно разрешить противоречие. Приёмка опирается только на run 2: его успешная проверка и remote SHA конфигурации `367943b591400647d8ae03b969a9fbb7beed69cc276f394e6fdc3d2690e55419` сохранены непосредственно перед прогоном. Run 1 оставлен как дополнительное наблюдение с неразрешённым конфликтом, а не как подтверждённый повтор. SHA `51ca…` не относится к проверенной конфигурации run 2. В сохранённом вызове нет явной установки `ENABLE_DEPRECATED_MISSING_DOMAIN_RESOLVER`; удалённое окружение отдельно не проверялось.

В sing-box были открыты TCP и UDP сокеты только на `127.0.0.1:19251`; его route rule направляло DNS inbound в `hijack-dns`, а DNS rules выбирали отдельные UDP- и TCP-upstream для соответствующего транспорта. Ответчик слушал `127.0.0.1:19250` по обоим транспортам.

Проба отправляла через sing-box четыре независимых запроса: A для `answer.dns-local.test.` и A для `missing.dns-local.test.` по UDP и TCP. Каждый ответ проверял transaction ID, имя вопроса, тип A, класс IN, RCODE, число ответов и IPv4 тело. Во втором прогоне прошли все четыре проверки: для `answer.dns-local.test.` получен NOERROR и `192.0.2.42`; для `missing.dns-local.test.` получен NXDOMAIN с нулём ответов. Записи run 1 тоже содержат успешные ответы, но их нельзя считать независимым подтверждённым повтором из-за конфигурационной неопределённости. См. [пробу второго прогона](evidence/run-2/probe.log), [журнал sing-box](evidence/run-2/sing-box.log) и [независимую проверку свидетельств](evidence/validation.txt).

Между прогонами helper был изменён: добавлена запись идентификаторов запросов для разбора счётчиков. Хеши исходника и ELF каждого прогона сохранены в свидетельствах; в `prototype/` оставлена финальная версия второго прогона. Поэтому воспроизводимость из сохранённого исходника относится ко второму прогону; первый подтверждается сохранёнными наблюдениями, а его исходная версия отдельно не сохранена.

Счётчики ответчика во втором прогоне: UDP — 2 запроса (один A, один NXDOMAIN); TCP — 3 запроса (два A, один NXDOMAIN). Sing-box залогировал две входящие TCP DNS-операции — A и NXDOMAIN, но ответчик получил ещё одну TCP A-операцию с upstream ID `1`, до запроса probe с ID `15740`; такую же разницу TCP=3 наблюдали и в первом прогоне. Отдельной соответствующей входящей записи sing-box нет. Точный источник этого дополнительного локального запроса не установлен, поэтому счётчик отражён как наблюдение и не приписан ни клиентской пробе, ни sing-box. Это не помешало проверенным ответам, однако атрибуция полного TCP-счётчика остаётся ограничением.

Хеши IPv4/IPv6 routes и rules совпали до и после каждого прогона: `d980f9b05b97eae098407214e104b6a23a3a823ad1aa5ba3aaa5419a3a60c619`, `52a656ed73f1a2c72f79a91fcd6f7cbe5bc59a1b33d5a89fb4e64cfac61c5b9c`, `208c4cc100e02e620c4114c9062d7102ecc09d30e48bac2552e326f6db5de910`, `77570d3b73b6f8265509d05ee2d03df846fd2f2d9f537a0dc58e0cb0739b1aaf`. Результаты записаны в [свидетельствах прогона 1](evidence/run-1-route-rule-hashes.txt) и [прогона 2](evidence/run-2/route-rule-hashes.txt).

После каждого запуска процессы завершались по сохранённым PID. В конце дополнительно подтверждены выход четырёх зарегистрированных PID, отсутствие слушателей на 19250/19251 и удаление только принадлежащего опыту каталога `/opt/tmp/hestia-dns-local.20261106-9f4c3d`; см. [очистку](evidence/cleanup.txt). Хеш-снимки маршрутов и правил не обнаружили изменений, но не исключают прочие кратковременные воздействия.

## Ошибки и их обработка

Первая команда `sing-box check` вернула код 1: sing-box 1.14.4 запросил `route.default_domain_resolver` или `domain_resolver`. Это сохранено в [первом протоколе проверки](evidence/router-validation.txt). После сверки с официальным [описанием Route](https://sing-box.sagernet.org/configuration/route/) и [UDP DNS сервера](https://sing-box.sagernet.org/configuration/dns/server/udp/) конфигурация получила `route.default_domain_resolver: synthetic-udp`. Повторная проверка завершилась с кодом 0; run 2 напрямую подтверждён на этой конфигурации. Независимая сверка свидетельств зафиксировала противоречие run 1 и поддерживает приёмку только run 2: [заключение проверяющего](evidence/validation.txt). Для run 1 атрибуция исправленной конфигурации основана только на неполной хронологии и остаётся недоказанной. Исправленная конфигурация содержит только числовой loopback upstream.

## Воспроизведение

Статический Linux/ARM64 helper собран локально Go 1.27.3; `gofmt`, `go vet` и `go build` прошли. Команды и результат сборки указаны в [Go-сборке](evidence/go-build.txt), [передаче](evidence/transfer-commands.txt), [команде аппаратного запуска](evidence/router-execution-command.txt) и [скрипте запуска](prototype/run-dns-study.sh). Для точного повтора нужна та же проверенная KN-1012, существующий SSH host key и loader. Перед повтором выберите новый приватный каталог и проверьте доступность выделенных портов. Скрипт запуска использует собственный watchdog на 75 секунд, сохраняет только хеши маршрутов/правил и завершает только созданные им PID.

Конфигурационный формат и действие `hijack-dns` сверены с первичной документацией sing-box: [DNS server](https://sing-box.sagernet.org/configuration/dns/server/), [DNS rule action](https://sing-box.sagernet.org/configuration/dns/rule_action/), [Direct inbound](https://sing-box.sagernet.org/configuration/inbound/direct/) и [Route](https://sing-box.sagernet.org/configuration/route/).

## Границы вывода

Подтверждена работа указанной версии sing-box и конкретной конфигурации для локальных UDP/TCP запросов на KN-1012 при собственной synthetic DNS endpoint. Не проверялись DNS системной службы Keenetic, DNS клиентов, порт 53, перехват клиентского трафика, DHCP, публичные резолверы, DNS за VPN, IPv6 DNS, производительность, эксплуатационная готовность, отказоустойчивость и поведение при перезапуске. Результат не подтверждает интеграцию Гестии с DNS Keenetic или работу резолвера вне этих двух loopback-портов.

Дополнительная граница свидетельств: для второго запуска отдельно сохранён хеш helper, но нет отдельной записи хешей удалённых sing-box и конфигурации непосредственно перед этим запуском. Финальный хеш конфигурации проверен в `router-validation-retry.txt`; эта запись не содержит времени и полной команды. Поэтому привязка именно этих входов к моменту второго запуска опирается на последовательность опыта и соответствующий журнал, а не на единый атомарный манифест запуска.

После аппаратного прогона shell-сценарий приведён к проектному оформлению shfmt 3.11.0 (`-i 4 -ci`); ShellCheck 0.11.0 прошёл. Изменены только пробелы и отступы. Точная предшествующая версия сохранена в [снимке исполненного сценария](evidence/run-dns-study-executed.sh.txt), SHA-256 `40504d9679259233bc510cd5ca25305abc30a57866440ba9f85e4eb37c9d5345`; текущая отформатированная версия имеет SHA-256 `02b84aab7c76a93b5555a539e257aa8d168f1a38fae27b249bae7e8bd6968b61`.
