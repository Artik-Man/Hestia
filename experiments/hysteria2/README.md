# Трафик через выход Hysteria 2

Исходники проверки: [tests/lab/hysteria2](../../tests/lab/hysteria2/). Отчёт и свидетельства остаются здесь. Перед повторным запуском применяйте [правила выбора стенда](../../docs/virtual-machines.md); исторические имена ВМ не являются указанием создать или запустить их.

Имена ВМ в описании приведены к принятой 6 ноября 2026 года схеме [prod/dev/client](../../AGENTS.md#виртуальные-машины). Исходные имена в свидетельствах и путях резервных копий сохранены.

Проверяли, получает ли узел назначения TCP и UDP от VPN-сервера и может ли клиент уйти напрямую после отказа туннеля. Испытывали рабочую копию на базе cd3ebac с изменениями Hysteria 2 от 5 ноября 2026 года. Стенд разработки — ARM64 Lima hestia-dev, sing-box 1.14.4.

На load1 четыре сетевых пространства имён соединены veth: клиент, шлюз, сервер и приёмник. Тестовый TLS-сертификат создаётся на каждый прогон. Сначала клиент обращается к приёмнику напрямую. Затем шлюз передаёт эти же запросы в TUN с выходом из конфигурации, сгенерированной компилятором Гестии. Завершающий шаг останавливает сервер, сохраняя прямой маршрут.

Ожидали разные адреса источника для прямого пути и туннеля и блокировку после остановки. В [результате испытания](evidence/load1.txt) обе пробы сначала пришли от 192.0.2.1, затем от 198.51.100.1. После отказа обе заблокированы. Этот прогон проверяет путь трафика, но сам по себе не проверяет импорт профиля через панель или выбор резервного выхода контроллером.

Для повторения разместите рабочую копию в гостевой системе и из её корня выполните:

```bash
sudo env SING_BOX=/путь/к/sing-box bash tests/lab/hysteria2/lab.sh
```

## Переключение на разрешённый резерв

Второй прогон на той же изолированной ВМ и рабочей копии проверяет выбор резерва работающим контроллером Гестии. Группа содержит Hysteria 2 и физический выход. В начале физический выход административно недоступен для группы. Проверка готовности туннеля получает DNS-ответ от тестового узла внутри сетевого пространства сервера. Дополнительные измерения качества выключены. Контроллер работает в отдельном пространстве монтирования с временными файлами настроек и состояния.

Ожидали, что контроллер подтвердит выход через туннель и, после разрешения резерва и остановки сервера, выберет физическое подключение. По [журналу прогона](evidence/load1-watch.txt) контроллер подтвердил оба выбора. Приёмник видел TCP и UDP с адреса сервера 198.51.100.1 через туннель и с адреса шлюза 203.0.113.1 через резерв. Проверка относится к IPv4 и последовательным новым соединениям.

Для воспроизведения на гостевой системе укажите абсолютный путь к Linux ARM64 сборке контроллера из той же рабочей копии:

```bash
sudo env SING_BOX=/путь/к/sing-box HESTIA_WATCH=/путь/к/hestia bash tests/lab/hysteria2/lab.sh
```

## «Подключаться через» и отказ внешнего UDP

На load1 проверили рабочую копию на базе cd3ebac с Linux ARM64 контроллером. В ручном списке первым стоял физический интерфейс, вторым — отдельный туннель Hysteria 2 через другой интерфейс. Правила фильтра блокировали внешний QUIC выбранного пути. Клиент открывал новые IPv4 TCP- и UDP-соединения к приёмнику после каждого переключения.

Ожидаемая последовательность полностью воспроизвелась: основной путь, резервный VPN, блокировка обоих протоколов при потере двух путей, восстановление через резерв и возврат на основной. На каждом рабочем пути приёмник видел адрес выхода конечного Hysteria-сервера. Опыт проверяет новые соединения; сохранение открытого сеанса при переключении отдельно не измерялось. [Журнал](evidence/load1-underlays.txt).

```bash
sudo env HESTIA_UNDERLAYS=ordered SING_BOX=/путь/к/sing-box HESTIA_WATCH=/путь/к/hestia bash tests/lab/hysteria2/lab.sh
```

## Повторный прогон 6 ноября 2026 года

На установленной `hestia-dev` проверена модульная сборка на базе `66bb2fa`, SHA-256 `a59e9ae9848f197273441699a1dcd645a3aa21d6dae61cebebacfa83e92cd208`. Локальные клиент, шлюз, QUIC-сервер и приёмник созданы в отдельных namespaces. Простой маршрут и ordered-underlays завершились с кодом 0: TCP/UDP проходили через ожидаемый источник; при отказе обоих транспортов блокировались, затем восстанавливались через резерв и основной путь. [Простой режим](../dev-validation/evidence/network/hysteria-plain.txt), [ordered](../dev-validation/evidence/network/hysteria-ordered.txt).

Watch-сценарий первоначально превысил свой тестовый предел 45 секунд при ожидании физического резерва. В текущем контроллере требуется три неудачных раунда с интервалом 15 секунд плюс длительность readiness-проб, поэтому такой предел меньше допустимого времени обнаружения. Исправлен только bounded timeout помощника до 150 секунд — как у существующей проверки транспорта; условие active/available и отказ по истечении срока сохранены. Повторный прогон прошёл: от подтверждения туннеля до подтверждения физического резерва прошло 50,862 секунды, затем обе пробы пришли от `203.0.113.1`. [Первый отказ](../dev-validation/evidence/network/hysteria-watch-initial-failure.txt), [повтор с UTC-временем](../dev-validation/evidence/network/hysteria-watch.txt). Это подтверждает причину отказа тестового harness; код runtime не менялся.

Команды воспроизведения выше актуальны; общий [runner](../../tests/lab/dev-validation/network.sh) задаёт изоляцию, версии и тайм-аут. [Сводный протокол](../dev-validation/README.md) фиксирует сохранность установленной конфигурации и маршрутов. Настоящие внешние серверы и сохранение уже открытого клиентского сеанса не проверялись.
