# Наблюдение за потерями на ARM64

Два интерфейса одной группы ведут к одному тестовому серверу по разным путям. Клиент идёт через FI1. Сервер выборочно отбрасывает UDP к X на входе первого пути. Второй путь, TCP к X и UDP к Y служат контролем. Проверка сопоставляет уникальные идентификаторы проб с захватами tcpdump на обоих выходах и журналом получателя. Отдельные клиентские соединения и снимки таблиц маршрутизации проверяют, что рекомендация сама не переключает трафик.

В быстром сценарии из 498 проб потерялись 11, все на FI1 для UDP к X. Через 0,90 с после начала потерь измеритель рекомендовал FI2 только для этой пары. После восстановления и истечения старых наблюдений оба выхода показали равное качество, рекомендация осталась FI2. Девять клиентских запросов по-прежнему вышли на FI1. [Протокол проверки](evidence/fast.txt).

При первом запуске возникла гонка между собственным тайм-аутом пробы и закрытием её сокета. Она превращала часть ожидаемых потерь в локальные ошибки. Теперь отмена задачи закрывает сокет немедленно, а истечение срока ожидания ответа регистрируется как потеря. Короткий сценарий и тест с молчащим UDP-сервером прошли на ARM64 после исправления.

На отдельной ВМ установили комплект, включили службу через systemd и получили UDP-ответ в изолированном сетевом пространстве. На проверенном ядре достаточно динамического пользователя с пустым набором capabilities. [Журнал службы](evidence/systemd.txt).

## Реальное окно 60 минут

Часовой прогон на Debian ARM64 занял 3815,02 с (1 ч 3 мин 35 с). За 764 раунда проверены все 4584 пробы на двух выходах. При внесённых потерях 12 проб UDP до X не получили ответа через FI1. Через FI2, по TCP до X и по UDP до Y потерь проб не было. Наблюдатель один раз рекомендовал FI2 для UDP до X спустя 14,94 с после включения потерь. В конце в часовом окне оба пути вернули по 721 из 721 проб до X, рекомендация осталась FI2.

Все девять контрольных запросов от клиента пошли через FI1. Счётчик фильтра зарегистрировал 13 отброшенных датаграмм: 12 измерительных и одну контрольную. Захваты на обоих интерфейсах завершились с нулевыми потерями при записи, а снимки маршрутов и правил совпали. Этот опыт проверял срок хранения реальных наблюдений и рекомендации без изменения маршрутов. [Протокол](evidence/hour.txt) · [Конфигурация](evidence/hour-config.json).

## Воспроизведение

На машине сборки в корне проекта выполните `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -o hestia ./cmd/hestia`. Передайте бинарник и каталог `experiments/observer` в одноразовую Debian ARM64-ВМ. В госте требуются Python 3, iproute2, iptables и tcpdump. Каталоги результатов должны быть пустыми.

```sh
sudo bash experiments/observer/lab.sh ./hestia fast /var/tmp/hestia-fast
sudo bash experiments/observer/lab.sh ./hestia hour /var/tmp/hestia-hour
```

Часовой сценарий использует интервал 5 секунд и ожидает завершения 764 реальных раундов. Он записывает пробы и захваты в указанный каталог, затем проверяет исчезновение начальных потерь за пределами окна. Порог преимущества для обоих испытаний составляет 15 процентных пунктов при минимуме 6 пар. Это параметры стенда.
