# Правила ведения документации

Документируй проект по-русски, поддерживай различие между требованиями, планами, подтверждёнными решениями и фактически проверенным поведением. Пиши для аудитории конкретного документа: README проекта предназначен для людей, AGENTS — для агентов, а тематические документы — для пользователей и участников разработки.

## Назначение файлов верхнего уровня

- `README.md` — описание продукта и его целевых функциональных возможностей для людей. Ссылайся из него на `DOCUMENTATION.md`; не превращай README в инструкцию для агентов или подробный каталог документов.
- `AGENTS.md` — инструкции, обязательные для агентов при работе в репозитории. Здесь также находится короткая карта исходников и рабочих каталогов. Подробные ролевые инструкции и правила размещай в `agents/` и ссылайся на них.
- `DOCUMENTATION.md` — короткий корневой индекс основных документированных областей проекта. Он ссылается на входные README каталогов с продуктовой документацией, исходниками, установкой, проверками, инструкциями агентам и отчётами экспериментов.

## Размещение материалов

- `agents/` — инструкции агентам и правила работы, специфичные для этого репозитория: ролевые профили, Bash style guide, правила виртуальных машин и эти правила ведения документации. Оглавление каталога — `agents/README.md`.
- `experiments/` — описания экспериментов, протоколы запусков, результаты и свидетельства. Для значимого прогона обновляй `experiments/<опыт>/README.md`.
- `docs/` — документация о продукте: требования, функции, архитектура, UX, дорожные карты и планы проверок. Оглавление — `docs/README.md`.
- Код и конфигурации лабораторных проверок остаются в `tests/lab/`; общие сценарии сборки, проверки, установки и проверки установленной версии — в `scripts/`; установка и конфигурации служб — в `deploy/`. Их README описывают соответствующие каталоги и процессы.

Не дублируй полные оглавления в корневых файлах. Корневой `DOCUMENTATION.md` ведёт к входным README основных областей; каждое такое README связывает документы и дочерние каталоги своей области. При создании, переносе, переименовании или удалении документа обновляй ссылки и оглавление соответствующей области.

## Требования к содержанию

- Начинай с того, что читателю нужно узнать или сделать. Используй точные названия продукта и сущностей, воспроизводи команды, пути, параметры и ключи API без изменений.
- В спецификации функции фиксируй ожидаемое поведение, границы и проверяемые критерии приёмки. До реализации согласуй их с Product Owner. Отмечай, что является подтверждённым требованием, предложением, планом или открытым вопросом.
- Вместе с изменением поведения обновляй затронутые спецификации, инструкции, примеры и ссылки. Сверяй фактические утверждения с кодом и результатами проверок; не выдавай запланированное за реализованное.
- В отчёте эксперимента указывай вопрос, проверенную среду и версию кода, условия, ожидаемый и фактический результаты, ошибки, границы вывода и команды воспроизведения. Связывай выводы с материалами в `evidence/` и отражай статус в дорожной карте. Незавершённый прогон описывай только по уже наблюдавшимся данным.
- Исследования Keenetic, KeeneticOS/Entware, документации производителя и решений конкурентов объединяй в `docs/keenetic-platform.md`; отдельные отчёты конкретных прогонов и их свидетельства размещай в `experiments/`.
- Документируй каждую именованную функцию и метод, включая приватные функции, тесты и вспомогательные функции стенда. Описывай назначение и контракт: гарантируемый результат, а где важно — входы, побочные эффекты и условия отказа. Для Go ставь Go doc перед объявлением и начинай с имени функции; в Python используй docstring, в shell — комментарий перед функцией. Документируй классы Python. `make docs-check` проверяет наличие комментариев, ревьюер — их соответствие поведению.

## Язык и аудитория

Проектную документацию и результаты для Product Owner веди на русском. Внутреннюю переписку и checkpoint исполнителей веди на английском. Технические документы должны быть понятны своей аудитории, содержать необходимые ссылки и явно обозначать ограничения выводов.
