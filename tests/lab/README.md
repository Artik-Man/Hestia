# Проверки и инструменты стенда

Каталог содержит модульные тесты, анализаторы сохранённых захватов и сценарии изолированных сетевых испытаний. Отчёты и свидетельства находятся отдельно в [experiments](../../experiments/README.md). Имена каталогов совпадают с именами опытов. Python-прототипы DNS и выбора выхода служат тестовыми моделями; это не исходники служб установленной Гестии.

## Автоматические проверки

Нужны Python 3.11 или новее и закреплённый wheel dnspython:

```sh
python3 -m venv /tmp/hestia-lab-tests
. /tmp/hestia-lab-tests/bin/activate
python -m pip install --require-hashes --only-binary=:all: -r tests/lab/requirements-test.txt
make test-lab
```

Команда запускает все `test_*.py` в этом дереве через стандартный `unittest` отдельными процессами из каталогов тестов. Так одноимённые модули `cache.py` не смешиваются. Отсутствие тестовых модулей, пустой набор, ошибка импорта или провал проверки завершают запуск с ненулевым кодом. `make test-experiments` сохранён как совместимый псевдоним.

Проверяются пять наборов: ротация DNS, stale-if-error, прогрев DNS, анализ маршрутов после перезапуска DNS и политика частичных потерь. Их общие модули находятся в соседних каталогах `dns-geo`, `dns-split-warm` и других; переносить отдельный тест без его зависимостей нельзя.

`make check` включает эти тесты, тесты установщика и Go, проверку документации функций, shfmt и ShellCheck. Bash проверяется в `deploy/` и `tests/lab/`. CI устанавливает зависимости из этого каталога и выполняет те же команды. Версии shell-инструментов указаны в [правилах проекта](../../AGENTS.md).

## Ручные и сетевые проверки

Наличие `verify.py` не означает, что он безопасен для офлайн-запуска: например, `dns-restart/verify.py` анализирует сохранённые пакеты, а `list-binding/verify.py` обращается к работающему API и создаёт соединения. `scheme3/probe.py` также работает с ВМ и внешними сайтами. Эти команды не запускаются автоматически через `make test-lab`.

Перед запуском прочитайте [правила ВМ](../../docs/virtual-machines.md) и отчёт `experiments/<имя>/README.md`. Копируйте исходники с сохранением структуры `tests/lab/` и необходимых `deploy/` и `backend/`. Относительные пути в сценариях рассчитаны на дерево репозитория, если конкретный отчёт не задаёт отдельную упаковку файлов в комплект (например, AWG multi). Команды в отчётах обновлены для нового расположения исходников; версии и наблюдения старых прогонов сохранены.

Для анализа свидетельств путь программы и путь данных различаются, например из корня репозитория:

```sh
python3 -B tests/lab/controller-routing/verify.py experiments/controller-routing/evidence
```

Для нового прогона используйте новый каталог вывода. После проверки добавляйте в отчёт только фактически наблюдавшиеся результаты и сохраняйте относящиеся к ним свидетельства; старые файлы не перезаписывайте.

Запуски разделены: `make test-source` проверяет исходники, `make test-dev` — установленную версию на dev без обновления. Команды и параметры других стендов описаны в [оглавлении сценариев](../../scripts/readme.md). В [dev-validation](dev-validation/README.md) сохранены специальные проверки первоначального изолированного стенда.
