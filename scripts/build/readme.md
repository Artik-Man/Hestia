# Сборка

```sh
make build
# либо явно выбрать каталог:
bash scripts/build/run.sh --output /tmp/hestia-artifacts
```

`run.sh` вызывает `run.py`. Нужны Go согласно `backend/go.mod`, Node/npm согласно `frontend/package.json` и установленные зависимости frontend. Сценарий собирает три приложения (`hestia`, `hestia-panel`, `hestia-observe`) дважды: Linux ARM64 и Keenetic ARM64 с build tag `keenetic`. Панель тоже собирается отдельно для каждой платформы: в `linux-arm64` она показывает версию из `frontend/package.json` с суффиксом `-vm`, а в `keenetic-arm64-experimental` — с суффиксом `-keenetic`. Обычный `npm run build` без конфигурации платформы показывает только базовую версию. Затем сценарий создаёт два комплекта в `dist/artifacts/<версия>/`: `linux-arm64` и `keenetic-arm64-experimental`.

Каждый комплект содержит манифест версии, ревизии, состояния рабочего дерева, Go build tags, хешей исходных входов и файлов поставки. Повторная сборка не перезаписывает существующий комплект. Сборка не подключается к стендам и ничего на них не устанавливает.

Экспериментальный Keenetic-комплект использует отдельные ARM64-бинарники с build tag `keenetic`. Внутри него формируются `/opt` rootfs и `.ipk`: Go-команды, панель, frontend assets, профильный helper, pinned sing-box, default deny managed profile, Entware init script и opkg lifecycle hooks. До распаковки Hestia IPK `preinst` запускает Go helper из control-архива IPK. Helper использует общий `keeneticrci.Client` и требует root-only token `/opt/etc/hestia/keenetic-rci-token` (файл без доступа группы/остальных, родительские каталоги root-owned и не writable ими), затем проверяет read-only RCI `show/version` на точную модель KN-1012 / KeeneticOS 5.2 Beta 3, архитектуру через `/opt/bin/busybox uname`, защищённый `/opt` и минимум 512 MiB свободного места. Совместимость архитектуры пакета проверяет сам Entware `opkg` до запуска `preinst`; hook не запускает вложенный экземпляр менеджера пакетов. IPK устанавливает `python3-light` и `python3-codecs`: второй пакет предоставляет модуль `unicodedata`, который импортирует профильный валидатор. Токен не включается в IPK; его нужно безопасно разместить отдельно до установки. Keenetic IPK содержит статические AWG runtime-компоненты: `amneziawg-go` с выделенным UAPI socket path и `awg-tools`. Keenetic-сборка выбирает Entware runtime, root-only supervisor управляет AWG instance services, а панель включает WireGuard/AmneziaWG и отдельный Hysteria 2 CRUD. Установка IPK, readiness supervisor и ответы LAN API проверены на KN-1012 для версии `20261107-225942-2bf46144bcb4` ([свидетельство](../../experiments/keenetic-ipk-packaging/evidence/install-20261107-225942/check.txt)); создание VPN-профиля, dataplane, ownership, fail-closed и rollback требуют дальнейшей целевой приёмки. Тег выбирает RCI physical connector и Entware пути, не вызывая NetworkManager или systemd. Supervisor включает Go smoke для binding lifecycle, запускает router/controller/panel/AWG instances и следит за binding journal. Пакет сохраняет profile/snapshot/backend как `conffiles`; init сериализует lifecycle-команды атомарным lock, opkg hooks блокируют запуск на время обновления/удаления, readiness подтверждается marker+IPC, а PID marker удаляется только после проверки остановки. Для чтения установленного snapshot пакет создаёт root-only `/opt/var/lock/hestia-install.lock`; отдельный read-only helper инвентаризации позволяет `/api/physical-connections` работать без включения Wi-Fi mutation routes. Эти API проверены на KN-1012 после установки IPK `20261107-123735-f9fea441ebfd` ([отчёт](../../experiments/keenetic-ipk-packaging/README.md#исправление-загрузки-конфигурации-и-инвентаря-подключений)). Если init принудительно завершён и lock остался, нужно подтвердить отсутствие Hestia-процессов и только затем удалить `/opt/var/run/hestia/lifecycle.lock`; автоматической очистки stale lock нет. Обновление не имеет транзакционного rollback. RoutePolicy/dataplane, DNS, Wi-Fi/WISP и полный клиентский путь остаются непроверенными.

Linux-комплект поддерживает первичную установку и обновление. Runtime-зависимости включаются как закреплённые готовые входы: `dist/runtime/sing.tgz`, `dist/runtime/amneziawg-go`, `dist/runtime/awg`; Keenetic IPK дополнительно использует `dist/runtime/amneziawg-go-keenetic`, собранный из того же upstream commit с linker override для выделенного UAPI каталога из [AWG UAPI опыта](../../experiments/keenetic-awg-uapi/README.md). Другой каталог задаётся `--runtime-dir`; SHA-256 всех входов сверяются с `runtime-lock.json` до компиляции. AWG binaries упакованы в `/opt/bin`, а Keenetic supervisor управляет AWG instance runtime через фиксированные роли; проверки маршрутов и жизненного цикла на целевом устройстве ещё не выполнены. При обновлении уже установленные Linux runtime-бинарники сохраняются. Ошибка компиляции или проверки завершается ненулевым кодом. Новый комплект передают отдельно в [deploy](../deploy/readme.md).

В Keenetic IPK init ждёт readiness supervisor до 60 секунд. Supervisor по возможности записывает ошибки старта и работы в `/opt/var/run/hestia/supervisor.log` с правами `0600`; если файл открыть не удаётся, сообщения остаются в stderr процесса. Успешность install hook требует readiness marker и подтверждённые статусы ролей через root-only IPC. Обновление этой логики и LAN API проверены на KN-1012 7 ноября 2026 года ([свидетельство](../../experiments/keenetic-ipk-packaging/evidence/install-20261107-165338/check.txt)).

Панель Keenetic получает отдельные флаги `-enable-hysteria2` и `-enable-awg`; первый включает Hysteria 2 CRUD через профильный helper и sing-box, второй — WireGuard/AmneziaWG CRUD через Entware runtime и управляемую supervisor службу. Целевая проверка добавления профилей, RoutePolicy, TCP/UDP, IPv4/IPv6 и отката на KN-1012 ещё не выполнена; собранный IPK не устанавливался.

## Подготовка runtime-входов

`test_build.py` проверяет отказ публикации при изменении runtime-входов или исходников во время сборки. Отдельный запуск: `python3 -m unittest discover -s scripts/build`; эти проверки также входят в `make test-workflows`.

`sing.tgz` — официальный архив sing-box 1.14.4 Linux ARM64; его SHA совпадает с `deploy/sing-box-1.14.4-linux-arm64.sha256`. Два AWG-бинарника — закреплённые результаты сборки проекта, а не обещание наличия готовых официальных assets. amneziawg-go: тег `v3.1.20260828`, commit `b5928efb6ca19f0153958460c3d141f04abc5c2e`, Go 1.27.3, `GOOS=linux GOARCH=arm64 CGO_ENABLED=0 GOFLAGS='-trimpath -buildvcs=false' make generate-version-and-build`. awg-tools: тег `v3.1.20260812`, commit `ee0f0a9aa34ff0a0da4b3433b9512781cfe02843`, `make -C src` на Debian ARM64 с GCC `12.2.0-14+deb12u1`; результат `src/wg` сохранён как `awg`.

Для текущего закреплённого комплекта использованы проверенные байты из dev: версия и хеши зафиксированы в [свидетельстве установки](../../experiments/dev-validation/evidence/deployment.txt). Каталог `dist/runtime` не хранится в Git. Его можно восстановить из доверенного предыдущего комплекта с теми же хешами либо воспроизвести сборку в соответствующем toolchain. Различие хешей после самостоятельной сборки требует отдельной проверки и обновления lock-файла; сценарий не принимает его молча. На macOS для самостоятельной C-сборки нужен ARM64 Linux cross-toolchain, либо отдельная заранее подготовленная сборочная среда; `make build` не использует стенд как сборочную машину.

## Отдельная компиляционная проверка CI

`make build-go` вызывает `run.py --check-go --output dist/go` и компилирует прикладные команды и preflight для Linux/Keenetic build tags, а также отдельные Ethernet, interface-schema и Wi-Fi survey-schema RCI research-команды. Research-бинарники остаются в проверочной папке и не включаются в продуктовый комплект. Для компиляции не нужны npm и runtime-входы; это не запуск эксперимента. CI отдельно собирает frontend в своей задаче; сборка полного двухплатформенного комплекта требует доверенных runtime-входов.

Сборка включает генерируемый Angular файл `3rdpartylicenses.txt` в `browser/`. При установке он попадает в `/usr/local/share/hestia-panel/current/3rdpartylicenses.txt` вместе с остальными файлами панели. `test_build.py` проверяет сохранение уведомления, независимость CI-компиляции и отказ при изменении runtime/исходников во время упаковки.
