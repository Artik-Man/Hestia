# Проверки установленной версии

```sh
python3 scripts/test/run.py --stand scripts/shared/stands/dev.json
python3 scripts/test/run.py --stand /путь/мой-стенд.json --output /путь/новый-отчёт
```

Сценарий принимает явное [описание стенда](../shared/readme.md), проверяет идентичность и Linux ARM64, затем копирует установленные бинарники и установленный `profile.py` в приватный каталог прогона. Приложение не собирается и не обновляется; отдельно компилируется только измерительный помощник лаборатории качества. Питание ВМ не меняется. Агентам для доступа к prod или роутеру по-прежнему нужно отдельное разрешение владельца.

Живой REST API проверяется только GET-запросами без вывода содержимого ответов. CRUD панели, DNS, качество, переключения AWG/WireGuard/Hysteria и контроллер проверяются с копиями установленной версии в изолированных пространствах имён и временных конфигурациях. Копия компилятора профиля также берётся с проверяемого стенда. Исторический `partial-loss` — отдельный прототип, что явно отмечается в `scope.json`; его результат не выдаётся за поведение установленного контроллера.

`guest.sh` управляет фазами `prepare`, `acceptance`, `network`, `final`; `network.sh` запускает отдельный сетевой сценарий и требует подтверждённое ожидаемое имя хоста. Только внутри приватного UTS-пространства используется совместимое имя `lima-hestia-dev` для прежних лабораторных проверок. Настоящая идентичность стенда сохраняется в отчёте. `read_only.py` проверяет доступность API на стандартном loopback-порту 8080 либо по `panel_url` из описания стенда. Разрешён только HTTP с буквальным IP, принадлежащим loopback или локальному интерфейсу выбранного стенда; DNS-имена, credentials, proxy и переадресации запрещены.

Нужны root/sudo, systemd, Linux namespaces/TUN, Python с dnspython, iproute2, iptables, tcpdump, openssl, curl, timeout, unshare; на машине запуска — Python, Go для измерительного помощника и транспорт Lima/SSH. Поддерживается стандартная структура установки: бинарники в `/usr/local/bin`, runtime в `/usr/local/lib/hestia`, frontend в обычном каталоге `/usr/local/share/hestia-panel/current`. Старые размещения и symlink вместо этого каталога отклоняются до лабораторных тестов; они требуют отдельной адаптации либо нормализации обновлением. Установленные `hestia`, `hestia-panel`, `hestia-observe`, `awg`, `amneziawg-go`, `sing-box` обязательны. Динамическая `libcronet.so`, если установлена рядом с sing-box, копируется и хешируется. Поддержка HTTP/3 проверяется самим тестом.

До и после сравниваются хеши приложения, полный состав каталогов runtime/UI, конфигурация `/etc/hestia`, основные маршруты, policy rules и именованные сетевые пространства. Неподдерживаемые symlink/special-файлы конфигурации отклоняются. Настройки никогда не восстанавливаются поверх параллельных изменений. Отсутствие аппаратного Ethernet даёт явный SKIP и неполное покрытие с ненулевым итогом. Другие отсутствующие обязательные зависимости — FAIL.

При прерывании останавливается только собственная временная служба тестов; после успешной начальной фиксации выполняется итоговая проверка сохранности. Приватные каталоги `/var/tmp/hestia-validation-*` и сетевых сценариев остаются для диагностики. В публичные отчёты экспортируются журналы проверок и хеши бинарников, а не конфигурации или ключи. Общий отчёт находится в новом `experiments/dev-validation/evidence/installed-*`.

Обычный полный сетевой прогон занимает около 10–20 минут на двух виртуальных CPU; при нагрузке дольше. Он создаёт процессы VPN и локальный трафик только в лабораторных пространствах имён, заметно использует CPU, память и несколько сотен мегабайт диска под копии бинарников и захваты. Даже без изменения реальной маршрутизации нагрузку следует учитывать при выборе времени тестирования рабочего стенда. Нужны разрешённые mount/network/PID/UTS namespaces, CAP_SYS_ADMIN/NET_ADMIN, TUN и поддержка фильтрации ядром. Запуск не предназначен для ограниченного контейнера. Удобные алиасы: `make test-dev`, `make test-prod`; произвольный стенд задаётся явным `--stand`.

Комплект лаборатории формируется из отслеживаемых публичных файлов выбранных сценариев и явного списка их общих зависимостей (`failover`, `scoped`, `fakeip`, `observer`, `steer-deny`, шаблон scheme3). Произвольные локальные JSON/ключи не подхватываются. Регрессионный тест проверяет наличие зависимостей всех выбранных сценариев и выполняет относительные импорты/генерацию синтетической конфигурации из уже упакованного дерева до обращения к стенду. Исторический путь Hysteria к `deploy/profile.py` заполняется копией установленного компилятора.
