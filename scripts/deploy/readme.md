# Установка уже собранного комплекта

```sh
make deploy-dev BUNDLE=/absolute/path/linux-arm64
make deploy-prod BUNDLE=/absolute/path/linux-arm64
make deploy STAND=/absolute/path/stand.json BUNDLE=/absolute/path/linux-arm64 TYPE=linux
# эквивалент:
bash scripts/deploy/run.sh --stand scripts/shared/stands/dev.json --bundle /absolute/path/linux-arm64 --type linux
```

`run.sh` вызывает `run.py`, который проверяет манифест, платформу и идентичность [стенда](../shared/readme.md), доставляет комплект и запускает `apply.sh`. Исходники не компилируются. Экспериментальный Keenetic-комплект отклоняется до подключения. ВМ должна быть запущена заранее; питание не меняется.

Поддерживаются первичная установка и обновление существующей управляемой установки Linux ARM64: systemd, Python, util-linux, iproute2, sudo без интерактивного пароля и Debian-совместимое окружение. При первичной установке runtime-зависимости берутся из проверенного комплекта; штатный установщик может установить недостающие базовые пакеты Debian. Неуправляемая или устаревшая singleton-AWG установка отклоняется до изменения приложения. Если `/etc/hestia` отсутствует, вызывается `fresh.sh`: он использует штатный `deploy/install.sh` с готовыми бинарниками, добавляет панель/AWG-службы и локальный пустой профиль. Панель и SOCKS слушают loopback; существующая конфигурация никогда не очищается ради первичной установки. Частичная или чужая установка отклоняется.

При обновлении меняются бинарники приложения, компилятор/проверка профиля и frontend. Настройки и runtime-бинарники сохраняются. В старой управляемой установке может отсутствовать только `hestia-observe`: обновление добавляет его, а откат возвращает прежнее отсутствие. Остальные обязательные файлы и проверки безопасности путей сохраняются. Резервная копия содержит `present.txt` и `absent.txt` с исходным наличием файлов. Активные службы приостанавливаются на время замены; именованные AWG-службы запускаются в прежнем активном состоянии и подтверждают готовность. Резервная копия остаётся в `/var/backups/hestia-deploy.*`. При ошибке обновление восстанавливает предыдущие файлы; если обнаружено конкурентное изменение конфигурации или более новая публикация приложения, разрушительный откат не выполняется и сохраняется диагностика.

Итоговая проверка сверяет конфигурацию, основные маршруты, службы и smoke. Снимки IPv4/IPv6 сохраняются в исходном однострочном формате `ip -o route`; рядом остаются файлы `.canonical` для сравнения. Перестановка разных назначений и прямых IPv6 link-local маршрутов на разных интерфейсах не считается изменением. Порядок маршрутов одного назначения консервативно сохраняется, кроме указанного интерфейсного link-local случая; порядок nexthop внутри записи и все атрибуты остаются значимыми. Ошибка получения или нормализации снимка приводит к отказу и откату. Отчёты лежат в новом каталоге `experiments/dev-validation/evidence/deploy-*` (или `--output`). Ошибка возвращает ненулевой код. Поддержка prod в интерфейсе не разрешает агенту запускать её без отдельного поручения владельца.

`apply.sh`, `fresh.sh` и `default-profile.json` — внутренние части проверенного комплекта, не отдельные команды обхода проверок транспорта. `test_deploy.py` проверяет офлайн отказ экспериментальному комплекту, порядок блокировки отката, отказ при конкурентном изменении и ошибки восстановления: `python3 -m unittest discover -s scripts/deploy`. Эти проверки не заменяют реальный запуск systemd.

## Проверенное поведение

На dev выполнено обновление финальным комплектом, независимо проверены хеши, API, службы и сохранение конфигурации/маршрутов. [Протокол](../../experiments/dev-validation/README.md#проверка-разделённых-команд). Новый путь первой установки проверен ревью и автоматическими тестами отказов/отката, но пока не прошёл полный запуск на новой чистой ВМ. Фактическая доставка проверена через Lima; SSH-транспорт покрыт локальными проверками без внешнего подключения.
