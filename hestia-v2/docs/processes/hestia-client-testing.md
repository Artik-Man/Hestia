# Процесс тестирования с помощью виртуальной машины hestia-client

## Назначение и границы

Используй `hestia-client` для генерации клиентского трафика и проверки его пути через выбранный шлюз. Перед сетевым тестом выбери целевую среду и проверь, куда ведут маршруты клиента. Не направляй тестовый трафик на рабочую Hestia или Keenetic без отдельного разрешения владельца; это ограничение действует и при доступе через `hestia-client`.

Для экспериментов выбирай `hestia-dev`, когда это соответствует сценарию. Не управляй питанием ВМ без учёта общей сети `socket_vmnet`: остановка dev может повлиять на prod и client. Не создавай новую временную ВМ без отдельного разрешения.

## Порядок работы

1. Выбери ВМ по назначению: `hestia-client` используй как клиент тестового трафика, `hestia-dev` — как среду разработки и испытаний.
2. Убедись, что `hestia-client` уже доступна. Указывай её `LIMA_HOME` явно; для текущего стенда подключение выполняется через существующий SSH config и alias `lima-hestia-client`.
3. Перед генерацией трафика зафиксируй адрес источника, маршрут по умолчанию, адрес шлюза и цель проверки. Сверь ожидаемый путь с фактическими маршрутами внутри клиента.
4. Запусти минимальный запрос, который отвечает на вопрос проверки. Для трассировки укажи интерфейс и source port, чтобы сопоставить клиентский поток с наблюдениями на шлюзе.
5. Собери наблюдения на клиенте и шлюзе в одном временном окне. Сопоставляй точные адреса и порты потока; одних близких временных меток недостаточно.
6. После теста проверь, что тестовый трафик завершён, и сохрани команды, среду, версию проверяемого кода, ожидаемый и фактический результат, ошибки и границы вывода.

Перед каждым опытом заново считывай состояние клиента, адреса интерфейсов и маршруты; адреса и состояние из предыдущего запуска не считай постоянными. Не запускай и не останавливай ВМ в рамках сетевой проверки без необходимости и отдельной оценки влияния на общую мостовую сеть.
