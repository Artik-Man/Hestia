## Работа с веткой master

До первого развёртывания кода Гестии на физическом устройстве Product Owner разрешает работать непосредственно в `master`, включая коммиты и push в `origin/master`. С момента первого развёртывания на устройстве действуют общие правила работы в ветках задач. Запуск стенда на виртуальной машине не завершает этот период.

## Роли команды Гестии

Архитектор назначает роли по [общим правилам и каталогу ролей](../ai-dev-practices/AGENTS.md#инструкции-по-ролям). Для задач шлюза используй также два проектных профиля:

| Роль | Когда подключать | Что передаёт команде |
|---|---|---|
| [Инженер по сетям Linux](docs/agent-prompts/linux-network-engineer.md) | Проектирование пути пакета, DNS, VPN, измерение потерь, переключение выходов и диагностика утечек | Схему путей, воспроизводимую сетевую конфигурацию и доказательства фактического выхода или блокировки |
| [Инженер по встраиваемому Linux](docs/agent-prompts/embedded-linux-engineer.md) | Выбор платы и образа, проверка возможностей ядра, первый запуск, испытания портов, нагрузки и восстановления | Матрицу совместимости для конкретной ревизии платы, протокол испытаний и проверенный способ восстановления |

При назначении указывай роль в скобках рядом с именем, например `Routes (Linux Network Engineer)` или `Board (Embedded Linux Engineer)`. Передай исполнителю критерии приёмки, технический контекст и пути к памяти задачи и личному checkpoint. Исполнитель общается с Product Owner через архитектора. Внутреннюю переписку и checkpoint веди на английском, проектную документацию и результаты для Product Owner — на русском. Для исходников и скриптов применяй [общий порядок работы с кодом](../ai-dev-practices/docs/process/code-changes.md). Независимую проверку поведения проводит тестировщик, ревью изменений кода и проверку безопасности выполняют соответствующие общие роли.

## Документация функций

Документируй каждую именованную функцию и метод, включая приватные функции, тесты и вспомогательные функции стенда. Опиши назначение и контракт: какой результат гарантирован, а где важно — входы, побочные эффекты и условия отказа. Для Go ставь Go doc непосредственно перед объявлением, начиная с имени функции; для Python используй docstring, для shell — комментарий перед функцией. Документируй и классы Python. Команда `make docs-check` проверяет наличие документации, а ревьюер сверяет её смысл с поведением кода.

## Форматирование и линтинг кода

Перед передачей изменений на ревью и перед коммитом отформатируй изменённый код и запусти линтер для его языка. Для Go выполни из корня репозитория `make fmt`, затем `make check`. Вторая команда проверяет форматирование, запускает статический анализ `go vet` и тесты. Исправь замечания и повтори проверку до успешного результата.

Для Bash-сценариев в `deploy/`, `tests/lab/` и `scripts/` используй shfmt 3.11.0 и ShellCheck 0.11.0. shfmt отвечает за отступы и единое оформление, ShellCheck находит ошибки раскрытия переменных, передачи аргументов и использования Bash. Подробные правила проекта записаны в [Bash style guide](docs/bash-style-guide.md). Команда `make fmt` форматирует Go и Bash, `make check` проверяет стиль, линтинг и тесты. Эти инструменты нужны на машине разработки и в CI. При установке Гестии на шлюз они не используются.

При создании Angular-фронтенда установи ESLint и Prettier как зависимости разработки (`devDependencies`). Настрой ESLint для TypeScript и Angular-шаблонов, а Prettier — для форматирования исходников, шаблонов и стилей. Добавь в `package.json` команды `lint`, `format` и `format:check`. Перед ревью и коммитом запускай из каталога фронтенда `npm run format` и `npm run lint`. В CI запускай `npm run format:check` и `npm run lint`.

## Структура Angular-компонентов

В корне `frontend/src/` оставляй только файлы `main.ts`, `index.html` и `styles.css`. Изображения храни в `frontend/src/assets/`, сервисы — в `frontend/src/core/services/`.

Каждый Angular-компонент размещай в собственном каталоге вместе с его шаблоном и собственными стилями. Используй общий префикс имени файлов, например `groups.component.ts`, `groups.component.html` и `groups.component.css`. Стили, которые подключают несколько компонентов, размещай в `frontend/src/styles/`. Для компонентов, которые Angular Router открывает через `component` или `loadComponent`, используй `frontend/src/routes/<имя>/`. Для оболочки панели и компонентов, которые подключаются в шаблонах, используй `frontend/src/core/components/<имя>/`. Основное меню панели размещай в `frontend/src/core/components/menu/`.

## Типизация REST API

Источником контракта служат зарегистрированные операции и типизированные структуры Go. Генерируй из них `backend/api/openapi.yaml`, затем из контракта через OpenAPI Generator генерируй TypeScript-сервисы и модели для Angular. В прикладном коде фронтенда вызывай сгенерированные сервисы. При изменении API обновляй Go-код и повторяй оба шага генерации. В CI проверяй воспроизводимость обоих результатов. Полученные из сети данные проверяй при выполнении.

## Виртуальные машины

Перед работой обязательно прочитай [Правила работы с виртуальными машинами](docs/virtual-machines.md): там указаны каталоги Lima, команды просмотра списка, границы доступа и история переименования.

- `hestia-prod` — рабочая Гестия владельца, не использовать для разработки и экспериментов.
- `hestia-dev` — разработка, интеграционные и нагрузочные испытания, изолированные эксперименты.
- `hestia-client` — генерация клиентского трафика и проверка пути через выбранный шлюз; доступ к prod или Keenetic через клиента также требует разрешения.

Управление питанием dev может затронуть сеть prod/client из-за общего `socket_vmnet`; до устранения зависимости такие операции согласовывай с владельцем как потенциально влияющие на prod.

## Изоляция экспериментов

`hestia-prod` (личная ВМ владельца, адрес `192.168.1.133`) и его Keenetic требуют отдельного разрешения владельца для доступа, отправки проб, изменения настроек или управления питанием. Для проектных экспериментов явно выбирай изолированную ВМ по имени. Передавай эту границу каждому исполнителю стенда.

## Результаты экспериментов

Исследования устройства Keenetic, KeeneticOS/Entware, документации производителя и исходников конкурентов веди в едином документе [Устройство Keenetic и интеграция Hestia](docs/keenetic-platform.md). Не создавай отдельные документы исследований для каждого конкурента или ограничения Keenetic. Протоколы прогонов и сырые свидетельства сохраняй в `experiments/`, а в общем документе фиксируй выводы и ссылки на них; планы и критерии остаются в дорожной карте и спецификациях.

Лабораторные проверки и их конфигурации храни в `tests/lab/`; отчёты и свидетельства — в `experiments/`. Общие сценарии сборки, проверки исходников, установки и проверки установленной версии находятся в `scripts/`, их структура описана в [scripts/readme.md](scripts/readme.md). Порядок запуска отдельных лабораторий описан в [tests/lab/README.md](tests/lab/README.md).

После каждого прогона, на основании которого команда принимает решение, обнови отчёт в `experiments/<опыт>/README.md`. Укажи вопрос, среду и версию проверенного кода, условия опыта, ожидаемый и фактический результат, обнаруженные ошибки, границы вывода и команды воспроизведения. Свяжи вывод с проверяемым свидетельством в `evidence/` и отметь статус в `docs/roadmap.md`. Для незавершённого прогона фиксируй только то, что уже наблюдалось.
