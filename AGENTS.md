## Работа с веткой master

До первого развёртывания кода Гестии на физическом устройстве Product Owner разрешает работать непосредственно в `master`, включая коммиты и push в `origin/master`. С момента первого развёртывания на устройстве действуют общие правила работы в ветках задач. Запуск стенда на виртуальной машине не завершает этот период.

## Роли команды Гестии

Архитектор назначает роли по [общим правилам и каталогу ролей](../ai-dev-practices/AGENTS.md#инструкции-по-ролям). Для задач шлюза используй также два проектных профиля:

| Роль | Когда подключать | Что передаёт команде |
|---|---|---|
| [Инженер по сетям Linux](docs/agent-prompts/linux-network-engineer.md) | Проектирование пути пакета, DNS, VPN, измерение потерь, переключение выходов и диагностика утечек | Схему путей, воспроизводимую сетевую конфигурацию и доказательства фактического выхода или блокировки |
| [Инженер по встраиваемому Linux](docs/agent-prompts/embedded-linux-engineer.md) | Выбор платы и образа, проверка возможностей ядра, первый запуск, испытания портов, нагрузки и восстановления | Матрицу совместимости для конкретной ревизии платы, протокол испытаний и проверенный способ восстановления |

При назначении указывай роль в скобках рядом с именем, например `Routes (Linux Network Engineer)` или `Board (Embedded Linux Engineer)`. Передай исполнителю критерии приёмки, технический контекст и пути к памяти задачи и личному checkpoint. Исполнитель общается с Product Owner через архитектора. Внутреннюю переписку и checkpoint веди на английском, проектную документацию и результаты для Product Owner — на русском. Для исходников и скриптов применяй [общий порядок работы с кодом](../ai-dev-practices/docs/process/code-changes.md). Независимую проверку поведения проводит тестировщик, ревью изменений кода и проверку безопасности выполняют соответствующие общие роли.

## Документация функций

Документируй каждую именованную функцию и метод, включая приватные функции, тесты и вспомогательные функции стенда. Опиши назначение и контракт: какой результат гарантирован, а где важно — входы, побочные эффекты и условия отказа. Для Go ставь Go doc непосредственно перед объявлением, начиная с имени функции; для Python используй docstring, для shell — комментарий перед функцией. Документируй и классы Python. Команда `make docs-check` проверяет наличие документации, а ревьюер сверяет её смысл с поведением кода.

## Форматирование и линтинг кода

Перед передачей изменений на ревью и перед коммитом отформатируй изменённый код и запусти линтер для его языка. Для Go выполни из корня репозитория `make fmt`, затем `make check`. Вторая команда проверяет форматирование, запускает статический анализ `go vet` и тесты. Исправь замечания и повтори проверку до успешного результата.

Для Bash-сценариев в `deploy/` и `experiments/` используй shfmt 3.11.0 и ShellCheck 0.11.0. shfmt отвечает за отступы и единое оформление, ShellCheck находит ошибки раскрытия переменных, передачи аргументов и использования Bash. Команда `make fmt` форматирует Go и Bash, `make check` проверяет стиль, линтинг и тесты. Эти инструменты нужны на машине разработки и в CI. При установке Гестии на шлюз они не используются.

При создании Angular-фронтенда установи ESLint и Prettier как зависимости разработки (`devDependencies`). Настрой ESLint для TypeScript и Angular-шаблонов, а Prettier — для форматирования исходников, шаблонов и стилей. Добавь в `package.json` команды `lint`, `format` и `format:check`. Перед ревью и коммитом запускай из каталога фронтенда `npm run format` и `npm run lint`. В CI запускай `npm run format:check` и `npm run lint`.
