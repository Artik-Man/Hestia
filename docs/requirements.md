# Требования к Гестии

Требования по итогам обсуждения 3–4 ноября 2026 года.

## Размещение и ответственность

Клиентские устройства выходят в интернет через существующий роутер. **Гестия (Hestia)** — Linux-шлюз, отвечающий за выбор внешнего подключения. Проект носит то же имя. В основной схеме Гестия устанавливается между роутером и провайдером. Для отладки допускается вторая схема: роутер подключён к провайдеру напрямую и передаёт весь клиентский интернет-трафик устройству через локальный VPN по одному Ethernet-кабелю. Гестия маршрутизирует трафик, обслуживает DNS-запросы с кэшированием ответов и постоянно наблюдает за доступными подключениями. Выходом может быть как линия провайдера, так и VPN. У разных подключений могут быть свои DNS-серверы. Нужно поддержать два одновременно активных SSTP с одним локальным туннельным IP, например `172.16.3.33`.

Единственная поддерживаемая платформа Гестии — Linux ARM64 (AArch64), как в виртуальной машине, так и на физическом устройстве. Сборка команд Гестии должна создавать исполняемые файлы для `linux/arm64` и отклонять другие цели, включая macOS и Linux x86-64.

## Требования к устройству

Физический шлюз должен иметь **не менее двух отдельных Ethernet-портов, каждый со скоростью не ниже 1 Гбит/с**. Оба порта должны работать одновременно. В ранее описанном варианте один порт соединяет шлюз с существующим роутером, другой — с внешней сетью. Количество VPN-туннелей само по себе не определяет число физических портов.

Во второй схеме задействован один Ethernet-порт устройства; минимум в два порта сохраняется для поддержки основной схемы. См. [схемы подключения](architecture.md#схемы-подключения). Цель основной схемы — маршрутизация до 1 Гбит/с. Скорость SSTP измеряем отдельно. Во время отладки администратор может вручную переключить клиентский профиль Keenetic на провайдера, чтобы восстановить интернет независимо от Гестии. Минимум CPU, оперативной памяти и диска определим после выбора нагрузки и измерений с включёнными мониторингом и журналом трафика.

## Основные сущности и приоритеты

- **Подключение** — отдельный выход в интернет, например линия провайдера или SSTP-туннель.
- **Группа подключений** объединяет подключения по стране их внешнего IP. Первые группы — «Из России» и «Из Финляндии». Группы образуют упорядоченный массив: чем выше позиция, тем выше приоритет группы. Первую позицию занимает группа по умолчанию.
- **Список доменов** — самостоятельная сущность, содержащая доменные правила и исключения. У списка может быть одна группа подключений или ни одной. При переназначении списка новая группа заменяет прежнюю. Записи списка сохраняются.

Внутри каждой группы задан исходный порядок подключений. Шлюз меняет их фактический приоритет на основании стабильности. Например, если FI-1 стоит выше FI-2, но устойчиво теряет пакеты до нужной цели, для неё шлюз может предпочесть FI-2. Позиция финской группы среди остальных групп при этом сохраняется.

Если в выбранной группе нет доступных подключений, шлюз блокирует её трафик, в том числе при ранее закэшированном клиентом IP. При смене подключения внешний IP может измениться. Переподключение приложения допустимо.

## Домены и исключения

Сначала шлюз выбирает самую конкретную совпавшую маску среди всех привязанных списков доменов. Только при равной специфичности выигрывает группа подключений, которая стоит выше в массиве. Например, если список России содержит `*.com`, а список Финляндии содержит `*.deepseek.com`, то `api.deepseek.com` идёт через Финляндию, даже когда Россия стоит первой.

| Пример назначения | Правило | Ожидаемый выход в примере |
|---|---|---|
| `google.com`, `www.google.com` | `*.com` | Финляндия |
| `api.deepseek.com` | `*.deepseek.com` | Россия |
| `mydeepseek.com` | `*.com` | Финляндия |

Страны в таблице иллюстрируют пользовательскую конфигурацию. Шлюз сопоставляет полные DNS-метки с записями привязанных списков. Порядок строк внутри списка не влияет на специфичность маски. Маска `*.deepseek.com` охватывает сам `deepseek.com` и поддомены любой глубины, включая `v1.api.deepseek.com`. При отказе выбранной группы трафик блокируется. Для записи без звёздочки предложен режим точного совпадения. В базовой схеме без GeoIP при отсутствии совпадений применяется группа по умолчанию. Это относится и к пустому списку правил, и к соединению по IP, для которого шлюз не может определить имя. Недоступность группы, выбранной явным правилом, не переводит трафик в группу по умолчанию.

## Карта стран GeoIP

Если для домена нет совпадения в привязанных списках, шлюз определяет страну реального IP назначения по GeoIP. Администратор задаёт в веб-интерфейсе соответствие между отдельной страной или блоком стран и группой подключений. Состав блока настраивается. В карте можно указать группу для остального мира.

| Условие в примере | Группа подключений |
|---|---|
| Россия | Россия |
| Блок «Евросоюз» | Финляндия |
| Любая другая определённая страна | Другая группа с VPN |

Маска домена имеет приоритет над картой. После выбора группы обычные правила стабильности определяют подключение внутри неё. Если все её выходы недоступны, трафик блокируется. Запись «Остальной мир» может вести в группу, отличную от группы по умолчанию. Если в карте для известной страны нет подходящей записи, действует группа по умолчанию.

Для известной страны шлюз сначала ищет запись самой страны, затем просматривает блоки сверху вниз до первого совпадения. Если совпадений нет, применяется запись «Остальной мир», когда она задана. Перестановка блоков влияет только на страны в их пересечении без собственной записи.

Если доменная маска не совпала и GeoIP не определил страну IP назначения, шлюз выбирает группу по умолчанию с причиной «Страна не определена». Запись «Остальной мир» применяется только при известной стране.

При отсутствии явной доменной маски GeoIP применяется к фактическому IP назначения каждого нового соединения. Для одного домена соединения к российскому и немецкому адресам могут выбрать разные группы.

При первоначальном DNS-разрешении домена без явного правила статус группы по умолчанию не даёт ей преимущества. При отсутствии действующего ответа в кэше шлюз параллельно опрашивает DNS через выбранное подключение каждой доступной группы. Клиент получает первый положительный ответ с пригодным адресом; остальные начатые попытки завершаются в фоне. NXDOMAIN от одного резолвера не прерывает ожидание положительного ответа от другого. Каждый ответ-кандидат сохраняет связь с резолвером, подключением и TTL. При явном доменном правиле запрос остаётся в выбранной группе. Выбор реального адреса при FakeIP предстоит согласовать. При диагностике медленного открытия домена журнал должен показывать, сколько клиент ждал ответа шлюза, какие DNS-попытки шли одновременно и что произошло с последующим потоком.

## Долговременный DNS-кэш

Шлюз должен поддерживать настраиваемое хранение положительных DNS-записей сверх их исходного TTL. Для динамических адресов срок хранения и правила выдачи истёкшего ответа настраиваются отдельно. Предлагаемый режим выдачи при сбое описан в [архитектуре](architecture.md#срок-хранения-dns-ответов).

### Фоновое обновление DNS

Администратор задаёт окно клиентской активности X и интервал фонового обновления Y. В фоновый прогрев попадают только часто используемые домены. Частота определяется исключительно по реальным клиентским обращениям в скользящем окне X. Разовое обращение обслуживается обычным DNS-кэшем. Администратор задаёт порог N: домен участвует в прогреве, пока за последние X часов было не менее N клиентских обращений. Для каждого имени и типа записи он повторяет запросы к тем же резолверам через те же подключения, пока это разрешают текущие правила. Фоновые попытки не создают записей в истории пользовательских обращений и не увеличивают счётчик частоты. Когда домен перестаёт удовлетворять критерию, его прогрев прекращается. Учёт частоты ограничен окном X. Цель — отвечать на следующий запрос клиента из действующего кэша. Предлагаемая семантика Y — верхняя граница интервала до следующей попытки обновления. Срок актуальности каждого полученного ответа определяется его TTL. [Проверка на ARM64](../experiments/dns-warm/README.md).

## Что считать стабильностью

Основная метрика — доля потерянных пакетов. Вторичные показатели — задержка, скорость и другие характеристики соединения. Окно оценки настраивается, исходное значение — **60 минут**. Нужны наблюдения за рабочим трафиком и возможность сравнить качество путей до одного назначения.

Каждое подключение проверяется постоянно и независимо, включая резервные. Для сравнения используются одинаковые цели, типы проб, частота, окна и критерии оценки. Пока текущее подключение доступно, трафик остаётся на нём, если измерения для альтернативы не показывают лучшую стабильность. Равный результат или нехватка данных о резерве не вызывают переключения.

Масштаб переключения зависит от масштаба проблемы. Если только один UDP-сервис работает хуже через конкретный туннель, нужно уметь выбрать другой выход для этого назначения. Если потери затрагивают разные независимые цели, может потребоваться сменить основной выход группы. Пороги переключения и способ совмещения измеренного качества с административным приоритетом остаются предметом испытаний.

## Журнал маршрутизации

Администратор настраивает срок хранения журнала трафика в веб-панели. По умолчанию хранятся записи за последние **24 часа**. Возраст записи отсчитывается от времени события.

Для каждого проходящего через шлюз IP назначения сохраняются время, известный шлюзу домен, выбранная группа, фактическое подключение и интерфейс, а также причина выбора. Это распространяется на IPv4 и IPv6, включая прямые обращения по IP. Если имя установить нельзя, IP всё равно записывается. В Angular-панели шлюза доступен экран «Журнал трафика». В строке поиска можно ввести любую подстроку домена или текстового представления IP назначения (IPv4 или IPv6). Отдельный фильтр выбирает протокол, например TCP или UDP. При совместном использовании остаются записи, удовлетворяющие обоим фильтрам. Поиск по IP включает записи без известного домена. Предлагаемая детализация — [одна запись на новый поток](monitoring.md#журнал-прохождения-трафика).

## Клиентские VPN-подключения

Гестия выступает клиентом удалённых серверов. Для первого выпуска согласованы четыре типа клиентских подключений: SSTP, VLESS, WireGuard и AmneziaWG. У каждого экземпляра подключения есть собственная конфигурация, ID для проб и журнала, принадлежность к группе подключений и исходная позиция в её порядке. Например, FI-1 может использовать WireGuard, а FI-2 — VLESS. Для обоих применяются общие правила выбора по стабильности и блокировки при отказе всей группы.

Администратор добавляет подключения через локальную Angular-панель. Предлагаемый сценарий: выбрать тип, заполнить поля этого типа, указать группу и приоритет, проверить соединение, затем включить его для клиентского трафика. На странице подключения доступны редактирование, включение, отключение и результат последней проверки. Журнал различает протокол подключения (например, WireGuard) и протокол пользовательского потока (например, UDP).

Действие «Добавить подключение» создаёт профиль одного из протоколов, поддерживаемых установленной версией Гестии. Администратор может создать несколько независимых профилей одного типа. Поддержка новых протоколов поставляется с обновлениями Гестии.

## Веб-интерфейс управления

На текущем этапе панель Гестии работает без аутентификации и учётных записей. Каждый, кому доступен интерфейс по его адресу, может менять все настройки, для которых реализовано редактирование. Это согласованная модель доступа для текущего этапа.

Администратор управляет группами подключений через веб-интерфейс шлюза. Он редактирует списки доменов и их привязки. Например, список с общим правилом для `*.com` привязывается к Финляндии, а список с исключением `*.deepseek.com` — к России. При изменении конфигурации продолжает действовать требование блокировки трафика группы при отсутствии живых выходов.

Администратор может назначить любую существующую группу группой по умолчанию. С момента применения изменения новые соединения, для которых ни доменные правила, ни карта стран не выбрали группу, используют выбранную группу по умолчанию. Удаление текущей группы по умолчанию блокируется, пока администратор не назначит другую.

При удалении группы снимаются её привязки. Списки доменов и все их записи сохраняются. Список без привязки отображается с пометкой «Группа не назначена» и пропускается при поиске совпадений. Администратор может привязать его к группе без повторного ввода масок. Например, если список с `*.deepseek.com` не привязан, а список с `*.com` привязан к Финляндии, то `api.deepseek.com` идёт через Финляндию.

Веб-панель реализуется как Angular-приложение на TypeScript. Для компонентов выбран PrimeNG. Скомпилированное приложение, стили и иконки раздаёт сам шлюз, чтобы панель открывалась из Wi-Fi при недоступных внешних подключениях. Для прикладного кода используется [Angular-гайд соседнего проекта](../../ai-dev-practices/docs/style-guides/frameworks/angular.md).
