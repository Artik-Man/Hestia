# Сохранение порядка групп и выходов

На странице «Группы подключений» оператор перетаскивает группу или выход за ручку. Сортировка переставляет выход внутри его группы. Чтобы [перенести выход в другую группу](features/connection-groups.md#перенос-подключения), перетащите его за ручку в список выходов этой группы. Перенос можно отменить или сохранить вместе с остальными изменениями. Стрелки на клавиатуре меняют позицию элемента, ручка которого находится в фокусе. До нажатия «Сохранить» это черновик страницы. Первая группа после применения становится группой по умолчанию. Внутри группы контроллер выбирает первый доступный выход.

## Контракт

`PUT /api/group-order` принимает две полные последовательности: `expected` — порядок, с которого началось редактирование, и `groups` — желаемый порядок. Каждая запись содержит ID группы и массив ID её выходов, включая пустой массив у группы без выходов. Например, для смены приоритета внутри группы:

```json
{
  "expected": [{"id":"fi","exits":["fi1","fi2"]},{"id":"ru","exits":[]}],
  "groups": [{"id":"fi","exits":["fi2","fi1"]},{"id":"ru","exits":[]}]
}
```

Сохраняются доменные списки и их привязки, набор выходов, настройки подключений и текущая доступность. При одинаковой специфичности доменных масок действует новый приоритет групп. Если новая основная группа не имеет доступного выхода, действует обычная блокировка.

Код 200 с полем `groups` означает, что службы загрузили новый профиль и подтвердили выходы. Форма сверяет весь возвращённый порядок и перечитывает снимок. Устаревший исходный порядок или занятая транзакция дают 409. Добавление, удаление или дублирование выходов в запросе сортировки дают 422. Запросы размером больше 64 КиБ получают 413. Когда запись выключена либо применение не подтверждено, панель получает 503. При изменении только доступности выходов порядок остаётся совместим с ожидаемым.

Перенос выхода между группами также пересобирает правило входящего трафика OpkgTun. При подготовке транзакции сортировка может восстановить только одно из двух точных устаревших состояний: маршрут направлен в пустую deny-only группу вместо `deny`, либо `deny` остался в backend после того, как проверенный профиль выбрал безопасную AWG-группу. Любые другие отличия маршрута отклоняются. Новый профиль сохраняет fail-closed поведение, когда безопасной группы нет.

Повторное сохранение неизменившегося порядка может применить транзакцию, если подготовленный маршрут отличается от текущего; это восстанавливает backend по проверенному профилю, не меняя порядок групп или выходов. Когда маршруты совпадают, подтверждается no-op без перезапуска служб.

## Включение на установленном шлюзе

Используйте режим `-enable-group-order -snapshot /etc/hestia/snapshot.json` для панели на управляемой установке. Нужны актуальные бинарники `hestia-panel`, `hestia`, сборщик профиля и службы восстановления из комплекта установки. Для системной учётной записи панели `hestia-panel` разрешите через `visudo` отдельный вызов помощника:

```sudoers
hestia-panel ALL=(root) NOPASSWD: /usr/local/bin/hestia -apply-group-order
```

Помощник использует блокировку установщика, журнал и подтверждение работающего sing-box по [правилам применения конфигурации](list-binding.md). Сохранение может прервать установленные соединения. Пока шлюз проверяет кандидата, через него уже может пройти трафик. При отказе восстановление возвращает прежнюю конфигурацию для последующих соединений.

Эксперимент на трёх WireGuard-пирах проверил сохранение из браузера, маршрут нового TCP-потока, отклонение конфликтующей правки и возврат к прежней конфигурации при отказе. [Отчёт и свидетельства](../experiments/group-order/README.md).
