# Минимальный объём исследования API Keenetic для коннекторов Hestia

Цель — найти и проверить программные интерфейсы Keenetic, достаточные для реализации коннекторов и платформенных адаптеров Hestia. Документ определяет обязательные операции и минимальные доказательства их доступности. Дата выделения плана — 7 ноября 2026 года, по решению владельца.

Под интерфейсом понимается конкретный HTTP API/RCI, CLI-вызов либо доступный интерфейс ОС/Entware. Для каждого результата указывается слой: работа отдельного runtime не подтверждает наличие API KeeneticOS. Группы, приоритеты, собственные списки, оценка качества, прогрев и GeoIP могут реализовываться в общем ядре Hestia; одноимённые функции Keenetic не обязательны. Сквозная приёмка продукта следует после проверки необходимых контрактов.

Для интеграции с Keenetic Product Owner предпочитает HTTP RCI с JSON-ответом перед разбором человекочитаемого CLI. Для Ethernet token-auth `GET /rci/show/interface` подтверждён на KN-1012; он возвращает пять физических записей типа `Port` с ID, link и, когда связь поднята, speed/duplex. Фильтрованный результат и ограничения сверены с предыдущим `show interface` и контролируемым link-событием LAN1. Успех команды `ndmc -c 'show interface'` сам по себе не доказывает работу HTTP RCI. Использовать CLI как fallback только если RCI недоступен или не предоставляет нужные поля.

Для локального RCI Entware на KN-1012 с KeeneticOS 5.2 Beta 3 подтверждены token-auth `GET /rci/show/version` и `GET /rci/show/interface` по `127.0.0.1:79` с заголовком `X-NDMA-TKN`; оба вернули HTTP 200 JSON. Ethernet-запрос разобрал пять физических портов; [результат и ограничения](../experiments/keenetic-ethernet-management-20261106/evidence/attempt-20261106T221126Z-rci-interface-filtered/result.json). Токен передавался через SSH-туннель на loopback и не сохранялся в свидетельствах. [Протокол RCI](../experiments/keenetic-rci-readonly/README.md#token-auth-чтение-ethernet-интерфейсов--7-ноября-2026-года). Подтверждены только эти два GET на данной прошивке; права токена на другие RCI-операции, POST/изменения и запрос непосредственно из Entware-приложения Гестии не проверены.

7 ноября общий Go-клиент повторил `GET /rci/show/interface` через временный SSH-туннель: HTTP 200, тот же список из пяти физических портов. Это подтверждает клиентскую аутентификацию и разбор ответа на рабочей станции; запрос из установленной Hestia на роутере и работа watcher не проверялись. [Свидетельство Go-запроса](../experiments/keenetic-ethernet-management-20261106/evidence/attempt-20261106T230806Z-go-rci-carrier/README.md).

Не смешивать локальный RCI на port 79 и HTTP Proxy API через port 79: производитель описывает для HTTP Proxy отдельный режим доступа с Digest-аутентификацией и разрешением HTTP Proxy для пользователя. Не считать локальный loopback общедоступным без авторизации на других прошивках или версиях. При запуске Hestia внутри Keenetic использовать токен для RCI 5.2 и не хранить пароль администратора.

[Историческая сводка результатов и ограничений](keenetic-platform.md#матрица-возможностей-hestia-на-keenetic) сохранена в архивном документе. Его статусы не определяют текущий план работ. Протоколы и первичные свидетельства находятся в [experiments](../experiments/README.md). Этот план не меняет статусы и не означает запуск новых проверок.

## Общий результат исследования API

Для каждой необходимой операции коннектора заполняется запись следующего вида:

| Поле | Что зафиксировать |
|---|---|
| Операция Hestia | Что коннектор должен прочитать или изменить; какой объект он адресует. |
| Интерфейс и вызов | Слой (KeeneticOS, ОС/Entware или runtime), точный метод/путь/CLI-команда, параметры и условия доступа/авторизации. Не записывать токены и секреты. |
| Контракт | Идентификаторы объектов и их устойчивость, формат/типы ответа, единицы, необязательные поля, ошибки и признак завершения асинхронной операции. |
| Изменение состояния | Временное или сохраняемое действие; повторный вызов, побочные эффекты, чтение фактического результата и способ восстановления. Для чтения — «не применяется». |
| Свидетельство и границы | Устройство/прошивка/компоненты, точные команды и входы без секретов, время, ответы и коды завершения, ссылка на попытку. Указать проверенную часть контракта и непроверенные условия. |
| Решение для коннектора | Доступно напрямую; доступно через адаптацию/собственный механизм Hestia; не найдено; недоступно в проверенной конфигурации с указанием основания. |

Минимальная проверка чтения — успешный программный вызов с разобранным ответом, который можно связать с известным объектом или контролируемым событием. Для записи — чтение исходного состояния, одна обратимая операция над выделенным объектом, чтение результата, точечная проверка эффекта и восстановление. Проверить повторный вызов и один релевантный безопасный отказ там, где это определяет контракт; не вызывать намеренно отказ рабочего подключения. Полный набор аварийных и нагрузочных сценариев в исследование API не входит.

Сетевой эффект проверяется короткой адресной пробой, когда одного ответа API недостаточно: например, назначение маршрута подтверждается пакетом через выбранный выход. Для жизненного цикла профиля подтверждённые state/connected описывают только состояние, сообщённое Keenetic; handshake и передача данных отмечаются отдельно. Найденная команда, чтение документации или ответ с неизвестной структурой не считаются завершённым контрактом. «Не найдено» не означает принципиальную невозможность.

Один пригодный способ вызова достаточен: дублировать уже проверенный CLI через HTTP только ради второго интерфейса не требуется. Для ещё не определённого механизма рассмотреть доступные варианты и зафиксировать выбор. Проверку совместимости ограничить фактической прошивкой; прочие версии не объявлять поддержанными без свидетельств.

Прототипы размещаются только в `experiments/<уникальное-исследование>/prototype/`, отчёты рядом, свидетельства в `evidence/`. Перед исполнением проверяются SSH host key и SHA-256; сохраняются точные исходники и конфигурации каждой попытки, время, команды и коды завершения. Используются собственные временные ресурсы, ограниченное время и очистка только своих объектов. Не сохранять секреты или сырые домашние таблицы; для маршрутов и правил достаточно хешей. Неудачные попытки не перезаписывать, утраченные свидетельства не восстанавливать по памяти.

## Минимальный объём исследования управления подключениями

| Операции коннектора | Что найти | Минимальная проверка |
|---|---|---|
| Перечислить подключения и прочитать состояние | Вызовы перечисления профилей/интерфейсов, ID, тип, административное состояние, link/connected; связь Ethernet-разъёма с объектом и Wi-Fi station с профилем. | Разобрать ответы для нужных типов; сопоставить ID с известным профилем и одним контролируемым изменением линка. Проверить, какие поля исчезают в отключённом состоянии. |
| Создать, настроить, включить, выключить и удалить VPN | Точные операции для требуемых типов VPN, схема параметров и секретов, ошибки, сохранение, чтение состояния. Разделить штатные VPN Keenetic и runtime под управлением Hestia. | Создать собственный тестовый профиль, прочитать его, изменить один параметр, выполнить ограниченный цикл состояния и удалить только его. Уже проверенные включение/выключение существующих WG/SSTP не повторять без новой причины; создание/удаление ими не доказано. |
| Настроить выбранное Ethernet-подключение | Операции чтения и применения поддерживаемых параметров порта/подключения и IPv4, необходимость сохранения, границы влияния на сегмент. Предпочесть HTTP RCI с JSON, если read-only контракт подтверждён. | Сначала подтвердить разбор read-only ответа для выбранного порта и сопоставить его с уже известным link-событием. Только если коннектору действительно требуется изменять параметры — одна необходимая обратимая настройка на выделенном порту, readback, наблюдение эффекта и возврат. Не требовать перебора всех режимов портов. |
| Сканировать и управлять WISP | Вызовы сканирования 2,4/5 ГГц и схема результатов; чтение/выбор профиля, настройка подключения, включение/выключение, ошибки и состояние. | Получить разбираемый результат для обоих диапазонов; на тестовом профиле проверить необходимую операцию настройки и цикл состояния с восстановлением. Зафиксировать влияние общего радиомодуля; не менять остальные AP. |

Полученные [Ethernet](../experiments/keenetic-ethernet-management-20261106/README.md), [Wi-Fi](../experiments/keenetic-wifi-management-20261106/README.md) и [VPN](../experiments/keenetic-virtual-management-20261106/README.md) свидетельства используются как уже проверенные части контрактов. Для Ethernet token-auth `GET /rci/show/interface` вернул JSON и пять физических портов; результат подтверждает только чтение нужных полей на KN-1012 / KeeneticOS 5.2 Beta 3. `show site-survey` завершался успешно, но полный разбор ответа остаётся открытым. Для Go-эксперимента подготовлены санитизирующие schema probes через `POST /rci/show` для site survey и `GET /rci/show/interface` для интерфейсов; обе команды используют общий RCI-клиент и компилируются, но новые запросы на роутер не отправлялись. [Свидетельство сборки интерфейсного probe](../experiments/keenetic-rci-readonly/evidence/schema-cli-build-20261107.txt). Циклы существующих VPN подтверждены, WISP не переключался. Полная передача клиентского трафика и производительность относятся к последующей интеграционной приёмке.

## Минимальный объём исследования выбора пути трафика

| Операции коннектора | Что найти | Минимальная проверка |
|---|---|---|
| Прочитать политики и назначение выхода | API/CLI либо интерфейс ОС для политик, таблиц, меток и правил; ID, приоритеты и принадлежность системных объектов. | Получить структурированный обезличенный результат для одного выбранного объекта. Ранее сохранённый хеш `show ip policy` подтверждает вызов, но не контракт содержимого. |
| Применить и изменить назначение потока | Вызов, связывающий узкую выборку по адресу/протоколу с выбранным выходом; чтение результата и удаление своего правила. | На собственном правиле направить контрольный TCP/UDP через A, изменить выход на B, подтвердить путь короткими пробами и вернуть исходное состояние. Установить, когда изменение действует на новые/существующие потоки. |
| Заблокировать выбранный поток | Доступный запрет без перехода к обычному default route; способ замены/удаления правила и взаимодействие с политиками KeeneticOS. | Установить блокировку только тестового потока при доступной напрямую цели, подтвердить отсутствие доставки и снять её. |
| Обнаружить изменение системной сети | Документированный hook/событие либо пригодный опрос, через который адаптер узнает об изменении интерфейса/политики и необходимости восстановить свои объекты. | Зафиксировать контракт выбранного источника и одно событие от собственного тестового объекта либо обнаружение изменения опросом. |

**Кандидат:** закреплённый sing-box 1.14.4 имеет TUN inbound и `auto_route`; его `auto_redirect` требует nftables. Предыдущая узкая проба на KN-1012 подтвердила эксклюзивное создание и очистку TUN, но не передачу пакетов. Следующее исследование должно установить, можно ли ограничить перенаправление одним клиентом и исключить собственный uplink, затем подтвердить одно TCP- и UDP-соединение и fail-closed поведение. Не включать глобальный `auto_route` до безопасного ограничения источника. В текущей Entware-упаковке TPROXY target не найден, но отсутствие пакета в feed не доказывает отсутствие поддержки в KeeneticOS/ядре. Факты и официальная ссылка закреплены в [спецификации коннекторов](features/keenetic-connectors.md#решение-по-исследованию-dataplane); целевой опыт, который меняет маршруты или направляет клиентский поток, ждёт отдельного разрешения владельца устройства.

Группы, приоритеты внутри группы, выбор лучшего выхода и автоматический резерв остаются логикой Hestia. В этом минимуме нужен способ применить её решение, а не готовый алгоритм выбора в Keenetic. Полные сценарии автоматического A→B→A и отказа всех выходов относятся к последующей приёмке. [Прежний urltest-опыт](../experiments/keenetic-exit-failover/README.md) сохраняется как частичное свидетельство runtime: выбор A для TCP подтверждён, UDP, резерв и блокировка не подтверждены; это не проверка API политик Keenetic.

## Минимальный объём исследования измерений и наблюдения

| Операции коннектора | Что найти | Минимальная проверка |
|---|---|---|
| Прочитать состояние и счётчики подключения | Источник link/connected, счётчиков трафика и доступных измерений; единицы, период обновления, сбросы и связь с ID подключения. | Прочитать выбранный объект до/после небольшого известного обмена; определить семантику изменившихся полей. Отсутствующее измерение не заменять придуманным значением. |
| Отправить собственную пробу через заданный выход | Программный механизм привязки сокета/процесса/тестового потока к интерфейсу или политике, включая резервный выход. | Отправить короткую пробу через A и резервный B, независимо подтвердить выход; при недоступности назначенного выхода проверить, что проба не обходит его через другой. Повторно использовать механизм маршрутизации из предыдущего раздела. |
| Получить событие потока и определить выход | API, журнал, поток событий или доступный механизм ОС для сведений о соединении; протокол, время, ID, выбранный/фактический выход, полнота и потери событий. | Создать один TCP- и один UDP-поток с известными маркерами, сопоставить полученные записи с наблюдением сервера. Если источник даёт только назначение или агрегаты, явно зафиксировать недостаточность для фактического журнала. |

Расчёт качества, интервалы проб, история, UI, Grafana, алерты и нагрузочная оценка не входят в поиск API. Итог должен установить, какие данные предоставляет Keenetic и какие пробы/наблюдения Hestia должна выполнять сама. Реализовывать целиком алгоритм измерения ради ответа на этот вопрос не требуется.

## Минимальный объём исследования доменных правил

| Операции коннектора | Что найти | Минимальная проверка |
|---|---|---|
| Получить списки Keenetic и их содержимое | Вызовы перечисления и чтения, ID/названия, записи, признаки включения и доступные сведения о точных доменах, поддоменах и исключениях. | Прочитать один список, разобрать ответ и сравнить с известными тестовыми записями. Не сохранять чужие списки целиком. |
| Обнаружить обновление списка | Событие, ревизию либо пригодный опрос; правила чтения согласованного состояния. | Изменить одну тестовую запись через штатную панель или уже проверенный вызов и обнаружить изменение программно. Запись списков через API Keenetic не обязательна для коннектора чтения. |
| Применить доменное решение Hestia | Возможность штатного доменного правила либо механизм применения решения к адресам/потокам, включая необходимую связь домена с потоком. | Применить одно собственное тестовое правило, подтвердить его действие на коротком TCP/UDP-обмене и удалить. Использовать уже проверенный API маршрутизации, если его достаточно; ограничения общих IP и неизвестного домена записать в контракт. |

Хранение собственных списков, маски, исключения, приоритет наиболее конкретного правила и редактор относятся к общей логике Hestia. Для них не требуется искать одноимённый API Keenetic. Полная матрица совпадений и конфликтов остаётся приёмкой этой логики. Локальные FakeIP-опыты сохраняют значение как свидетельства runtime, но не подтверждают чтение списков Keenetic.

## Минимальный объём исследования DNS

| Операции коннектора | Что найти | Минимальная проверка |
|---|---|---|
| Прочитать и изменить точку подключения DNS-службы | Вызовы чтения штатного DNS/форвардинга и подключения собственного resolver для выбранного клиента/сегмента; порты, права, ограничения источников и восстановление. | Прочитать настройки, временно направить DNS только тестового клиента в собственный ответчик, подтвердить UDP/TCP-запросы и восстановить. |
| Назначить путь upstream-запроса | Механизм привязки собственного DNS-запроса к нужному выходу/политике. | Выполнить по одному контролируемому запросу через выбранные выходы и подтвердить путь. Повторно использовать уже проверенную операцию привязки; не создавать второе исследование того же механизма. |
| Определить границу кэша и наблюдений DNS | Наличие API чтения/настройки/сброса штатного кэша и событий DNS; либо возможность полностью обслуживать кэш и наблюдения собственной службой Hestia. | Для выбранного варианта проверить одну необходимую операцию с тестовой записью и доступность домена/времени/источника события для Hestia. Если API штатного кэша не найден, зафиксировать альтернативу и её условия без утверждения о невозможности DNS-функции. |

TTL-политика, устаревшие ответы, ручные списки и автоматический прогрев могут полностью принадлежать Hestia. На этом этапе нужно установить доступность интеграции и исходных данных, а не реализовать и испытать весь прогрев. Уже выполненные [локальный DNS](../experiments/keenetic-dns-local/README.md), [CNAME/TCP fallback](../experiments/keenetic-dns-fallback/README.md) и [FakeIP/TTL](../experiments/keenetic-fakeip-ttl/README.md) сохраняются с прежними ограничениями; они не подтверждают API изменения DNS-настроек Keenetic.

## Минимальный объём исследования GeoIP

| Операции коннектора | Что найти | Минимальная проверка |
|---|---|---|
| Применить решение по IP/префиксу | Достаточность уже найденных операций маршрутизации для назначения выхода адресу/набору адресов; изменение и удаление своего назначения. | Переиспользовать свидетельство адресного правила из исследования пути трафика. Дополнительную пробу проводить только для ещё не проверенного необходимого типа адреса/префикса или операции. |
| Определить необходимость штатного GeoIP | Какие сведения Keenetic действительно нужны адаптеру, если страна определяется локальной базой Hestia или внешним сервисом. Если выбран штатный механизм — его точные вызовы, формат и ограничения. | Зафиксировать границу ответственности. При отсутствии дополнительной зависимости от Keenetic явно записать «отдельный API GeoIP Keenetic не требуется» с основанием в проверенном адресном маршрутизаторе; при наличии — проверить одну необходимую операцию. |

Локальная геобаза, точечные запросы к 2ip, разрешение расхождений и кэширование относятся к Hestia и внешнему API. Их проверка не является исследованием API Keenetic и не входит в этот минимум. Совместимость полного набора правил, приоритет доменных правил и поведение при сбоях 2ip проверяются на этапе реализации/приёмки общей логики. Отсутствие штатного GeoIP API само по себе не блокирует коннектор маршрутизации. Ранее подтверждённых аппаратных результатов GeoIP нет; новый статус успешной проверки не присваивается.
