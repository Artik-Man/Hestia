# Развёртывание схемы 3 на MacBook

Стенд состоит из двух Debian 12 ARM64 ВМ Lima на MacBook с Apple Silicon. Гестия принимает трафик Keenetic через WireGuard и обслуживает веб-панель. Вторая ВМ играет роль клиента. Обе получают собственные DHCP-адреса от Keenetic через Wi-Fi-мост. [Схема сети](architecture.md#3-лабораторная-схема--гестия-в-вм-на-macbook) · [Проверки на действующем стенде](validation.md#схема-3--wireguard-через-lima-вм-на-macbook).

## 1. Подготовить Mac

Выполняйте команды из корня репозитория. На стенде использована Lima 2.2.1 с драйвером VZ. На Mac нужны Git, средства сборки Xcode Command Line Tools, Go по версии из `go.mod`, Node.js и npm по требованиям `frontend/package.json`. На первом запуске понадобится сеть для скачивания образа, пакетов и зависимостей фронтенда.

Для нового стенда задайте постоянный каталог состояния и отдельные имена. Сохраните эти переменные для следующих запусков.

```sh
export LIMACTL="$(command -v limactl)"
export LIMA_HOME="$HOME/.lima-hestia"
export HESTIA_GATEWAY_VM=hestia-s3-gateway
export HESTIA_CLIENT_VM=hestia-s3-client
```

Действующий личный стенд использует имена `hestia-stage1` и `hestia-test-client` и отдельный `LIMA_HOME`. Команды управления из этой инструкции рассчитаны на новые имена. Для настройки или проверки личного стенда требуется отдельное разрешение владельца.

Проверьте через `networksetup -listallhardwareports`, что Wi-Fi использует `en0`. В конфигурации Lima `$LIMA_HOME/_config/networks.yaml` сеть `bridged` должна иметь `mode: bridged` и имя фактического Wi-Fi-интерфейса. Для отдельного нового каталога Lima создаёт стандартную конфигурацию. Если Wi-Fi использует другой интерфейс, укажите его в записи `bridged`, затем сгенерируйте правило sudoers для этой конфигурации.

```sh
bash deploy/scheme3/bridge.sh
```

Скрипт собирает отсутствующий `socket_vmnet` v1.2.2 в отдельном каталоге, устанавливает его под `/opt/socket_vmnet`, генерирует правило через `limactl sudoers`, проверяет его через `visudo` и устанавливает с владельцем `root:wheel` и правами `0444`. Существующее несовместимое правило требует ручной сверки. Эти действия относятся к macOS.

## 2. Создать ВМ и проверить LAN

```sh
bash deploy/scheme3/host.sh start "$HESTIA_GATEWAY_VM"
bash deploy/scheme3/host.sh start "$HESTIA_CLIENT_VM"
for vm in "$HESTIA_GATEWAY_VM" "$HESTIA_CLIENT_VM"; do
    "$LIMACTL" shell "$vm" -- ip -4 -br addr show lima0
    "$LIMACTL" shell "$vm" -- ip route get 1.1.1.1
done
```

В лаборатории шлюз получил `192.168.1.133`, клиент — `192.168.1.124`. При повторении используйте выданные адреса и закрепите их за соответствующими MAC в Keenetic. Обе ВМ должны видеть роутер через `lima0`. Проверьте соединение с веб-интерфейсом с каждой ВМ:

```sh
for vm in "$HESTIA_GATEWAY_VM" "$HESTIA_CLIENT_VM"; do
    "$LIMACTL" shell "$vm" -- curl --noproxy '*' --interface lima0 --max-time 5 \
        -sS -o /dev/null -w '%{http_code}\n' http://192.168.1.1/
done
```

Ожидается HTTP 200 или перенаправление на страницу входа. При тайм-ауте проверьте `ip neigh show dev lima0`. На действующем стенде одна ВМ имела адрес, но показывала `INCOMPLETE` для роутера. Перезапуск только этой ВМ через `limactl stop` и `limactl start` восстановил ARP. Перед настройкой маршрутов добейтесь связности обеих ВМ с Keenetic.

## 3. Установить Гестию на чистую ВМ

Сценарий рассчитан на лабораторную LAN `192.168.1.0/24`. Проверьте отсутствие пересечений с туннельной сетью `10.253.241.0/30`, TUN-сетью `172.30.0.0/30` и других назначений таблиц 200 и 201. На роутере действующего стенда диапазон туннеля уже занят. Для параллельного полного прогона нужен отдельный лабораторный роутер с этим планом адресации. Команда update обслуживает только шлюзы, подготовленные этими скриптами. ВМ с вручную установленными службами разворачивают отдельно и переключают клиента после проверки.

```sh
bash deploy/scheme3/host.sh install "$HESTIA_GATEWAY_VM"
```

На шлюзе используются вход `wg-keenetic`, группа `default`, выход `keenetic-direct` через `lima0` и пустой список доменных правил. Таблица 200 направляет входящие из WireGuard пакеты в TUN. Таблица 201 возвращает ответы в WireGuard, включая маршрут к `10.253.241.1/32`: Keenetic может подставлять этот адрес вместо адреса тестового клиента. Панель читает `/etc/hestia/snapshot.json`. Статус служб и ответ API проверьте из гостя:

```sh
"$LIMACTL" shell "$HESTIA_GATEWAY_VM" -- systemctl is-active \
    wg-quick@wg-keenetic hestia-sing-box hestia hestia-panel
```

Откройте в браузере `http://<LAN-IP Гестии>:8080/`. На действующем стенде это [панель Гестии](http://192.168.1.133:8080/). В разделе «Группы и правила» должен появиться доступный выход `keenetic-direct`.

### Пакет userspace-коннектора WireGuard/AmneziaWG

Сборка `host.sh install|update` дополнительно собирает на Mac ARM64-версию `amneziawg-go` с upstream tag `v3.1.20260828` и полным Git commit `b5928efb6ca19f0153958460c3d141f04abc5c2e`. Для приложения и runtime закреплён и проверяется Go `1.27.3` для Darwin ARM64; сборка запрещает автозагрузку другого toolchain. Исходники `amneziawg-tools` закреплены на tag `v3.1.20260812`, commit `ee0f0a9aa34ff0a0da4b3433b9512781cfe02843`; на Debian ARM64 из них собирается `awg`. `host.sh` проверяет точный commit до сборки и вычисляет SHA-256 для переносимых бинарного файла и архива исходников; `host-apply.sh` сверяет эти суммы перед установкой. Для сборки `awg` нужны пакеты `build-essential` в госте. Никакой модуль ядра не устанавливается.

На шлюзе runtime и утилита устанавливаются соответственно в `/usr/local/lib/hestia/amneziawg-go` и `/usr/local/bin/awg`. Профили и метаданные размещаются в `/etc/hestia/awg`, каталог принадлежит `root:root` с режимом `0700`, секретный профиль — `0600`. Панель запускает только фиксированные helper-режимы через отдельную системную учётную запись `hestia-panel`; sudoers разрешает `-awg-check`, `-awg-create`, `-awg-update`, `-awg-list` и `-awg-delete`. Секрет передаётся helper через stdin. Панель не получает ambient capabilities; узкий systemd capability bounding set нужен только для того, чтобы sudo helper мог выполнять разрешённые root-операции. `hestia-snapshot` даёт панели чтение `snapshot.json`, а root helper использует общий `/run/hestia-install.lock`.

Для сохранённого готового подключения используется отдельный отключённый по умолчанию `hestia-awg.service`: он запускает фиксированный `hestia -awg-runtime`, работает от root с `CAP_NET_ADMIN` и `CAP_CHOWN`, читает `/etc/hestia` и пишет только в `/run/hestia-awg`. Tmpfiles создаёт `/run/hestia-awg` как `root:hestia-snapshot` с режимом `0750` и heartbeat `health.json` с режимом `0640`; readiness и таблица маршрутов остаются root-only с режимом `0600`. На старте `hestia-binding-recovery.service` сначала восстанавливает незавершённое поколение; если в профиле есть готовый AWG-коннектор, recovery запускает AWG unit и ждёт readiness-маркер до продолжения. `hestia-binding-watch.path` и sing-box стартуют после recovery. Unit AWG не включается напрямую в автозапуск, чтобы шлюз без AWG-коннектора продолжал запускаться штатно.

Сохранённый статус `configured` не означает, что подключение активно: добавление выхода в группу, управление постоянным сервисом и публикация маршрута выполняются только как одна транзакция с откатом и проверками fail-closed для IPv4/IPv6. Маркер готовности появляется после handshake и egress-проверки. До завершения этой транзакции установка не подтверждает передачу пользовательского трафика через AWG.

При первой установке или обновлении `host-apply.sh` до включения managed-профиля компилирует seed `guest-profile.json` во временный каталог и сравнивает кандидат с текущими `snapshot.json` и `sing-box.json`. Проверка требует совпадения полного snapshot и routing-семантики backend, включая TUN `hestia0`, `keenetic-direct` на `lima0`, selector default и `route.final=default`. При несовпадении обновление прекращается до изменения сервисов и конфигурации. При совпадении скрипт добавляет `/etc/hestia/profile.json` и контрольные суммы, сохраняя байты snapshot/backend неизменными; `.installer-managed` публикуется последним. Для повторного запуска установленное поколение проверяется через `profile.py --validate-managed`. Профиль и backend становятся `root:root 0600`, snapshot остаётся `root:hestia-snapshot 0640`.

На ошибке установщика rollback удаляет только те managed-profile артефакты, которые совпадают с seed этого bootstrap и сохранённой суммой backend; пользовательские или изменённые файлы не удаляются. Прямой вызов миграции на ВМ не выполняйте: сначала проверьте исходный diff, а само развёртывание стенда запускается отдельным согласованным шагом.

## 4. Подключить Keenetic

После установки профиль уже сохранён в `private/<имя ВМ>-keenetic.conf` под корнем проекта с закрытыми правами. Файл содержит ключ Keenetic. При необходимости повторите экспорт:

```sh
bash deploy/scheme3/host.sh export-peer "$HESTIA_GATEWAY_VM"
```

Каталог `private/` исключён из Git. В Keenetic выберите «Другие подключения» → WireGuard → «Загрузить из файла». Проверьте endpoint `<LAN-IP Гестии>:51827`. Адрес Keenetic внутри туннеля — `10.253.241.1/30`, адрес Гестии — `10.253.241.2/30`. Включите профиль и проверьте рукопожатие с обеих сторон:

```sh
"$LIMACTL" shell "$HESTIA_GATEWAY_VM" -- sudo wg show wg-keenetic
```

Для опыта со всем IPv4-трафиком подготовьте отдельную политику Keenetic с единственным выходом через Гестию. В обычной политике оставьте выход провайдера для MacBook и самой Гестии, чтобы исходящие соединения шлюза могли вернуться в интернет. В профиле WireGuard включите «Использовать для выхода в интернет», в разрешённых IPv4-подсетях пира задайте `0.0.0.0/0` и назначьте отдельную политику только зарегистрированной клиентской ВМ. Проверьте, что у основной политики приоритет по-прежнему имеет провайдер.

## 5. Проверить результат и обновить сборку

```sh
python3 experiments/scheme3/probe.py
```

Скрипт с Mac делает два запроса с клиентской ВМ и одновременно наблюдает соединения на Гестии. Код 0 означает, что оба сайта дали HTTP 2xx/3xx и оба потока прошли через WireGuard и вышли через `lima0`. На исходном стенде `ya.ru` прошёл через Гестию, а `example.com` открылся в обход неё, поэтому проверка вернула 1. Причина выбора маршрута для второго адреса открыта. Проверка охватывает HTTPS по IPv4.

Для штатного обновления сборки из текущего рабочего дерева:

```sh
bash deploy/scheme3/host.sh update "$HESTIA_GATEWAY_VM"
```

После обновления откройте панель и повторите проверку. Для остановки лаборатории сначала верните клиентскую ВМ в обычную политику Keenetic, затем отключите лабораторный WireGuard-профиль. Остановите обе ВМ командами `"$LIMACTL" stop "$HESTIA_CLIENT_VM"` и `"$LIMACTL" stop "$HESTIA_GATEWAY_VM"`. Диски сохранятся для следующего запуска.
