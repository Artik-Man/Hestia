# Физические и виртуальные подключения

В разделе «Подключения» отображаются прямые транспорты, Wi-Fi и виртуальные подключения. Физические Ethernet-интерфейсы не выводятся отдельной таблицей. Инвентаризация физических интерфейсов остаётся read-only backend-источником для сетевых операций и Wi-Fi; сама по себе она не назначает интернет-выход и не меняет сетевые настройки.

## Список прямых транспортов

Реализовано в панели и backend; проверка на Keenetic после установки новой сборки ещё не проводилась.

Таблица «Прямые подключения» показывает прямые выходы, независимо от их включения в группу и наличия физического backing device. Служебный входной канал скрыт из прямых и виртуальных подключений по роли `input`; системная конфигурация и сохранённые ссылки не удаляются. Backend сообщает панели роль канала (`input` или `output`); пользовательские подписи — «Вход» и «Выход». Внутренний ID остаётся только для серверных профилей и маршрутов.

Строка показывает роль, назначение и доступность. Доступность выхода берётся из состояния группы с тем же ID; для входа или выхода без такого состояния показывается «Нет данных». Link state физического адаптера не используется как готовность всего канала. Платформенные входы нельзя переименовывать или добавлять как выход группы.

Таблицы Wi-Fi и виртуальных VPN-подключений остаются. Обычные прямые подключения сохраняют свои отображаемые имена; платформенные каналы нельзя переименовывать. Удаление транспорта со страницы недоступно. Существующий API физической инвентаризации остаётся для Wi-Fi и других потребителей, но список каналов не зависит от наличия соответствующего kernel netdev в его ответе.

### Критерии поведения

1. На странице подключений показаны выходы; служебный вход не отображается ни в прямых, ни в виртуальных подключениях. Названия выходов берутся из API.
2. Роль платформенного канала приходит из backend; frontend не сопоставляет каналы с платформами и внутренними ID.
3. Физические Ethernet-интерфейсы не выводятся отдельной таблицей; Wi-Fi и таблица виртуальных VPN-подключений сохранены.
4. Доступность берётся из состояния выхода с тем же стабильным ID. Для кандидата без такого состояния показывается «Нет данных»; физический carrier не используется как readiness OpkgTun.
5. Канал с ролью `input` не показывается в списке подключений и не предлагается как выход группы.
6. Платформенный выход доступен для группы; изменение групповой очередности не раскрывает внутренний routing ID.
7. Обычные direct-транспорты сохраняют переименование; платформенные каналы не переименовываются, удаление transport-кандидата из панели недоступно.

Реализация использует каталог direct-кандидатов и snapshot групп. `npm run format`, `npm run lint`, `npm run build` и кросс-сборка Go для Linux ARM64 Keenetic прошли. Browser-тесты и проверка на физическом Keenetic не запускались. `make docs-check` остановился: в окружении отсутствует `shfmt`.

Wi-Fi работает в режиме клиента. Пользователь выбирает адаптер и диапазон 2,4 или 5 ГГц, вводит SSID и пароль. Сведения, возвращаемые в таблицу, исключают пароль. Виртуальные подключения сохраняют редактор конфигурации, выбор транспорта и действия WireGuard.

Wi-Fi-профиль использует NetworkManager. При сохранении шлюз активирует профиль на выбранном адаптере и ждёт настройки IPv4. Для профиля создаётся отдельная таблица маршрутов. Назначение нового физического подключения выходом группы остаётся отдельной операцией. На load1 проверено обнаружение Ethernet; испытание Wi-Fi с точкой доступа требует адаптера. [Протокол](../../experiments/physical-connections/README.md).

## Read-only Ethernet-инвентаризация

### Контракт

Ethernet-коннектор только обнаруживает физические проводные интерфейсы и сообщает их стабильный в пределах платформы ID, наличие, link state и назначенные Hestia прямые выходы. Для Linux-интерфейсов `carrierState` принимает `up`, `down` или `unknown`; совместимое поле `online` истинно только при `carrierState=up`. Ошибка или отсутствие carrier-наблюдения остаётся `unknown`, а не превращается в наблюдённый `down`. Порт с отключённым кабелем остаётся в перечне. `down` означает только отсутствие активного link в момент чтения и не означает, что разъём пустой. Привязка прямого выхода выполняется отдельно по ID интерфейса.

Инвентаризация read-only: она не назначает разъём как WAN, не меняет сегмент/VLAN, IP-адрес, DHCP, скорость, дуплекс, расписание порта или состояние интерфейса. Эти операции не входят в первый Ethernet-коннектор и требуют отдельных критериев и решения Product Owner.

На Keenetic RCI-идентификаторы физических портов и имена kernel-интерфейсов образуют отдельные пространства имён. RCI port inventory не используется для отображения Ethernet в панели. Имя Keenetic-провайдера можно показывать у текущего kernel-интерфейса default route только когда RCI называет ровно одно активное подключение default route, а Linux сообщает ровно один соответствующий default-route интерфейс; при неоднозначности панель не приписывает имя провайдера. Отображаемое имя выбирается в порядке: название прямого подключения Hestia, подтверждённое имя провайдера Keenetic, kernel interface name.

Linux-реализация уже читает физические интерфейсы и carrier. На Keenetic подтверждён token-auth HTTP RCI с JSON: `GET /rci/show/interface` к loopback `127.0.0.1:79` вернул пять уникальных физических записей `type=Port` с ID `GigabitEthernetN/M`. В read-only снимке `GigabitEthernet0/0` и `/0/3` были down; `/0/1` и `/0/2` — up на 100/full; `GigabitEthernet1/0` — up на 1000/full. Из других полей сохранялись только ID, link, speed и duplex. Связь LAN1 ↔ `GigabitEthernet0/0` подтверждена отдельным controlled link down/up/down; другие физические гнёзда по одному снимку не сопоставляются. [Отчёт Ethernet и свидетельство](../../experiments/keenetic-ethernet-management-20261106/README.md) · [минимальный план API](../keenetic-platform-minimal.md).

### Контракт инвентаризации Ethernet

Контракт API физической инвентаризации сохраняется: Linux и Keenetic backend отдают kernel-интерфейсы с `kind=ethernet`, `present`, `carrierState`, `online` и `exitIds`, но панель больше не выводит их отдельной таблицей. `carrierState=unknown` означает, что link state определить не удалось, а `online` истинно только для `up`. На Keenetic RCI port inventory и kernel-инвентарь остаются отдельными пространствами имён. Проверка инвентаря не меняет сетевую конфигурацию.

Авторизованный RCI JSON и разбор физических `Port`-записей подтверждены на KN-1012; типизированный Go-коннектор возвращает ID, link и доступные speed/duplex. Kernel inventory и carrier Keenetic читаются отдельно через sysfs по Linux-имени устройства; отсутствующее, нечитаемое или некорректное значение выдаётся как `unknown`, watcher выбирает выход fail-closed и публикует дедуплицированное предупреждение. Прямая связь `GigabitEthernetN/M` с kernel interface name не установлена. Для отображения имени текущего провайдера допускается только однозначная корреляция logical RCI default route с единственным Linux main default-route interface; это не считается аппаратным соответствием порта и не влияет на маршрутизацию. Другие системные операции не подтверждены. Общая очередность описана в [спецификации платформенных коннекторов](keenetic-connectors.md).

## Включение виртуальных подключений

По запросу от 13 ноября 2026 года в таблице виртуальных подключений добавляется ToggleSwitch. Выключение — административное действие: подключение остаётся в списке со своими параметрами, группой и очередностью, но не переносит трафик. В колонке доступности показывается «Отключено», независимо от прежнего состояния проверки. Повторное включение возвращает подключение к обычной проверке доступности; оно не означает автоматически успешную связь.

Критерии приёмки:

1. Переключатель доступен для виртуальных подключений WireGuard, AmneziaWG и Hysteria 2. Исходное состояние ранее сохранённых подключений — включено.
2. Выключенное подключение исключено из передачи трафика и не может быть использовано как транспорт другого VPN. Если разрешённого выхода нет, трафик блокируется.
3. Состояние сохраняется после перезапуска и редактирования профиля; настройки и принадлежность группе сохраняются.
4. Интерфейс подтверждает изменение только после ответа backend. При ошибке сохраняет прежнее положение и сообщает о сбое; повторный запрос для той же строки блокируется до завершения.
5. Служебный вход остаётся скрытым; обычные прямые выходы не получают этот переключатель.

## Автоматическое обновление состояния

В разделе «Подключения» ручные кнопки «Обновить» и «Обновить состояния» убраны. Пока раздел открыт, панель каждые 3 секунды запрашивает состояние виртуальных подключений и прямого выхода провайдера. Незавершённые чтения не прерываются очередным тиком; формы и несохранённый ввод сохраняются. При уходе с раздела опрос прекращается. Ошибки чтения не меняют административное состояние подключения.

## Исправление переключения VPN — 13 ноября 2026 года

Проверяемые критерии исправления `0.1.15`:

- Во время применения состояния связанные фоновые чтения не конкурируют с записью. Временная занятость конфигурации не показывается как потеря состояния и не сбрасывает строки; краткая коллизия чтения и изменения обрабатывается без перезагрузки страницы.
- Пользователь видит, что переключение выполняется. После подтверждения или завершённого отказа переключатель снова доступен; повторное включение не требует перезагрузки страницы. Если HTTP-подтверждение задержалось, интерфейс проверяет результат именно этой попытки по её UUID. Подтверждённое завершение освобождает переключатель как после успеха, так и после отката; истечение времени само по себе не разрешает повторную запись. Терминальная сетевая ошибка отображается как неподтверждённое состояние с перечитыванием данных.
- Административное включение допускает временно недоступный VPN-сервер: состояние сохраняется как включённое, а доступность остаётся независимой. Отсутствие handshake не превращает подключение обратно в административно отключённое.
- До готовности сетевой защиты и во время недоступности peer трафик не утекает в обычный маршрут. Строгая проверка нового или изменённого VPN-профиля сохраняется. Ошибка установки локальных guard/маршрутов по-прежнему отклоняет операцию.
