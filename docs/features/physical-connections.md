# Физические и виртуальные подключения

В разделе «Подключения» три таблицы: Ethernet, Wi-Fi и виртуальные подключения. Ethernet-адаптеры определяет шлюз. Отключение кабеля меняет состояние порта; настроенный прямой выход связывается с адаптером по имени интерфейса. Обнаружение само по себе не назначает порт интернет-выходом и не меняет сетевые настройки.

Wi-Fi работает в режиме клиента. Пользователь выбирает адаптер и диапазон 2,4 или 5 ГГц, вводит SSID и пароль. Сведения, возвращаемые в таблицу, исключают пароль. Виртуальные подключения сохраняют редактор конфигурации, выбор транспорта и действия WireGuard.

Wi-Fi-профиль использует NetworkManager. При сохранении шлюз активирует профиль на выбранном адаптере и ждёт настройки IPv4. Для профиля создаётся отдельная таблица маршрутов. Назначение нового физического подключения выходом группы остаётся отдельной операцией. На load1 проверено обнаружение Ethernet; испытание Wi-Fi с точкой доступа требует адаптера. [Протокол](../../experiments/physical-connections/README.md).

## Ethernet-коннектор

### Предлагаемый контракт

Ethernet-коннектор только обнаруживает физические проводные интерфейсы и сообщает их стабильный в пределах платформы ID, наличие, link state и назначенные Hestia прямые выходы. Для Linux-интерфейсов `carrierState` принимает `up`, `down` или `unknown`; совместимое поле `online` истинно только при `carrierState=up`. Ошибка или отсутствие carrier-наблюдения остаётся `unknown`, а не превращается в наблюдённый `down`. Порт с отключённым кабелем остаётся в перечне. `down` означает только отсутствие активного link в момент чтения и не означает, что разъём пустой. Привязка прямого выхода выполняется отдельно по ID интерфейса.

Инвентаризация read-only: она не назначает разъём как WAN, не меняет сегмент/VLAN, IP-адрес, DHCP, скорость, дуплекс, расписание порта или состояние интерфейса. Эти операции не входят в первый Ethernet-коннектор и требуют отдельных критериев и решения Product Owner.

На Keenetic RCI-идентификаторы физических портов и имена kernel-интерфейсов образуют отдельные пространства имён. Пока не подтверждено сопоставление конкретного порта с устройством ядра, панель показывает два перечня раздельно и не приписывает портам выходы Hestia.

Linux-реализация уже читает физические интерфейсы и carrier. На Keenetic подтверждён token-auth HTTP RCI с JSON: `GET /rci/show/interface` к loopback `127.0.0.1:79` вернул пять уникальных физических записей `type=Port` с ID `GigabitEthernetN/M`. В read-only снимке `GigabitEthernet0/0` и `/0/3` были down; `/0/1` и `/0/2` — up на 100/full; `GigabitEthernet1/0` — up на 1000/full. Из других полей сохранялись только ID, link, speed и duplex. Связь LAN1 ↔ `GigabitEthernet0/0` подтверждена отдельным controlled link down/up/down; другие физические гнёзда по одному снимку не сопоставляются. [Отчёт Ethernet и свидетельство](../../experiments/keenetic-ethernet-management-20261106/README.md) · [минимальный план API](../keenetic-platform-minimal.md).

### Предлагаемые критерии приёмки

1. На каждой платформе инвентарь возвращает физические Ethernet-интерфейсы с ID, `kind=ethernet`, `present`, `carrierState`, `online` и `exitIds`; виртуальные интерфейсы и Wi-Fi не выдаются за Ethernet. `carrierState=unknown` означает, что link state определить не удалось, а `online` истинно только для `up`.
2. Для KN-1012 RCI-ответ разбирается как JSON и однозначно выбирает физические порты среди вложенных bridge/интерфейсов. На этой модели известная связь LAN1 ↔ `GigabitEthernet0/0` сверяется с сохранённым наблюдением link `down → up → down`; прочие порты из одного link-down снимка не объявляются пустыми.
3. Неполный, неизвестный или несовместимый ответ возвращает диагностируемую ошибку/неподдерживаемое состояние, а не выдуманный `offline`.
4. Проверка инвентаря не меняет сетевую конфигурацию Keenetic. Связь `exitIds` отражает только Hestia-конфигурацию, а не предположение из имени порта.

Авторизованный RCI JSON и разбор физических `Port`-записей подтверждены на KN-1012; типизированный Go-коннектор возвращает ID, link и доступные speed/duplex. Kernel inventory и carrier Keenetic читаются отдельно через sysfs по Linux-имени устройства; отсутствующее, нечитаемое или некорректное значение выдаётся как `unknown`, watcher выбирает выход fail-closed и публикует дедуплицированное предупреждение. Сопоставление `GigabitEthernetN/M` с kernel interface name не установлено; интерфейс и API сохраняют пространства имён раздельными и не отображают неподтверждённые связи. Другие системные операции не подтверждены. Общая очередность описана в [спецификации платформенных коннекторов](keenetic-connectors.md).
