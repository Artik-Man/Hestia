Последнее обновление: 2026-11-04

## 1. Цель и продуктовый контекст

Добавить управляемый userspace-коннектор, чтобы Гестия могла использовать существующий профиль обычного WireGuard или AmneziaWG как выход выбранной группы. Для обоих режимов применяется один runtime `amneziawg-go`; отдельная реализация протокола WireGuard внутри контроллера не добавляется. Гестия управляет жизненным циклом подключения и направлением потоков, а runtime — протоколом VPN. В рабочем дереве реализованы импорт, проверка, транзакционное сохранение/удаление, запуск выхода и выбор группы. Независимое ревью и проверка на `hestia-stage1` ещё не выполнены; функция не считается принятой до этих проверок.

### Метрики успеха и продуктовая аналитика

Телеметрия продукта не добавляется. Функция считается работоспособной, когда тестовый поток и DNS проходят через AWG-пир, а при отказе туннеля трафик не утекает в другой выход без разрешённой политикой группы.

## 2. Область работ

### Согласованная поставка

Полный вертикальный путь для подключения WireGuard или AmneziaWG 3.1: импорт файла профиля через панель, проверка, безопасное хранение, запуск отдельного коннектора, подключение выхода к группе, индикация состояния и применение существующей политики выбора/блокировки. Оба варианта используют один `amneziawg-go` userspace runtime; AWG-параметры необязательны для обычного WireGuard-профиля. Проверять поведение можно на `hestia-stage1`; изменения Keenetic и основного маршрута ВМ запрещены в этой работе.

### Согласованные границы

**Входит:** Linux ARM64; обычный WireGuard-профиль и профиль AmneziaWG 3.1 из предоставленного пользователем файла; один userspace runtime `amneziawg-go`; импорт и строгая проверка обоих вариантов подключения; назначение группе и использование как выхода; интеграционная проверка на `hestia-stage1`. В первой версии можно хранить несколько профилей, но одновременно в состоянии `ready` может находиться только один коннектор на экземпляр Гестии.

**Не входит:** запуск AmneziaVPN на macOS-хосте; любые изменения Keenetic; изменение основного маршрута Linux; поддержка других протоколов; AmneziaWG kernel module. Product Owner не хочет использовать kernel module; при проблемах userspace сначала исследуются альтернативы userspace. Возврат к kernel module потребует отдельного согласования.

## 4. Системный анализ

### Известное текущее состояние

- Панель импортирует `.conf`, вызывает сгенерированные API-сервисы для проверки и управления подключениями и отображает только публичные метаданные. Ответы API не содержат приватный конфиг.
- Привилегированный helper проверяет профили через отдельный временный userspace-интерфейс. Операции создания, обновления и удаления входят в журнал `binding.Engine`, который связывает секретное дерево, `profile.json`, backend, snapshot и состояние сервисов.
- Runtime использует выделенный `awg0`; sing-box направляет AWG direct outbound через `bind_interface` и routing mark. Внешний сокет AWG `FwMark` остаётся нулевым. Отдельные таблицы IPv4/IPv6 и unreachable guards реализованы, но их численные параметры и поведение ещё требуют независимого ревью и испытания на Linux.
- Здоровье выхода подтверждается handshake и привязанной DNS/HTTPS-пробой. Сервис публикует приватный `ready` marker для транзакции и отдельный root-owned, group-readable `health.json`; контроллер считает AWG недоступным при отсутствующем или просроченном heartbeat и применяет порядок группы/deny.
- `deploy/profile.py` поддерживает обычный WireGuard endpoint, метаданные userspace-коннектора и enriched schema v2 для существующего scheme3 TUN/direct backend. Компилятор проверяет семантическое совпадение схемы с установленным backend.
- Фактическая совместимость предоставленного профиля, runtime на целевой ВМ и сетевой выход ещё не проверялись в этом ходе.
- `docs/requirements.md` перечисляет AmneziaWG среди клиентских VPN-подключений первого выпуска.
- Архитектурное направление по коннекторам описано в `docs/architecture.md#vpn-подключения-через-управляемые-коннекторы`.
- Пользовательский AWG-профиль содержит ключи и параметры поколения 3.1; значения секретов не копируются в этот документ или память задачи.

### Сценарии и открытые решения

1. Администратор создаёт профиль AWG 3.1 или импортирует конфигурационный файл.
2. Backend валидирует и сохраняет секреты отдельно от отображаемой модели подключения.
3. Коннектор поднимает туннель без изменения основного маршрута ВМ.
4. Проверка доступности привязана к конкретному выходу и не получает ложноположительный результат через LAN.
5. Администратор назначает подключение группе; поведение при отказе подчиняется общей политике группы.

Состояние «проверено» и состояние «доступно для трафика» различаются: тест соединения сам по себе не меняет назначение в группе. Здоровье выхода должно подтверждаться не только последним handshake, но и привязанной пробой/прохождением трафика.

## 5. Архитектура и технический выбор — предложение

Основной кандидат — `amneziawg-go v3.1.20260828` с AWG-инструментами `v3.1.20260812` как единый управляемый userspace-коннектор на Linux ARM64 для обычного WireGuard и AmneziaWG 3.1. Product Owner подтвердил, что этот runtime применим к обоим форматам. Это согласуется с официальным описанием `amneziawg-go` как форка `wireguard-go`, расширенного параметрами AmneziaWG; AWG-параметры задают совместимость с обфусцированным peer, а их отсутствие оставляет обычный WireGuard-режим. Официальный README описывает Linux TUN runtime, AWG tools, Header Protection и остальные параметры 3.x; Header Protection требует значения S1–S4 не меньше 12. Конкретный профиль проверяется без раскрытия значений. Если runtime не принимает профиль или не устанавливает соединение, сначала исследуются другие userspace-библиотеки/runtime. Модуль ядра исключён из решения и не рассматривается как план Б; к нему можно вернуться только по отдельному запросу Product Owner. [amneziawg-go v3.1.20260828](https://github.com/amnezia-vpn/amneziawg-go/tree/v3.1.20260828) · [amneziawg-tools v3.1.20260812](https://github.com/amnezia-vpn/amneziawg-tools/releases/tag/v3.1.20260812)

Секретный профиль хранится отдельно в root-owned файле с режимом `0600`; публичная модель и snapshot содержат только метаданные, включая тип AWG-коннектора для контроля heartbeat. Huma API имеет типизированные операции проверки, создания, обновления, чтения и удаления. Создание/обновление сначала подготавливает runtime и проверяет bound egress, затем публикует конфигурацию и selector; общий journal позволяет откатить профиль, secret tree, backend, snapshot, маршруты и сервисы. Непроверенный runtime не выдаётся как здоровый. В один момент времени разрешён максимум один профиль со статусом `ready`; сохранённые профили сверх этого остаются `configured`. UI освобождает ссылку на файл после закрытия формы; автоматическое стирание содержимого из памяти браузера не гарантируется.

Сетевой вариант реализован как userspace интерфейс без установки main default route; sing-box направляет выбранный выход через `awg0`, routing mark и отдельную таблицу с unreachable default. IPv6 отмеченный поток блокируется отдельной unreachable guard; внешний UDP endpoint AWG остаётся на underlay, а UAPI `FwMark` внешнего сокета должен быть нулевым. Используемые кандидаты IPv4 mark/table/rule — `0x202`/`202`/`1002`; code-level preflight проверяет конфликты и владение. Их совместимость и фактические пути ещё не подтверждены на отдельной Linux-ВМ. Основной маршрут и настройки Keenetic в этом ходе не менялись.

Не передавать пользовательский конфиг непосредственно в `awg-quick`, пока не исключены hook-поля и управляющие директивы: парсер должен разрешать только поддерживаемые поля, не исполнять команды из файла и писать служебную конфигурацию атомарно с закрытыми правами.

### Типизация и контракты

Go API использует типизированные DTO и возвращает только метаданные. Источник контракта — зарегистрированные Huma операции; после финальных правок нужно повторно сгенерировать OpenAPI и TypeScript-клиент.

### Матрица проверок и результаты

Согласованная стратегия: unit/API тесты с контролируемым fake runtime, затем проверка на `hestia-stage1` с предоставленным профилем, фактическим AWG handshake, DNS и HTTP(S) запросом, сравнением маршрутов до/после и проверкой блокировки при остановке AWG. Keenetic не меняется. Для панельного сценария добавить клавиатурную E2E-проверку импорта и настройки подключения.

| ID критерия | Сценарий | Ожидаемое свидетельство | Результат |
|---|---|---|---|
| WG-1, AWG-1 | Импорт/парсер — обычный WG и AWG 3.1, неизвестные и недопустимые поля | Synthetic parser/API tests; отсутствие секретов в ответах; неизвестные директивы отклонены | Реализовано локально; целевой runtime/E2E ждёт проверки |
| AWG-2…AWG-4 | Проверить оба режима, сохранить выход и направить контрольный поток | Handshake, DNS и внешний IP/захват подтверждают выбранный туннель | Локальные fake-runtime/transaction тесты; сетевое свидетельство не собрано |
| AWG-5…AWG-6 | Сверить основной маршрут и остановить коннектор | Default route и Keenetic WG неизменны; нет утечки через direct; секреты не выводятся | Route guards и heartbeat failover реализованы; независимое ревью и stage1 тест ещё не выполнены |

## 7. Ревью и передача

- Ревью кода: выполнено статически 4 ноября 2026 года; замечания по редактированию профиля и смене файла во время проверки исправлены и повторно закрыты.
- Ревью ИБ: выполнено статически 4 ноября 2026 года. Открытый P1: конфиг с приватным ключом передаётся по HTTP; до использования реальных профилей требуется TLS. Открытый P2: обновление не защищено версией/ETag от конкурентной перезаписи.
- Проверка поведения: фронтенд собран и экран осмотрен в локальном preview. Выбор файла и успешный ответ API браузером не подтверждены; preview не предоставляет `/api/awg`. Испытание на изолированном шлюзе ожидается; личную ВМ не трогать до отдельного шага архитектора/тестировщика.
- Остаточные риски: обмен секретом, фактический импорт, runtime/профиль и маршрутная изоляция не прошли полноценную сквозную проверку.
- Статус: реализация по согласованной спецификации.
