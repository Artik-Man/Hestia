# Надёжное обновление Hestia IPK на Keenetic — задача KEENETIC-IPK-UPDATE-01

## Статус

Спецификация сформирована по сбоям установки на KN-1012 11 ноября 2026 года.
По прямому поручению Product Owner от 11 ноября устранить причину и установить
сборку, текущая реализация ограничена исправлением несовпадающих сроков
ожидания supervisor и boot recovery; транзакционный updater из полного плана
ниже остаётся отдельной незавершённой работой.
Текущая ручная процедура и ограничения описаны в
[инструкции поставки](../../scripts/deploy/keenetic-ipk.md), а фактический
неудачный прогон — в [отчёте сборки и установки](../../experiments/keenetic-ipk-packaging/README.md#неудачное-обновление-keenetic-11-ноября-2026-года).

## Цель

Сделать обновление и откат Keenetic IPK предсказуемой транзакцией, которая либо
завершает обновление с готовым supervisor, либо автоматически возвращает
последнюю рабочую версию и сохраняет доступ к пользовательской конфигурации.
После отказа оператор должен получить точную причину и однозначный безопасный
следующий шаг.

## Наблюдавшиеся проблемы

Подтверждены в прогоне 11 ноября:

1. Ошибка Go `exec: Stdout already set` не была выявлена локальной сборкой и
   стала причиной первого отказа запуска supervisor. Ошибка исправлена и
   покрыта узким локальным тестом.
2. Исправленный пакет завершил миграцию OpkgTun сообщением
   `ld-linux-aarch64.so.1 failed: signal: killed`. Ошибка повторилась при
   попытке `opkg configure` на сохранённой версии.
3. Установка сохранённого IPK не восстановила readiness: пакет остался
   `install user unpacked`, supervisor не поднялся, а API панели не ответил.
4. `opkg` оставил `-opkg` файлы для package defaults, отличавшихся от
   пользовательской конфигурации; решение Hestia по сверке этих файлов при
   rollback пока не автоматизировано.
5. Профиль, controller snapshot и sing-box config проходили отдельные
   read-only проверки, а IPv4/IPv6 default-route hashes сохранились. Это
   показывает, что проверка синтаксиса и сохранности главных маршрутов сама
   по себе не гарантирует завершение package lifecycle.
6. В более ранней постустановочной проблеме отсутствовал каталог
   `/opt/var/lib/hestia/dns-policy`. Текущая postinst создаёт этот каталог,
   ключ `2ip.key` после сбоя сохранился, но API 2ip после текущего сбоя не
   проверен.

Не установлено, почему loader завершился сигналом `killed`, почему supervisor
не стал ready при rollback и были ли эти отказы связаны. Kernel log не
подтвердил OOM. Недостаток памяти, конкуренция процессов и временная
недоступность зависимого компонента остаются гипотезами.

7. При последующей попытке после исправления `4b03944` init остановил запуск с
   `Hestia supervisor did not become ready` через 60 секунд. Init ожидал 60
   секунд, в то время как supervisor допускает до 47 минут на boot recovery;
   восстановление committed AWG runtime может занимать до 15 минут. Этот
   внешний таймаут мог прервать восстановление до публикации readiness.
8. Сборка с увеличенным сроком ожидания supervisor достигла readiness и
   запустила миграцию. Затем candidate backend validation остановилась ровно на
   локальном двухминутном timeout (`backend-validator timed out after
   2m1.532s`). Внешний `-enable-keenetic-ingress` допускает пять минут, поэтому
   внутренний предел был причиной второго отказа.

9. После увеличения backend timeout проверка завершилась, но миграция
   откатилась на activation smoke. Коммит `880c07c` установил convergence window
   свежих router/controller selectors в пять секунд. На устройстве в тот момент
   запускались backend, controller и AWG runtime; короткое окно является
   вероятной причиной отказа, но требует проверки после увеличения до 30 секунд.

## Границы

Задача покрывает подготовку, установку, миграцию, проверку готовности и
восстановление Keenetic Entware IPK. Она не меняет пользовательскую политику
маршрутизации и не считает сохранность default route достаточным доказательством
сохранности всех policy routes. Секреты, ключ 2ip и полный профиль не должны
попадать в логи или отчёты. Успешный пакетный lifecycle сам по себе не
подтверждает клиентский dataplane.

## Ожидаемое поведение

1. До остановки действующей версии updater проверяет хеш и архитектуру пакета,
   доступное место, preflight устройства, пользовательский профиль, обязательные
   каталоги состояния и доступность проверенного rollback IPK.
2. Все каталоги состояния, включая каталог DNS policy, создаются идемпотентно
   с проверкой symlink/non-directory conflicts и root-only правами. Пользовательские
   ключи остаются вне package defaults и переживают обновление и откат.
3. Обновление проходит явно фиксируемые состояния. После прерывания питания или
   ошибки lifecycle процедура по журналу определяет завершённую фазу и может
   безопасно продолжить или откатить её.
4. Profile migration и backend checks не оставляют сервис в неопределённом
   состоянии. Объём памяти, CPU, время ожидания и параллельная нагрузка
   ограничены и проверяются на целевом KN-1012; отказ процесса сохраняет signal,
   exit code, имя шага и безопасный stderr/stdout.
5. При отказе до подтверждённой готовности updater восстанавливает точный
   проверенный предыдущий пакет и пользовательские данные, запускает его
   supervisor, проверяет readiness и снимает transaction marker только после
   успешной проверки. Если rollback неуспешен, система сохраняет достаточно
   состояния для восстановления без повторного `opkg install/configure` вслепую.
6. Изменение package defaults не перезаписывает пользовательскую конфигурацию.
   Для каждого оставленного `-opkg` sidecar есть проверяемая политика разрешения
   конфликта, и итоговое состояние входит в отчёт транзакции.
7. Успех означает одновременно: `install user installed`, нужная версия и
   архитектура, валидные profile/controller/sing-box inputs, supervisor ready,
   API GET smoke, отсутствие transaction marker, проверенный статус 2ip без
   вывода ключа и совпадающие до/после hashes главных и управляемых Hestia
   маршрутов.

## Критерии приёмки

- Unit-тесты покрывают переходы состояния и fault injection на каждом шаге:
  preflight, backup, unpack, postinst, миграция, запуск, health check, rollback.
- Тесты процесса вызывают ошибки запуска и таймаута, включая signal-killed,
  и подтверждают, что лог сохраняет исходную причину без утечки секретов.
- Интеграционные тесты проверяют повторное выполнение и восстановление после
  прерывания в каждом состоянии; ни один сценарий не оставляет молча
  `install user unpacked`, активный marker или неизвестный набор процессов.
- На KN-1012 успешно проверяются update и rollback при включённом 2ip key:
  API показывает `configured=true` без раскрытия значения, supervisor и API
  готовы, пользовательские настройки сохранены, маршруты до/после совпадают.
- Fault-injection на целевом устройстве проверяет минимум отказ postinst,
  отказ migration, supervisor timeout и прерывание процесса. После каждого
  отказа автоматически готова предыдущая рабочая версия или выдано
  воспроизводимое документированное recovery-состояние.
- Под нагрузкой, сопоставимой с обычной работой KN-1012, migration завершается
  без убийства процесса и без выхода за согласованный бюджет RAM/CPU/времени.
- Bash hooks проходят закреплённые форматтер и ShellCheck; Go изменения проходят
  `make fmt`, `make check`, профильные unit/integration тесты и docs-check.
- Обновлены инструкция установки, спецификация, отчёт опыта и roadmap; все
  заявленные результаты связаны с evidence.

## План реализации

1. Разделить updater на явную транзакцию с журналом фаз и точкой фиксации.
2. Отделить построение и проверку migration candidate от её активации; измерить
   ресурсы каждого шага на KN-1012 и определить безопасный порядок работы служб.
3. Реализовать автоматический rollback и recovery, включая пользовательские
   conffiles, package marker и проверки маршрутов.
4. Добавить fault-injection, повторяемые локальные lifecycle tests и сценарий
   целевого аппаратного update/rollback.
5. Обновить ручную инструкцию и выполнить независимую проверку реализации,
   безопасности и результата на KN-1012.

## Открытые вопросы

- Какой процесс и конкретный migration substep был завершён сигналом `killed`?
- Как supervisor readiness сорвалась при rollback при успешных отдельных
  проверках конфигурации?
- Должен ли rollback возвращать полный предыдущий `/opt/etc/hestia` snapshot
  автоматически или сохранять изменения, внесённые пользователем после backup?
- Как измерять и ограничивать пиковую память на прошивке KeeneticOS без
  достоверной OOM записи?
- Какие из Hestia-owned policy routes должны входить в транзакционный
  fingerprint, кроме default routes?
