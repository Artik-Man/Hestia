# Платформенный модуль управления службами

Первый шаг рефакторинга в ветке `keenetic` реализует Linux-адаптер управления службами для транзакционного движка `binding`. Основание — поручение Product Owner о разделении ядра и платформенных модулей и [дорожная карта](../keenetic-roadmap.md). Модуль использует существующий `os/exec` и средства `context` Go. Новые зависимости отсутствуют.

## Граница и контракт

Движок получает интерфейс операций запуска, остановки, чтения активности и проверки наличия шаблона AWG. Идентификатор службы состоит из закрытого набора ролей и идентификатора AWG-подключения для экземпляра. Linux-адаптер преобразует роли в фиксированные имена unit и проверяет AWG ID существующим валидатором, включая исторические теги.

Запуск и остановка группы выполняются одной командой с прежним порядком аргументов. Ошибка групповой операции может означать частичное выполнение. Координатор сохраняет существующее восстановление из журнала и отдельный контекст отката. Успех запуска дополняется существующими проверками readiness и smoke.

Состояние различает `Active`, `Inactive` и `Unknown`. `systemctl is-active --quiet` с кодом 0 означает Active, код 3 означает Inactive, остальные ошибки возвращают Unknown и ошибку. Отмена контекста также даёт Unknown. Для проверки обязательной активности движок сохраняет прежнюю ошибку команды. Для решения о сохранении живого backend допускается только Active. Существующая логика снятия guards в пакете AWG остаётся самостоятельным потребителем до следующего шага миграции.

Production-конструктор `binding.Installed` подключает Linux-адаптер. Команды исполняются без shell, с лимитом 20 секунд, прежним фиксированным окружением и без включения stdout/stderr в ошибки. Проверка шаблона AWG сохраняет три фиксированных системных каталога и отклонение ссылок и нерегулярных файлов.

## Критерии приёмки

- SVC-1. Неизвестная роль, лишний instance ID и недопустимый AWG ID отклоняются до исполнения команды.
- SVC-2. Порядок и группировка start/stop, smoke и readiness соответствуют исходному поведению.
- SVC-3. Active, Inactive и Unknown различаются; ошибка чтения состояния исключает сохранение backend на основании его активности.
- SVC-4. Сохраняются timeout, отмена, окружение, закрытость вывода и независимый откат.
- SVC-5. Частичный отказ batch-команды обрабатывается существующим координатором восстановления.
- SVC-6. Существующие блокировки, форматы, API и повторные операции проходят регрессионные тесты.
- SVC-7. Штатный конструктор использует новый адаптер, тестовая подмена системных команд остаётся доступной.
- SVC-8. Проверяются идентификаторы, состояния, отмена, batch-отказ и существующие транзакционные сценарии binding/AWG. Полный прогон и независимое ревью проводятся перед контрольной публикацией этапа.

## Статус

Контракт подготовлен перед реализацией. Первый адаптер и его подключение к `binding` реализованы. На macOS arm64 успешно выполнены `make fmt`, `make check` (Go vet и тесты, shell lint, тесты установщика и экспериментов, проверка документации), а также `git diff --check`. Независимые ревью кода и проверка безопасности завершены без блокирующих замечаний. Тестировщик отдельно повторил `go -C backend test -count=1 ./internal/services/... ./internal/binding ./internal/awg` и `make build`: обе команды завершились успешно. Проверки с подменой системных команд подтверждают контракт и порядок операций; фактическое исполнение systemd на Linux ими не проверяется. Это не завершение этапа 2: следующие шаги выделяют пути, сеть и оставшихся потребителей управления службами по общей дорожной карте. Проверки на Linux и Keenetic ещё не проводились.

`Inactive` означает результат «не активен», но не доказывает отсутствие процессов и не разрешает удалять защитные маршруты. Проверки завершения AWG и удаления guards в этот перенос не входят.
