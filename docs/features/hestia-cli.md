# hestia-cli: передача файлов для исследований

## Назначение и границы

`hestia-cli` — отдельная Go-команда для административных операций Hestia и исследовательской работы. HTTP-сервер на порту `8081` загружает исследовательские файлы и IPK на Keenetic и отдаёт подготовленные результаты. Сервер не запускает файлы и не устанавливает IPK: оператор запускает исследование или `opkg` отдельной SSH-командой. Команда `dns-forwarder` отдельно управляет DNS-профилем клиентских сегментов Keenetic.

HTTP-сервер сам не устанавливает обновления и не меняет маршруты, конфигурацию роутера или службы Hestia. Он работает только с двумя явно заданными существующими каталогами: каталогом загрузки и каталогом выгрузки. В HTTP-запросе нельзя передать путь к произвольному каталогу. Изменение DNS-прокси выполняется только отдельной явной CLI-командой; старт Hestia и наличие `dns.json` ничего не меняют.

## Контракт

- Команда запускается как `hestia-cli serve`; адрес по умолчанию — `:8081`.
- `-upload-dir` и `-download-dir` задают разные существующие абсолютные каталоги без символьных ссылок и без права записи для группы/остальных. Имена файлов в API не содержат путей.
- `-token-file` задаёт обычный приватный файл токена без прав доступа группы и остальных; запросы передают его через `Authorization: Bearer`.
- `PUT /v1/files/upload/{name}` заменяет файл атомарно только после полного получения тела. Максимальный размер по умолчанию — 128 MiB; увеличить его нельзя.
- `GET /v1/files/download/{name}` отдаёт только обычный файл из каталога выгрузки.
- Имя — ASCII из букв, цифр, точки, подчёркивания и дефиса; длина — от 1 до 128 символов, первый символ — буква или цифра. Путь, скрытое имя и управляющие символы отклоняются.
- Ошибки API не раскрывают локальные пути и системные сообщения. Неавторизованный запрос получает HTTP 401.
- Служба не выполняет команды, не запускает загруженные файлы и не читает другие каталоги.

## Критерии приёмки

1. Go-сборка формирует отдельный `hestia-cli` для Linux ARM64 и включает его в каталог готовых исследовательских артефактов.
2. Сервер принимает файл только с валидным токеном, в заданный каталог загрузки и в пределах лимита; публикация файла атомарна.
3. Сервер отдаёт только обычные файлы из заданного каталога выгрузки, включая большие файлы потоково.
4. Path traversal, символьные ссылки, неправильные имена, несуществующие каталоги и неверные права токена отклоняются.
5. Сервер останавливается по SIGTERM и завершает активные HTTP-запросы в пределах таймаута.
6. Передача файлов не запускает бинарник. Исследование запускается оператором отдельно через SSH.

## Запуск и HTTP-примеры

### Профиль DNS-прокси Keenetic

Команды запускают локальный `/bin/ndmc` на Keenetic и требуют root. `enable` сначала проверяет готовность Hestia DNS на loopback и отсутствие чужого профиля или назначения на запрошенных интерфейсах. Укажите все нужные клиентские сегменты повторяющимся `-interface`. На KN-1012 12 ноября 2026 года read-only инвентарь показал `Home`, `GuestWiFi` и `GuestWiFi_5G`; перед применением сверяйте текущий инвентарь устройства.

```sh
/opt/bin/hestia-cli dns-forwarder status
/opt/bin/hestia-cli dns-forwarder enable \
  -interface Home \
  -interface GuestWiFi \
  -interface GuestWiFi_5G
/opt/bin/hestia-cli dns-forwarder disable
```

Для работы DNS-служба должна быть настроена слушать `127.0.0.1:<порт>` выше 1024, а в `dns.json` поле `router` должно быть `127.0.0.1`. Команда создаёт DNS profile `HestiaDNS` с единственным DNS upstream на этот loopback-порт и назначает профиль выбранным сегментам. Она не занимает порт 53, не переписывает DNS upstream прочих сегментов и не перехватывает запросы клиентов, настроенных на сторонний DNS напрямую. Именные профили, назначенные отдельным клиентам Keenetic, сохраняют приоритет.

Повторное включение совпадающей конфигурации идемпотентно. При конфликте команда отказывает без перезаписи чужих настроек. Если включение потребует активировать глобальный filter engine, команда откажет при наличии других профилей или назначений. Команда также откажет при существующих per-device профилях/пресетах, чтобы не заявлять, что её профиль получил каждый клиент. Маркер профиля хранит точный список интерфейсов. `disable` сверяет его с фактическими назначениями и upstream; при ручном изменении профиля или списка назначений команда отказывает. При частичной ошибке отключения команда пытается восстановить профиль и уже снятые назначения. Если Hestia создала DNS filter engine, она удаляет его только когда других профилей и назначений больше нет.

Не включайте профиль на рабочем Keenetic до согласованного тестового окна: назначение применяется ко всем устройствам выбранных сегментов. Сквозной прогон на KN-1012 ещё требуется.

### HTTP-сервер передачи файлов

Для первоначальной установки поместите бинарник `hestia-cli` и token-файл непосредственно в Entware `/opt` через локальную установку/носитель. SSH не используется для передачи их содержимого. Этот bootstrap необходим, потому что работающий `hestia-cli` не может передать сам себя; его автоматизация пока не входит в эту функцию. После установки SSH используется только для команд подготовки и запуска сервера.

```sh
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go -C backend build -trimpath -buildvcs=false -o /tmp/hestia-cli ./cmd/hestia-cli
umask 077
mkdir -p private
chmod 0700 private
test -s private/hestia-cli.token || openssl rand -hex 32 > private/hestia-cli.token
chmod 0600 private/hestia-cli.token
```

Локальная копия токена хранится в `private/hestia-cli.token`. Каталог `private/` исключён из Git правилом в корневом `.gitignore`; сохраняйте для каталога права `0700`, для файла токена — `0600`. Команда выше создаёт токен только при отсутствии непустого файла: не перегенерируйте токен без одновременной замены его копии на роутере. Не включайте значение токена в журналы, отчёты и команды, сохраняемые в историю.

На роутере подготовьте каталоги и запустите сервер на LAN-адресе:

```sh
umask 077
mkdir -p /opt/var/lib/hestia-cli/inbox /opt/var/lib/hestia-cli/outbox
# token-файл заранее помещён в /opt/etc/hestia-cli.token через локальный bootstrap
# /opt/etc/hestia-cli.token
/opt/bin/hestia-cli serve \
  -listen 192.168.1.1:8081 \
  -upload-dir /opt/var/lib/hestia-cli/inbox \
  -download-dir /opt/var/lib/hestia-cli/outbox \
  -token-file /opt/etc/hestia-cli.token
```

Загрузите IPK или исследовательский бинарник с доверенного компьютера:

```sh
curl --fail-with-body \
  --config - --upload-file ./research-arm64 \
  http://<keenetic-lan-address>:8081/v1/files/upload/research-arm64 <<EOF
header = "Authorization: Bearer $(cat private/hestia-cli.token)"
EOF
```

После запуска исследования по SSH сохраните отчёт в каталоге выгрузки, затем скачайте:

```sh
curl --fail-with-body \
  --config - -o ./research.log \
  http://<keenetic-lan-address>:8081/v1/files/download/research.log <<EOF
header = "Authorization: Bearer $(cat private/hestia-cli.token)"
EOF
```

Сервер работает в foreground и корректно завершается по SIGTERM. Для временного исследовательского сеанса его можно запустить через SSH в фоне, перенаправив stdout/stderr в отдельный файл. Автозапуск после перезагрузки и управление службой не входят в первый этап.

Токен нельзя передавать по недоверенной сети или записывать в отчёт. Доступ к порту `8081` должен быть ограничен доверенной LAN; публикация в WAN не входит в сценарий.

## Состояние

Сервер файлов и endpoints компилируются для Linux ARM64 и Keenetic ARM64 в Go-only сборке. 11 ноября 2026 года бинарник установлен на Keenetic по `/opt/bin/hestia-cli`; сервер запущен на `192.168.1.1:8081`, ограничен LAN-адресом и отвечает HTTP 401 без токена. Автозапуск сервера после перезагрузки пока не настроен. Для Hestia DNS добавлена отдельная явная команда управления DNS-профилем Keenetic; её целевое поведение и откат требуют аппаратной проверки. Режим запуска исследования, сбор логов автоматически и клиентские подкоманды `upload`/`download` остаются отдельными расширениями.
