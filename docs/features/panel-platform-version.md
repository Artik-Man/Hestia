# Версия и целевая платформа в панели

## Цель

Показывать в шапке панели версию приложения вместе с целевой платформой сборки, чтобы администратор мог отличить Linux-комплект для виртуальной машины от Keenetic-комплекта.

## Предлагаемое поведение

- Базовая версия берётся из единого источника версии панели — `frontend/package.json`.
- Каждая полная `make build` один раз повышает patch-версию командой `npm version patch --no-git-tag-version`; npm обновляет `frontend/package.json` и `frontend/package-lock.json` без создания Git-коммита или тега.
- Комплект `linux-arm64` получает метку `vm`; панель показывает, например, `0.1.2-vm`.
- Комплект `keenetic-arm64-experimental` получает метку `keenetic`; панель показывает, например, `0.1.2-keenetic`.
- Обе платформы используют одну базовую версию в рамках одной сборки.
- Полная сборка использует повышенную версию и в каталоге `dist/artifacts/<версия>/`, манифестах и Keenetic IPK.
- Версия повышается до начала компиляции и не откатывается при последующей ошибке сборки. Режим `--check-go` и отдельный `npm run build` версию не повышают.
- Метка платформы задаётся сборщиком для каждой платформы отдельно; готовые frontend assets не разделяются между комплектами.
- `npm run build` без платформенной настройки сохраняет базовое отображение версии без суффикса, чтобы обычная локальная сборка не заявляла целевую платформу.
- Формат манифестов и имена платформенных подкаталогов не меняются; значения версий комплектов и IPK используют новую SemVer patch-версию.

## Согласованные критерии приёмки

1. В браузере из Linux-комплекта рядом с логотипом отображается `<версия>-vm`.
2. В браузере из Keenetic-комплекта рядом с логотипом отображается `<версия>-keenetic`.
3. Обе панели показывают одну и ту же базовую версию из `frontend/package.json`.
4. Сборка frontend без платформенного параметра показывает только базовую версию.
5. Проверка сборки подтверждает, что в каждый комплект помещены assets именно его платформы.
6. Полная сборка увеличивает patch ровно на единицу, синхронизирует оба npm-файла и использует новую базовую версию для обоих комплектов.
7. Режим `--check-go` не меняет версию и `npm version` не создаёт Git-коммит или тег.

## Границы

Изменение касается подписи в шапке панели и правила повышения patch-версии при полной сборке. Оно не меняет API и backend runtime.

## Результаты проверки

- `npm run lint` и `npx prettier --check angular.json src/core/components/panel/panel.component.ts` завершились успешно.
- Angular production builds для `vm`, `keenetic` и без конфигурации платформы завершились успешно. В собранных assets подтверждены суффиксы `-vm` и `-keenetic`; локальная сборка осталась без суффикса.
- Полная сборка `GOCACHE=/private/tmp/hestia-go-cache python3 scripts/build/run.py --output /private/tmp/hestia-artifacts-platform-version` завершилась успешно. В созданных комплектах проверены соответствие `manifest.platform` и суффикса в панели.
- Ревью кода и проверка ИБ не выявили замечаний. Проверка advisories зависимостей не проводилась: зависимости не менялись.
- Автоматизированные тестовые наборы и браузерный E2E не запускались.
- Для повышения версии проверены синтаксис `scripts/build/run.py` через `python3 -m py_compile` и отсутствие ошибок пробелов через `git diff --check`. Полная сборка и npm-команда не запускались; фактическое повышение версии и упаковка артефактов требуют отдельного прогона.

## План реализации

1. Добавить типизированную конфигурацию платформы frontend с допустимыми значениями `vm` и `keenetic` и без суффикса для стандартной локальной сборки.
2. Собирать frontend отдельно для каждого платформенного комплекта и копировать соответствующие assets.
3. Проверить собранные assets обоих комплектов и стандартной локальной сборки.
4. Обновить документацию сборки и выполнить форматирование, линтинг и применимые проверки.
