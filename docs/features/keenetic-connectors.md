# Платформенные коннекторы Hestia для Keenetic

Статус: рабочая спецификация по поручению Product Owner от 7 ноября 2026 года. Целевая платформа исследования — KN-1012 с KeeneticOS 5.2 Beta 3 и Entware; использование изолированной среды и подключение к физическому устройству описываются отдельно для каждого этапа.

## Цель

Собрать из Go-компонентов Hestia поставку, которая запускается на Keenetic и предоставляет существующие функции шлюза через платформенные адаптеры. Эксперименты и production-коннекторы используют Go и общую типизированную библиотеку там, где контракт общий. Неизвестная возможность Keenetic остаётся явно неподдержанной до отдельного исследования, а отсутствие функции не маскируется успешным ответом.

## Объём

Реализация следует границам [каталога коннекторов](connector-catalog.md) и существующим интерфейсам в `backend/internal/network`, `services`, `storage`, `binding` и `controller`.

## Веб-панель в LAN на KN-1012

На установленном Keenetic Giga KN-1012 панель должна открываться из домашней LAN по адресу `http://192.168.1.1:8080/`, без SSH-туннеля. Адрес слушателя хранится в root-only файле `/opt/etc/hestia/panel-listen` и должен содержать конкретный частный IP роутера и порт. Wildcard-адреса не разрешены; обработчик принимает запрос только с Host, совпадающим с настроенным IP. Панель не аутентифицирует пользователей, поэтому слушатель ограничивается LAN IP, а не WAN IP или всеми интерфейсами; устройства, имеющие доступ к LAN, получают доступ к функциям панели.

Критерии приёмки: (1) `netstat` показывает `192.168.1.1:8080`, а не `127.0.0.1:8080`; (2) HTTP-запрос из LAN к `http://192.168.1.1:8080/` получает `200`; (3) проверка профиля и readiness supervisor после перезапуска проходят; (4) private listener и Host-проверка сохраняются, wildcard bind не используется.

## Чтение подключений из установленного пакета

Для первой установки Keenetic IPK обязан создать root-owned install-lock до запуска supervisor, чтобы managed snapshot reader и физическая инвентаризация могли использовать общий shared lock. Панель должна вызывать read-only `-physical-list` helper независимо от флага управления AWG; на KN-1012 ответ содержит kernel interfaces и RCI native Ethernet ports. Wi-Fi mutations остаются неподдержанными и должны завершаться явной ошибкой.

Критерии приёмки: (1) initial managed `GET /api/groups-and-rules` возвращает HTTP 200 с default deny group; (2) `GET /api/physical-connections` возвращает HTTP 200 и инвентарь с KN-1012; (3) при выключенном AWG перечисление интерфейсов работает; (4) пакет создаёт постоянный non-symlink root-only lock до старта supervisor; (5) Wi-Fi запись не включает неподдерживаемую Keenetic мутацию.

## Запуск supervisor при установке и обновлении

Lifecycle `postinst` ждёт готовность supervisor до 60 секунд, чтобы медленный запуск ролей на целевом Keenetic не превращался в ложный отказ установки. Supervisor записывает ошибки запуска и работы в `/opt/var/run/hestia/supervisor.log` с правами `0600`. Если готовность не подтверждена за отведённое время, установка завершается ошибкой, init останавливает принадлежащие Hestia процессы, а пользователь может проверить журнал перед восстановлением предыдущего IPK.

Критерии приёмки: (1) успешный старт подтверждается readiness marker и IPC состоянием обязательных служб; (2) старт может занимать до 60 секунд; (3) при ошибке до readiness причина попадает в root-only журнал; (4) тайм-аут сохраняет отказ установки и выполняет остановку, не удаляя конфигурацию и предыдущий IPK.

## Добавление VPN-подключений в панели Keenetic

Панель на Keenetic должна позволять создать, просмотреть, изменить и удалить Hysteria 2, WireGuard и AmneziaWG через те же редакторы и REST-контракты, что и Linux-сборка. Hysteria 2 использует уже поставляемый sing-box и отдельную capability панели; её включение не включает запись Wi-Fi или инвентарь портов. WireGuard и AmneziaWG используют существующую общую AWG-модель и должны сохранять различия протоколов в профилях.

Транзакционная проверка поколения принимает платформенное хранение snapshot: на Linux — `0640` с группой снимка, на Keenetic — `0600 root:root`, если эта группа не установлена. AWG health marker на Linux публикуется как `root:hestia-snapshot 0640`, на Keenetic — как `root:root 0600` внутри закрытого runtime-каталога; контроллер принимает только соответствующий платформе режим. Keenetic-композиция не зависит от отсутствующей в Entware группы. Heartbeat обновляется после проверки egress раз в 15 секунд и считается свежим до 35 секунд, чтобы внешняя HTTPS-проверка не создавала запрос каждую секунду и не сбрасывала marker на единичной задержке. Проверка собранного sing-box backend на Keenetic запускает бинарник через `/opt/lib/ld-linux-aarch64.so.1` с library path Entware. Проверка владения IPv6 fail-closed маршрутом принимает точную форму вывода Keenetic `unreachable default dev lo metric 32767 error -113`. Сохранение WireGuard/AmneziaWG сначала транзакционно записывает профиль как `configured`: профиль виден в панели, availability false, он не становится default exit, а его outbound блокирует трафик. Затем отдельная транзакция пытается подтвердить handshake, запуск роли, underlay и применение маршрутов. После подтверждённого handshake исходный `PersistentKeepalive` восстанавливается отдельной Entware-командой с контекстом до 10 секунд, не зависящим от deadline ожидания handshake; поддерживаются как одиночные интервалы, так и диапазоны AmneziaWG. Диагностика различает deadline, отказ команды и некорректные аргументы, не раскрывая её вывод или значения ключей. При подтверждённом откате неудачной активации API оставляет профиль сохранённым как «Недоступно». Повторное сохранение позже может перевести его в `ready` только после подтверждения handshake и фактической доступности маршрута. Ошибки валидации, компиляции, целостности первоначального сохранения или отката не должны создавать фиктивный успешный результат. Keenetic-сборка подключает Entware AWG runtime и отдельную службу через root-only supervisor; UI/API включаются только для этой композиции. Проверка родительского `/opt/tmp` учитывает исходные Unix mode bits: Entware Go runtime на KN-1012 может не передавать sticky bit в `os.FileMode`, поэтому разрешается только root-owned каталог без group/world write либо root-owned каталог со sticky bit; общий временный каталог без sticky bit должен быть исправлен до запуска AWG. UAPI socket directory должен совпадать в `amneziawg-go` и `awg-tools`; для Keenetic пути обоих pinned runtime задаются build inputs, и build проверяет их соответствие. awg-tools в Keenetic-пакете должен быть статическим ARM64 бинарником, совместимым с системной средой роутера; пакетная проверка подтверждает pinned hash и корректный выбор runtime, а целевой запуск подтверждает выполнение на KN-1012.

Критерии приёмки: (1) Hysteria 2 CRUD в Keenetic сборке доходит до установленного helper и компилирует новый snapshot средствами sing-box, с проверкой secret-safe ошибок; (2) WireGuard и AmneziaWG можно добавить раздельно, секреты сохраняются под root-only правами, а новый профиль после ошибки активации и подтверждённого отката отображается как «Недоступно»; (3) профиль `configured` не изменяет default exit и не получает пользовательский трафик; (4) профиль становится `ready` и получает маршруты только после handshake и фактического подтверждения egress; (5) восстановление keepalive после подтверждённого handshake не зависит от истечения deadline пробы; (6) ошибки валидации, компиляции, целостности или отката восстанавливают прежние snapshot, профиль, службы и маршруты; (7) перезапуск supervisor восстанавливает только подтверждённые подключения; (8) сборка подтверждена локально, а поведение на KN-1012 и целевой прогон с TCP/UDP, IPv4/IPv6 и откатом остаются отдельной аппаратной приёмкой.

### Прямой интернет-провайдер как underlay WireGuard на Keenetic

В редакторе WireGuard/AmneziaWG поле «Подключаться через» должно предлагать текущий прямой интернет-выход Keenetic с именем провайдера, полученным через RCI. Определение выхода строится по текущему IPv4 default route и подтверждённой связи его netdev с логическим подключением RCI. Наблюдение на KN-1012, где default route проходил через `eth3` и провайдера «ПАКТ», — характеристика проверенного устройства на момент исследования, а не константа для реализации. В коде запрещено закреплять имя адаптера (`eth2`, `eth3` и подобные) или физический порт: другой Keenetic, прошивка либо способ поставки могут дать иной набор netdev. Если активный маршрут или его RCI-сопоставление неоднозначны, underlay не предлагается и изменение профиля завершается безопасной ошибкой.

Внутренний ID прямого выхода Keenetic — `keenetic-uplink`, отдельный platform-scoped идентификатор. Он не совпадает с `keenetic-direct`, который уже используется подключением схемы Lima, и не выводится из видимого имени провайдера. При установке backend привязывает его к netdev, обнаруженному для текущего default route, и добавляет в группу `default`, если выход ещё не назначен другой группе. Транзакция повторно проверяет маршрут и отказывает при изменении или неоднозначности пути; `defaultExit` и существующее распределение групп сохраняются. В панели платформа показывает выход как «Выход» и не раскрывает netdev или routing ID. Его можно перемещать в любую группу. Runtime controller по-прежнему выбирает первый здоровый выход по порядку группы: если более приоритетные выходы недоступны, прямой uplink может стать активным failover. Linux backend показывает соответствующий прямой канал как «Выход».

Отдельный `keenetic-opkgtun` доступен VPN-соединениям как underlay к peer. Он привязан к Hestia TUN `opkgtun0`, не добавляется обычным выходом в группы и публикуется только в Keenetic-сборке. Внешний transport, отправленный через этот путь, входит в Hestia через OpkgTun и направляется только в одну безопасную AmneziaWG-группу. Компилятор исключает группу, в которой прямой или транзитивный underlay любого AWG-выхода снова зависит от OpkgTun; если безопасного пути нет, вход блокируется. `keenetic-direct` в Linux/VM остаётся доступным VPN-underlay по существующей схеме.

Критерии приёмки: (1) каталог API, модальное окно WireGuard и список доступных выходов групп показывают «ПАКТ» как прямое подключение на KN-1012; (2) страницу групп можно использовать, чтобы добавить uplink в выбранную группу без VPN mutation и сохранить прежний `defaultExit`; если более приоритетные выходы нездоровы, runtime failover может выбрать ПАКТ; (3) при имитации другого имени netdev API и candidate выбирают обнаруженный адаптер, без ветвей, привязанных к `eth3`; (4) provider ID не конфликтует с пользовательским WireGuard/WG ID из Lima; (5) выбор для VPN сохраняется и компилирует transport через обнаруженный default-route netdev; (6) handshake и фактический egress VPN подтверждаются отдельно от доступности direct exit; (7) список underlay в Linux остаётся без Keenetic-only выхода.

### Многоканальный WAN и выбор выхода по качеству — предложение Product Owner

**Статус:** идея зафиксирована 10 ноября 2026 года; требуется согласовать подробное поведение до реализации.

Цель — дать Hestia инвентарь всех WAN Keenetic (несколько провайдеров, LTE/модем и WISP/мобильная точка доступа), измерять каждый канал отдельно и выбирать выход по внутренней логике качества Hestia. Смена выбранного Hestia выхода не должна менять глобальный приоритет или сохранённые подключения Keenetic.

Предлагаемый первый срез — переключать целую группу Hestia между каналами, когда выбранный путь недоступен или измерения устойчиво показывают худшее качество. Пробы должны быть привязаны к конкретному WAN и подтверждать фактический egress; одной проверки link/carrier недостаточно. Если ни один путь не проходит условия доступности, группа блокирует трафик. Правила для отдельных сайтов, IP или протоколов — отдельный следующий срез: общий рейтинг канала не выражает разные исключения провайдеров для разных типов трафика.

Перед реализацией требуется исследовать read-only сопоставление логических provider/WISP записей RCI с Linux netdev, route table и обратным путём на KN-1012. Для каждого WAN нужны отдельная привязка сокетов проб, безопасная таблица/метка маршрутизации и контроль того, что измерения и VPN-underlay действительно выходят через нужный канал. Реализация не должна менять Keenetic priorities, policy assignments или основной default route. Неоднозначный provider↔netdev mapping должен закрывать этот выход для выбора. Текущий адаптер показывает имя только для однозначного default route, а WISP inventory и его привязка к egress на целевом устройстве ещё не подтверждены.

Критерии для проектирования: (1) устойчивые ID и имена всех WAN, включая WISP, не зависят от имён netdev; (2) пробы каждого кандидата идут через этот кандидат и показывают подтверждённый egress; (3) уже имеющийся Hestia quality selector переключает группу по измерениям и порогам без изменения Keenetic global priority; (4) отказ всех каналов завершается fail-closed; (5) проверки покрывают link loss, сохранённый link при отсутствии интернета, частичные TCP/UDP/DNS/HTTPS отказы, смену приоритета Keenetic, WISP и восстановление после перезапуска; (6) главный маршрут Keenetic, чужие policies и обратный путь остаются сохранными; (7) отдельно решается, нужен ли per-destination/protocol policy beyond whole-group failover.

### Приоритеты маршрутизации AmneziaWG на Keenetic

KeeneticOS устанавливает собственное правило `priority 9 lookup main`, поэтому mark-правило Hestia с приоритетом `1002` не может выбрать AWG таблицу и должен быть отвергнут проверкой fail-closed. Для Keenetic резервируются свободные приоритеты `1..8`: каждая AWG запись использует пару `2*slot+1` для маршрута туннеля и `2*slot+2` для внешнего blackhole guard; это ограничивает число AWG slots четырьмя. `0 lookup local` остаётся первым. Установленный Entware `/opt/sbin/ip` не принимает терминальный action токен `unreachable`; эквивалентное правило создаётся формой `lookup unspec type blackhole` и должно читаться обратно как `lookup unspec blackhole`. При обновлении только root-owned manifest с точной прежней аллокацией разрешает перенос существующего mark-правила с прежнего приоритета; новые правила добавляются до удаления старых, чтобы таблица с fail-closed default оставалась достижимой.

Критерии приёмки: (1) VPN mark-rule расположен перед Keenetic `priority 9 lookup main`; (2) внешний mark перехватывается owned blackhole guard до системного default route; (3) legacy manifest и совпадающие rules мигрируют без удаления чужих правил; (4) отказ миграции оставляет новый/старый guard rule и fail-closed route; (5) обычный незамаркированный трафик и LAN-доступ к роутеру сохраняют исходный путь.

### Решение по исследованию dataplane

Для входного трафика рассматриваются два способа: (1) штатная политика Keenetic направляет выбранные устройства через отдельный WireGuard-интерфейс, ведущий во вход Hestia; (2) Hestia прозрачно перехватывает поток по mark через TProxy/Redirect либо ограниченный TUN. Keenetic документирует назначение WireGuard-интерфейса политике через `ip hotspot policy`; конкуренты SKeen и XKeen используют свои firewall chains/marks для TProxy/Redirect. Ни один из вариантов не испытан с Hestia на KN-1012. Исследование практик и границ сведено в [документ интеграции Keenetic](../keenetic-platform.md#актуализация-выбор-клиентского-трафика-и-охват-трафика-самого-роутера--8-ноября-2026-года).

При любом варианте Hestia должна принимать IP-пакеты, а не только создавать исходящий VPN. Текущий AWG slot mark/table обслуживает только исходящие Hestia-потоки; `amneziawg-go` не создаёт входной peer. sing-box TUN 1.14.4 остаётся возможным транспортным/перехватывающим компонентом, но `auto_route` включает маршруты сам, а `auto_redirect` этой версии опирается на nftables. Создание TUN на KN-1012 уже проверялось без передачи пакетов. Не включать глобальный маршрут или firewall hook до проверки выборочной области и восстановления.

До приёмки ни туннельный вход, ни прозрачный перехват клиентского трафика не включаются: пакет не меняет маршруты, Netfilter, DNS-настройки или конфигурацию KeeneticOS. Для первого варианта нужно подтвердить, что локальный WireGuard endpoint может безопасно принять соединение с самого Keenetic, а Keenetic включает его в политику без конфликтов с другими соединениями. Для второго — ограничить перехват тестовой политикой/клиентом и защитить uplink от петли. Перед любым целевым испытанием нужны снимок и воспроизводимый откат. Следующий исследовательский этап сравнивает оба варианта по входу пакетов в Hestia, ответному маршруту, fail-closed, IPv4/IPv6 и TCP/UDP; он не должен направлять весь домашний трафик без отдельного согласования.

### Выборочный трафик клиента Keenetic

Wi-Fi в каталоге Hestia для этой сборки означает подключение самого роутера к внешней точке доступа (WISP), а не точку доступа для домашних клиентов. iPhone подключён к Keenetic по Wi-Fi, и Keenetic позволяет назначить его отдельной сетевой политике. Владелец предложил создать под управлением Hestia входной VPN WireGuard/SSTP и добавить интерфейс в такую политику. Это пока архитектурный кандидат, не согласованная реализация: внешний VPN-клиент Hestia и его mark-таблица сами по себе не дают входного peer и не направляют LAN-пакеты iPhone в Hestia.

Критерий приёмки: после фиксации iPhone в отдельной Keenetic-политике её IPv4/IPv6 TCP/UDP-потоки поступают в Hestia dataplane и выбирают назначенную группу; внешний egress подтверждается с iPhone. Потоки других клиентов и незамаркированный трафик роутера сохраняют исходную политику, ответы возвращаются iPhone, а отказ или остановка Hestia не создают обход выбранного VPN через WAN. До такой проверки нельзя считать клиентскую политику способом провести iPhone через Hestia.

Не переносить в Keenetic API логику групп, приоритетов, доменных списков, GeoIP, оценки качества и DNS-кэша: она остаётся в ядре Hestia, пока не доказана обязательная платформенная зависимость.

Entware upstream installer создаёт базовые `/opt/etc` и `/opt/var/lock`, а его `rc.unslung` запускает scripts из `/opt/etc/init.d`; пакет nginx также заводит `/opt/var/run`. Это подтверждает соглашения Entware, но каталоги и права ещё нужно проверить на KN-1012 перед установкой Hestia ([installer](https://github.com/Entware/installer.sh/blob/master/generic.sh), [`rc.unslung`](https://github.com/Entware/rtndev/blob/master/entware-opt/files/rc.unslung), [nginx package](https://github.com/Entware/entware-packages/blob/master/net/nginx/Makefile)).

## Общие критерии приёмки

1. У каждого интерфейса одна Go-реализация с явной композицией для Keenetic и Linux; исследовательские запросы не дублируют аутентификацию или разбор общих контрактов.
2. Все операции имеют типизированный вход/выход и явную классификацию чтения или изменения состояния. Ошибки не содержат секреты, сырые конфигурации или несанитизированное тело RCI.
3. Возможность включена в manifest только после фактической проверки на целевой прошивке. Непроверенная операция возвращает безопасную ошибку и не запускает Linux-specific fallback.
4. Для клиентского трафика тестируются IPv4 и IPv6, TCP и UDP, выбранный выход, недоступность выхода, отказ VPN, перезапуск и восстановление. Снятие guards допустимо только после подтверждённой остановки owned runtime.
5. Установка и удаление меняют только файлы, службы и правила Hestia; до изменения сети сохранены исходные значения и воспроизводимый откат.
6. Поставка запускает backend, панель и необходимые runtime-компоненты после загрузки Entware; объявленные зависимости включают стандартные модули Python, которые использует проверка профиля. Управляемая панель использует установленную карту стран без передачи запрещённого пользовательского override. Установщик проверяет модель, архитектуру, прошивку, объём `/opt`, права и доступные системные возможности до внесения изменений.
7. После каждого этапа протокол содержит версию прошивки/кода, точный запрос или команду, ожидаемое и фактическое поведение, состояние до/после, очистку, свидетельства и границы вывода.
8. Preflight определяет архитектуру через доступную в Entware утилиту; init-скрипт запускает и останавливает принадлежащий Hestia supervisor через опции `start-stop-daemon` и `usleep`, поддерживаемые BusyBox на KN-1012. Остановка подтверждается по фактическому состоянию процессов, включая ограниченный переход TERM → KILL.

## Подтверждённая исходная точка

На KN-1012 / KeeneticOS 5.2 Beta 3 локальный token-auth `GET /rci/show/version` и `GET /rci/show/interface` через `127.0.0.1:79` вернули HTTP 200 JSON. Ответ интерфейсов содержал пять физических `Port`-записей. Это подтверждает только две read-only операции на проверенной сборке. [Протокол и свидетельства](../../experiments/keenetic-rci-readonly/README.md) · [инвентарь Ethernet](../../experiments/keenetic-ethernet-management-20261106/README.md).

Проверка окружения ранее обнаружила ядро `4.9-ndm-5`, наличие `/dev/net/tun`, отказ `unshare(CLONE_NEWNET)` с `EINVAL` и различия ELF-загрузчика для сторонних runtime. До проверки альтернатив эти ограничения считать активными. Локальный runtime sing-box/AWG сам по себе не подтверждает передачу клиентского трафика, политику маршрутизации или безопасную работу служб.

## Первый реализуемый срез

1. Вынести клиент аутентификации в `backend/pkg/keeneticrci`, доступный исследовательским командам и коннекторам.
2. Сохранить контракт Ethernet-порта в типах Go и определить адаптацию к REST-модели Hestia. Модель API должна вместить стабильный ID `GigabitEthernetN/M`.
3. Составить таблицу возможностей Keenetic-композиции для `network.Physical`, `network.Carrier`, `network.RoutePolicy`, socket binding, services и storage. Для каждой неизвестной операции определить минимальное исследование до реализации.
4. Собирать Linux и Keenetic Go-варианты раздельно; включить `/opt` layout только в Keenetic-вариант. Не включать установку или сетевые изменения на KN-1012 в локальную сборку. Подготовить проверяемый `.ipk` и план отката до отдельного аппаратного запуска.

## Сверка с текущими Go-интерфейсами

Preinst до распаковки пакета запускает Go helper из control-архива IPK. Helper использует общий `keeneticrci.Client` и root-only token `/opt/etc/hestia/keenetic-rci-token`; read-only `GET /rci/show/version` проверяет KN-1012 / KeeneticOS 5.2 Beta 3, после чего проверяются Entware architecture, права `/opt` и свободное место. Токен не включается в IPK: его нужно отдельно разместить владельцем устройства до установки. Неизвестная модель/прошивка, недостаток места, недоступный RCI или неполные сведения завершают preflight отказом. В upstream `opkg` `preinst` запускается по пути из временного control-каталога ([`pkg_run_script`](https://lxr.openwrt.org/source/opkg-lede/libopkg/pkg.c#L1355)); совместимость Entware `opkg` с этим helper ещё не проверялась на устройстве.

| Точка интеграции | Текущее состояние | Работа для Keenetic |
|---|---|---|
| `network.Physical` | Один интерфейс объединяет чтение Ethernet/Wi-Fi и запись/удаление NetworkManager Wi-Fi-профилей; команда физического API обращается к `platform.Physical()` | Linux выбирает NetworkManager adapter; Keenetic перечисляет реальные kernel devices через sysfs и отдельно читает typed RCI port list в `nativeEthernetPorts`, сохраняя полный ID, link/speed/duplex без смешения двух пространств имён. Общий RCI пакет содержит read-only WISP station status reader, но он пока не подключён к REST-модели: соответствие RCI station ID и Linux device, а также публичная семантика профиля не подтверждены. Wi-Fi mutations возвращают unsupported |
| `network.Carrier` | Типизированный метод `State(string) CarrierState` реализован через sysfs для Linux и потребляется watcher-контроллером; `unknown` остаётся недоступным, а watcher публикует дедуплицированное предупреждение. Аргумент — kernel device name из профиля выхода | Keenetic-вариант также читает carrier по kernel device name через sysfs. REST-инвентарь отдельно сообщает `carrierState=up|down|unknown`; совместимое `online` истинно только для `up`. Отсутствующий/нечитаемый carrier сохраняется как `unknown`, fail-closed исключает выход. RCI ID и link физических гнёзд остаются отдельной инвентаризацией и не преобразуются в `bind_interface` |
| `network.RoutePolicy` | Linux `iproute2`-адаптер устанавливает IPv4/IPv6 guards, marks/rules и удаляет только подтверждённое owned state | KN-1012 inventory подтвердил `/opt/sbin/ip` (BusyBox 1.37.0); снимки маршрутов и правил получены через `list`, как и предписывает справка BusyBox. Keenetic runner переводит общие `route show`/`rule show` в `list`, ограничивает время и объём вывода и принимает только read-only inventory и точные AWG операции в зарезервированных таблицах/marks/devices. Для одной таблицы/метки подготовлена отдельная read-only `keenetic-route-preflight`: она сводит проверку зарезервированных правил, таблиц и имени устройства к redacted результату, но ещё не запускалась на KN-1012. Поддержка числовой таблицы 202+, формат owned routes, запись, ownership, fail-closed и восстановление не проверены на устройстве; включённый в локальную сборку AWG API не подтверждает корректность целевого dataplane |
| `network/socket.Binder` | Keenetic ARM64 использует Linux connector `SO_BINDTODEVICE`/`SO_MARK`; Go binder и профильный compiler согласованно валидируют имя интерфейса (1–15 ASCII символов, первый — буква/цифра/`_`), 32-битную неотрицательную метку и режим; binder выполняет параметры в установленном порядке и возвращает ошибки обоих вызовов | Проверить socket options на KN-1012: права процесса, TCP/UDP, назначение интерфейса и метки, отсутствие пакетов при ошибке; до этого сетевые пробы остаются fail-closed и connector считается собранным, но не принятым на целевой платформе |
| `services.Manager` / `Offline` | Linux build выбирает systemd; Keenetic build использует Entware supervisor для router/controller/panel/binding watcher, AWG instance roles и Go smoke; DNS включается при наличии защищённого конфига | AWG role запускает fixed `/opt/bin/hestia -awg-runtime <id>` через root-only IPC, проверяет root-owned runtime tools и сообщает stop только после выхода сохранённого процесса. DNS роль запускается при старте supervisor только если установлен root-owned `/opt/etc/hestia/dns.json`; перед запуском профильный helper создаёт confined DNS path export из активной sing-box конфигурации. Supervisor раз в секунду сверяет optional DNS worker и хеш конфига, останавливает его при удалении/небезопасном файле или изменении JSON, затем поднимает новую версию; после завершения на смене поколения маршрутизатора также выполняется restart с ограниченным backoff. Ошибка экспорта при старте блокирует readiness, после старта ошибки рестарта не останавливают остальные службы. Keenetic DNS-настройки не меняются. При старте supervisor обнаруживает оставшиеся процессы после предыдущего экземпляра и отказывает при неоднозначном состоянии. Go smoke сверяет поколение конфигурации, API selector, controller event и process state. Установка на KN-1012 подтвердила readiness supervisor для базовых ролей; AWG start/stop, crash recovery, DNS роль и безопасное удаление маршрутов не проверены |
| `storage.Installed()` | Build tag `keenetic` выбирает Entware layout под `/opt`; без тега остаётся Linux layout с `/etc`, `/run`, `/var/lib` и NetworkManager-путями | Проверить все каталоги на KN-1012, передать layout через остальные platform adapters и не обращаться к системным `/etc`/`/run` для приватного состояния |
| `cmd/hestia` composition | Linux и Keenetic ARM64-компиляции используют build-tag selectors в `platform`; physical REST inventory отдаёт native port IDs отдельно | Keenetic panel отдельно включает Hysteria 2 helper API и WireGuard/AmneziaWG API; Entware composition выбирает AWG runtime, route runner, root-only service lifecycle и Linux socket binder. Эти маршрутизирующие операции собраны, но ещё не проверены на KN-1012 |

Для физических подключений, служб, helper и профилей добавлена platform composition: Linux выбирает NetworkManager/systemd/sudo, Keenetic использует RCI, Entware supervisor и direct root helper, а Python compiler и sing-box запускаются из `/opt`. Keenetic physical inventory отдельно включает kernel Ethernet/Wi-Fi устройства из sysfs и нативные физические порты RCI; `GigabitEthernetN/M` не используется как имя Linux-интерфейса. Controller и Go smoke проверяют carrier выбранного выхода через sysfs kernel device name. Keenetic AWG policy factory использует fixed-path runner `/opt/sbin/ip` с bounded output; runner ограничивает операции резервными таблицами, marks и устройствами. IPK переносит статический AWG daemon с выделенным UAPI-каталогом и `awg-tools`. Entware AWG runtime driver теперь подключён к Keenetic composition; supervisor запускает отдельные instance services через `/opt/bin/hestia -awg-runtime <id>`, а панель включает WireGuard/AmneziaWG CRUD. Keenetic socket binding использует Linux `SO_BINDTODEVICE`/`SO_MARK` с возвратом ошибок; целевые socket options не подтверждены. Supervisor поднимает router/controller/panel, следит за binding marker, экспортирует confined quality paths и принимает локальные команды только от root. DNS Go-служба включается, когда установлен root-owned `/opt/etc/hestia/dns.json`; перед запуском профильный helper экспортирует текущие DNS egress пути, а supervisor перезапускает службу после смены поколения sing-box с ограниченным backoff. Без файла DNS выключен, штатные DNS настройки роутера не меняются. `SmokeFresh/SmokeCurrent` перенесены в Go. Сборка создаёт `.ipk` версии v2 с `aarch64-3.10`, Entware dependencies, conffile начальной managed default deny конфигурации и lifecycle hooks. Snapshot reader использует root-only `/opt/var/lock/hestia-install.lock`, который теперь создаётся IPK. Панель получает отдельный read-only physical inventory helper и раздельные Hysteria 2 CRUD routes без включения Wi-Fi mutations; после обновления до `20261107-123735-f9fea441ebfd` оба `/api/groups-and-rules` и `/api/physical-connections` на KN-1012 вернули HTTP 200, а физическая модель содержала пять портов RCI ([отчёт](../../experiments/keenetic-ipk-packaging/README.md#исправление-загрузки-конфигурации-и-инвентаря-подключений)). Supervisor публикует readiness marker только после старта основных ролей; `postinst` ждёт marker и проверяет активные роли через root-only IPC. `prerm` подтверждает отсутствие всех управляемых процессов по `/proc`, даже когда PID-файл отсутствует; при неопределённости не даёт opkg продолжить. `opkg` сохраняет пользовательские conffiles при обновлении/удалении. Целевые проверки AWG, DNS listener/routes, Wi-Fi/WISP и клиентского dataplane не завершены. Обновление не транзакционно откатывается при ошибке postinst; восстановление требует повторной установки предыдущего `.ipk` с сохранёнными conffiles.

## Известные блокеры приёмки

- RCI ID `GigabitEthernetN/M` передаётся отдельно как `nativeEthernetPorts[].id`; имена kernel devices поступают из sysfs как `interfaces[].interfaceName` и используются для `bind_interface`. Автоматическое соответствие физического гнезда конкретному kernel device не выводится; если UI или управление портами потребует такую связь, её нужно исследовать отдельно.
- `/rci/show/interface` предоставляет только инвентарь и link snapshot. Он не подтверждает назначение порта в WAN/LAN, WISP lifecycle, маршруты, перехват клиентского трафика или восстановление правил.
- Ядро Keenetic ранее не создавало network namespace. Runtime и dataplane должны получить отдельное подтверждение на безопасном тестовом трафике.
- Текущий `keenetic-arm64-experimental` содержит отдельный build-tag variant с `/opt` layout и собираемый `.ipk`; установка на KN-1012 подтвердила Entware lifecycle, supervisor IPC, LAN panel и HTTP 200 от API конфигурации и physical inventory ([отчёт](../../experiments/keenetic-ipk-packaging/README.md#исправление-загрузки-конфигурации-и-инвентаря-подключений)). Группа default deny пока не содержит Hestia exits. Клиентский dataplane и DNS не проверялись; транзакционный upgrade rollback отсутствует.


### Следующий сервисный срез

Сервисный код соблюдает критерии: root-only IPC в закрытом runtime, статические команды, process handles, отказ при оставшихся процессах и `Offline` только по подтверждённому состоянию. В Go реализованы ограниченный smoke, router/controller/panel, binding watcher и запуск через Entware init; перед controller строятся confined quality paths, панель по умолчанию слушает loopback и принимает только заданный loopback/private IP. ARM64 compile/vet проходят; локального IPC прогона не было. BusyBox-набор, права, автозапуск, smoke и panel на KN-1012 остаются отдельной проверкой; это не разрешает сетевую/конфигурационную мутацию.

Статус этапа 1: Go RCI client, read-only Ethernet connector, отдельный sysfs kernel inventory, build-tagged `/opt` layout и REST inventory реализованы. Controller/smoke carrier использует Linux device names, а нативные RCI port IDs остаются отдельными. Supervisor, Go smoke, root helper, Entware profile paths, experimental `/opt` bundle и IPK v2 собраны; init lifecycle сериализован lock-каталогом, а opkg upgrade/remove удерживает maintenance marker до успешного configure. Установка IPK на KN-1012 и проверка панели с LAN-клиента подтверждены 7 ноября 2026 года; `http://192.168.1.1:8080/`, `/api/groups-and-rules` и `/api/physical-connections` вернули HTTP 200. [Отчёт и evidence](../../experiments/keenetic-ipk-packaging/README.md#исправление-загрузки-конфигурации-и-инвентаря-подключений). Для этапа 2 добавлен отдельный ограниченный reader статусов WISP station в общей RCI библиотеке; он не включён в API и не проверен на целевой HTTP JSON-схеме. Site survey, управление WISP, AWG, RoutePolicy/dataplane, DNS, транзакционный rollback обновления и полный трафиковый путь открыты.
