# Bash для сценариев развёртывания

Актуальность источников проверена: 2026-11-04
Область: `deploy/` и `experiments/`

Этот гайд фиксирует применимые правила проекта для Bash. Скрипты могут запускаться на macOS-хосте, Debian-госте или CI; проверяй конкретную версию Bash и доступные утилиты в целевой среде и не используй конструкции, которых там нет.

## Источники и инструменты проекта

| Тема | Источник | Применение |
|---|---|---|
| Семантика Bash | [GNU Bash Reference Manual](https://www.gnu.org/s/bash/manual/bash.html) | Поведение shell, параметры, массивы, traps и код завершения |
| Статический анализ | [ShellCheck Wiki](https://www.shellcheck.net/wiki/) | Разбор предупреждений и безопасная передача аргументов |
| Форматирование | [mvdan/sh — shfmt](https://github.com/mvdan/sh) | Единый формат Bash-скриптов |
| Проектные команды и закреплённые версии | [`AGENTS.md`](../AGENTS.md) и [`Makefile`](../Makefile) | `shfmt` 3.11.0, ShellCheck 0.11.0; формат `shfmt -i 4 -ci` |

## Правила проекта

- Пиши явный Bash shebang и включай `set -euo pipefail`, если контракт скрипта не требует документированного исключения.
- Документируй каждую именованную функцию комментарием непосредственно перед объявлением: назначение, входы, побочные эффекты и результат/условие отказа.
- Всегда заключай раскрытие переменных в кавычки, если намеренно не требуется разбиение слов или globbing. Для списков используй массивы и передавай их как `"${array[@]}"`.
- Не собирай команды в строку, не применяй `eval` и не передавай недоверенные данные в shell. Вызывай программы с фиксированными путями или аргументами, а данные передавай через stdin либо отдельный файл с закрытыми правами.
- Обрабатывай ошибки каждого перехода установки: до замены сохрани состояние, используй ограниченные временные каталоги, задавай trap-очистку и определи, как вернуть предыдущие файлы и состояния служб.
- Проверяй владельца, тип файла и права перед записью в системные пути. Секреты не выводи в терминал, журнал, аргументы процесса, диагностические сообщения или артефакты.
- Держи команды идемпотентными либо явно отклоняй повторный запуск, если он может изменить чужое состояние.
- Для systemd unit-файлов используй отдельные декларативные файлы; не генерируй исполняемую shell-логику из полей пользовательского профиля.
- Не подавляй ShellCheck inline без локального комментария, объясняющего конкретную безопасную причину.

## Проверки

Перед ревью и коммитом запускай из корня репозитория:

```sh
make fmt
make check
```

Для узкой проверки Bash можно выполнить:

```sh
shfmt -i 4 -ci -d path/to/script.sh
shellcheck -x -P SCRIPTDIR -s bash path/to/script.sh
bash -n path/to/script.sh
```

`make fmt` форматирует все Bash-скрипты в `deploy/` и `experiments/`; перед его запуском проверь рабочее дерево и убедись, что он не перезапишет несвязанные незакоммиченные изменения. `make check` также запускает проверки и тесты проекта.

## Примечание о CI

На дату проверки в корневом Makefile определены локальные цели форматирования, линтинга и тестирования, но активная CI-платформа для этих целей не установлена. Не добавляй новый CI-пайплайн в рамках этого гайда.
