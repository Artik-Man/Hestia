# Дорожная карта Гестии

Цель — установить Гестию на физический ARM64-шлюз между провайдером и роутером и подтвердить, что клиентский трафик идёт через разрешённое подключение либо блокируется. Ниже предложен порядок работ. Требования к продукту собраны в [спецификации](requirements.md), а детальные сценарии — в [плане испытаний](validation.md).

На 4 ноября 2026 года выполнен [эксперимент с FakeIP](../experiments/fakeip/README.md): TCP и UDP для двух доменов с одним IPv4 и портом вышли через разные интерфейсы на двух ARM64-ВМ. Выходы были статическими и виртуальными. Переключение при отказе, реальные SSTP, скорость и запуск на плате ещё предстоит проверить.

Каждая функция проходит свой цикл: согласуем проверяемую спецификацию с Product Owner, при неопределённости ставим эксперимент, пишем тест на ожидаемое поведение и затем реализуем его. Проверки, которые требуют реальной платы или внешнего VPN-сервера, отмечаем отдельно от результатов ВМ.

## Этапы и критерии перехода

| Этап | Результат работы | Как принимаем |
|---|---|---|
| 1. Спецификация первого MVP и воспроизводимый стенд | Определить состав первого выпуска контроллера, его язык, границы ответственности с sing-box и способ управления маршрутами. Описать подготовку ARM64-ВМ в репозитории. Lima и Ansible — предложенные инструменты. | Из чистой ВМ воспроизводится уже пройденный FakeIP-тест. Повторная подготовка сохраняет рабочее состояние. Согласованы сценарии отказа на следующем этапе. |
| 2. Эксперименты с отказами и SSTP | Поставить два опыта: отказ выхода после выдачи FakeIP и работа двух SSTP с одинаковым внутренним IP в отдельных сетевых пространствах. Установить, какие переключения выполняет sing-box и чем должен управлять контроллер. | При живом резерве новое соединение проходит через резерв своей группы. При отказе всей группы захваты подтверждают отсутствие пользовательских пакетов и связанных внешних DNS-запросов на чужих выходах. Пробы обоих SSTP различимы. |
| 3. Разработка сквозного MVP маршрутизации | Реализовать модель групп и подключений, привязку списков доменов, выбор по маске и приоритету, группу по умолчанию, применение конфигурации и минимальный журнал решений. Для MVP достаточно конфигурации из файла и заданного состояния доступности выходов. | Тесты проверяют порядок правил, отключённые списки, резерв и блокировку при пустой группе. Клиент за ВМ получает FakeIP и проходит по ожидаемому TCP/UDP-маршруту. Ошибка применения сохраняет последнюю рабочую конфигурацию. |
| 4. Разработка измерений и автоматического переключения | Добавить постоянные независимые пробы всех каналов, включая резервные, историю по цели и протоколу, настраиваемое окно (по умолчанию 60 минут) и причины переключений. Сначала наблюдать решения, затем включить их применение. | При равном качестве сохраняется прежний выход. При потерях UDP только до X через FI-1 новые потоки к X переходят на FI-2, остальные остаются на FI-1. Общая деградация и восстановление проходят отдельные проверки. |
| 5. Разработка DNS и GeoIP | Добавить параллельный опрос разрешённых резолверов, раздельные кэши, выбор по реальному IP каждого соединения и карте стран. Затем добавить долговременный кэш и прогрев частых доменов по N/X/Y. До реализации согласовать выбор реального адреса при FakeIP и условия аварийной выдачи истёкших записей. | Быстрый положительный ответ не ждёт медленного резолвера. Явная маска важнее GeoIP. При неизвестной стране используется группа по умолчанию. Прогрев соблюдает TTL и прекращается при падении частоты, фоновый DNS не создаёт пользовательских посещений. |
| 6. Разработка управления и диагностики | Реализовать локальный API и Angular-панель с PrimeNG для групп, списков, карты стран и журнала. Довести журнал от решения до фактического выхода, добавить поиск по домену/IP и протоколу, настраиваемое хранение (по умолчанию сутки). Подключить локальные Prometheus, Grafana и Alertmanager. | Из Wi-Fi можно изменить правило, проверить результат и открыть журнал даже при недоступном интернете. По времени событий оператор различает медленный DNS и задержку соединения. При остановке мониторинга контроллер продолжает переключать маршруты. |
| 7. Сборка ARM64 и репетиция установки | Подготовить версионированный комплект с зависимостями, службами, настройкой портов, резервной копией конфигурации и инструкцией отката. | На чистой Debian ARM64-ВМ проходят установка, перезагрузка, обновление и откат. Списки и группы сохраняются. После запуска служб сквозной клиентский тест снова проходит. |
| 8. Первый запуск на плате | Проверить выбранный образ, загрузку, TUN, veth, namespaces, оба Ethernet-порта и реальные VPN. Развернуть проверенный комплект сначала в изолированном сегменте. | Плата восстанавливает маршруты после перезагрузки. Захваты подтверждают выбор выхода и блокировку при полном отказе. Есть локальный доступ для восстановления. С первого развёртывания на физическом устройстве применяем правила ветвления из [AGENTS.md](../AGENTS.md). |
| 9. Приёмка под нагрузкой и ввод в эксплуатацию | В основной схеме измерить прямую маршрутизацию с целью до 1 Гбит/с. Отдельно измерить SSTP до реальных серверов. Испытать нагрев, диск, потери пакетов и событий при включённых журнале и мониторинге. | Есть протокол с конфигурацией, длительностью нагрузки, скоростью по направлениям, потерями, температурой и восстановлением после отказа. Проверено возвращение на рабочую конфигурацию. Product Owner принимает решение о включении для основной сети. |

## Что можно делать параллельно

Этапы 1–7 доступны на ВМ. Для проверки реальных SSTP на этапе 2 понадобятся два тестовых подключения и контрольная цель; при их отсутствии виртуальную часть выполняем отдельно. Выбор платы, проверку её образа и замер потолка реальных VPN можно вести параллельно с разработкой. Компоненты интерфейса можно разрабатывать после согласования API на этапе 3. Основную производительность измеряем в схеме со шлюзом перед роутером; однокабельный вариант с Keenetic нужен для отладки и ручного восстановления связи.

## Ближайшая задача

Подготовить к согласованию спецификацию **«Отказ выхода после выдачи FakeIP»**. Заданы две группы, FI-1 и FI-2 в одной из них, живой выход другой группы и клиент с закэшированным адресом. Зафиксировать три ожидаемых результата: новое TCP-соединение и новый UDP-поток достигают сервиса через FI-2 при отказе FI-1; при отказе обоих финских выходов пакеты не появляются в другой группе; результат наблюдаем по захватам и журналу. Переподключение уже существующего сеанса допустимо. Этот сценарий определит контракт первого контроллера.
