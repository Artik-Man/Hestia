# Первый MVP контроллера Гестии

Проект спецификации для согласования. Цель выпуска — по заданному состоянию выходов провести новый поток клиента через нужное подключение и объяснить выбор. Первый эксперимент проверяет, сохраняет ли клиент доступ через резерв своей группы с уже полученным FakeIP. Исходная точка — [проверенное разделение доменов с общим IPv4](../experiments/fakeip/README.md).

## Границы первого выпуска

Готовые компоненты и ограничения разобраны в [исследовании Go-библиотек](go-components.md). Предлагается писать контроллер на Go и собирать исполняемый файл для Linux ARM64. Контроллер читает конфигурацию групп, подключений и привязанных списков, проверяет ссылки и порядок, рассчитывает выбор и записывает причину решения. В первом выпуске доступность выходов задаёт оператор стенда. Автоматические измерения, SSTP, GeoIP, IPv6 и панель управления проходят отдельные этапы [дорожной карты](roadmap.md).

sing-box принимает клиентский DNS и трафик к FakeIP через TUN, восстанавливает домен и передаёт поток в выбранный выход. Linux ограничивает маршрут таблицей и интерфейсом этого выхода. Предлагается проверять новую конфигурацию перед применением и при ошибке сохранять последнюю рабочую. Способ переключения выходов без потери соответствия FakeIP проверим на этапе 2. Если обновление sing-box уничтожает это соответствие, такой способ применения не проходит приёмку.

## Правила, проверяемые в MVP

1. Контроллер выбирает самую точную маску из привязанных списков по полным меткам домена. При равной маске выигрывает группа выше в массиве. Отвязанный список сохраняется и пропускается при поиске. В рамках MVP при отсутствии совпадения применяется группа по умолчанию.
2. Для выбранной группы контроллер использует доступное подключение с наивысшим заданным приоритетом. При отсутствии доступных выходов он блокирует трафик группы. Связанный с явным правилом внешний DNS подчиняется тому же ограничению.
3. Журнал связывает время, домен, адрес назначения, протокол, правило, группу, выбранный выход или причину блокировки. Выбранный выход и фактически наблюдаемый интерфейс различаются в отчёте. Фактический выход в эксперименте подтверждается захватом пакетов.

## Приёмка отказа после выдачи FakeIP

На изолированном стенде RU-1 принадлежит группе по умолчанию. Финская группа содержит FI-1 и FI-2 в порядке предпочтения. Два тестовых домена разных групп используют один реальный IPv4 и порт. Клиент один раз получает разные FakeIP и использует их до конца серии. У каждого нового TCP-соединения и каждой новой UDP-пробы с новым исходным портом свой маркер.

| Состояние | Действие клиента | Ожидаемый результат |
|---|---|---|
| Все выходы доступны | Обратиться к обоим FakeIP по TCP и UDP | Финские пробы видны только на FI-1, российские только на RU-1. Ответы сервера подтверждают доставку. |
| FI-1 недоступен, новое состояние применено | Повторить пробы по прежнему финскому FakeIP | Оба протокола получают ответ через FI-2 без повторного DNS-запроса клиента. Переподключение прежнего сеанса допустимо. |
| FI-1 и FI-2 недоступны, RU-1 работает | Повторить финские пробы и запросить новое имя под явной финской маской с пустым кэшем и, если выдан FakeIP, открыть к нему соединение | Финские пробы блокируются. На RU-1 отсутствуют их пакеты и внешние DNS-запросы для финского имени. В журнале указана недоступность всей группы. |
| Полный отказ финской группы сохраняется | Обратиться к российскому FakeIP в том же окне захвата | Обе контрольные пробы получают ответ через RU-1. Захват на чужом выходе работал во время проверки блокировки. |
| FI-2 снова доступен | Повторить пробы по прежнему финскому FakeIP | Оба протокола снова проходят через FI-2. |

Перед отказом запрашиваем отдельное уникальное финское имя и открываем соединение к выданному FakeIP. Сопоставляем имя в захвате на разрешённом интерфейсе с запросом в журнале тестового резолвера. Эта контрольная проба учитывает, что sing-box может отложить внешнее DNS-разрешение до подключения клиента. Захваты на всех выходах запускаем до изменения состояния, сохраняем PCAP, журнал с отметками применения, ответы клиента и сервера. Для проверки утечки DNS используем наблюдаемый тестовый резолвер и уникальное имя, а захват включает DNS наряду с полезным трафиком. Таймаут клиента сам по себе не подтверждает блокировку. Время переключения измеряем отдельно от времени обнаружения отказа. Порог для автоматического обнаружения предстоит определить на этапе измерений стабильности.

После согласования сначала воспроизводим отказ на стенде и проверяем сохранность FakeIP. Для реализации переводим таблицу и правила выбора в тесты, затем реализуем контроллер до прохождения проверок.
