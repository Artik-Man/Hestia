# Первый MVP контроллера Гестии

Product Owner согласовал границы MVP и выбор Go 4 ноября 2026 года. Цель выпуска — по заданному состоянию выходов провести новый поток клиента через нужное подключение и объяснить выбор. Первый эксперимент проверяет, сохраняет ли клиент доступ через резерв своей группы с уже полученным FakeIP. Исходная точка — [проверенное разделение доменов с общим IPv4](../experiments/fakeip/README.md).

## Границы первого выпуска

Контроллер пишем на Go и собираем исполняемый файл для Linux ARM64. Он читает конфигурацию групп, подключений и привязанных списков, проверяет ссылки и порядок, рассчитывает выбор и записывает причину решения. В первом выпуске доступность выходов задаёт оператор стенда. Автоматические измерения, SSTP, GeoIP, IPv6 и панель управления проходят отдельные этапы [дорожной карты](roadmap.md).

sing-box принимает клиентский DNS и трафик к FakeIP через TUN, восстанавливает домен и передаёт поток в выбранный выход. Linux ограничивает маршрут таблицей и интерфейсом этого выхода. Контроллер должен проверять новую конфигурацию перед применением и при ошибке сохранять последнюю рабочую. Переключение через локальный API селектора при сохранении FakeIP проверено на [сквозном SSTP-стенде](../experiments/sstp-gateway/README.md). Если обновление sing-box уничтожает это соответствие, такой способ применения не проходит приёмку.

## Правила, проверяемые в MVP

1. Контроллер выбирает самую точную маску из привязанных списков по полным меткам домена. При равной маске выигрывает группа выше в массиве. Отвязанный список сохраняется и пропускается при поиске. В рамках MVP при отсутствии совпадения применяется группа по умолчанию.
2. Для выбранной группы контроллер использует доступное подключение с наивысшим заданным приоритетом. При отсутствии доступных выходов он блокирует трафик группы. Связанный с явным правилом внешний DNS подчиняется тому же ограничению.
3. Журнал связывает время, домен, адрес назначения, протокол, правило, группу, выбранный выход или причину блокировки. Выбранный выход и фактически наблюдаемый интерфейс различаются в отчёте. Фактический выход в эксперименте подтверждается захватом пакетов.

## Приёмка отказа после выдачи FakeIP

На изолированном стенде RU-1 принадлежит группе по умолчанию. Финская группа содержит FI-1 и FI-2 в порядке предпочтения. Два тестовых домена разных групп используют один реальный IPv4 и порт. Клиент один раз получает разные FakeIP и использует их до конца серии. У каждого нового TCP-соединения и каждой новой UDP-пробы с новым исходным портом свой маркер.

| Состояние | Действие клиента | Ожидаемый результат |
|---|---|---|
| Все выходы доступны | Обратиться к обоим FakeIP по TCP и UDP | Финские пробы видны только на FI-1, российские только на RU-1. Ответы сервера подтверждают доставку. |
| FI-1 недоступен, новое состояние применено | Повторить пробы по прежнему финскому FakeIP | Оба протокола получают ответ через FI-2 без повторного DNS-запроса клиента. Переподключение прежнего сеанса допустимо. |
| FI-1 и FI-2 недоступны, RU-1 работает | Повторить финские пробы и запросить новое имя под явной финской маской с пустым кэшем и, если выдан FakeIP, открыть к нему соединение | Финские пробы блокируются. На RU-1 отсутствуют их пакеты и внешние DNS-запросы для финского имени. В журнале указана недоступность всей группы. |
| Полный отказ финской группы сохраняется | Обратиться к российскому FakeIP в том же окне захвата | Обе контрольные пробы получают ответ через RU-1. Захват на чужом выходе работал во время проверки блокировки. |
| FI-2 снова доступен | Повторить пробы по прежнему финскому FakeIP | Оба протокола снова проходят через FI-2. |

Перед отказом запрашиваем отдельное уникальное финское имя и открываем соединение к выданному FakeIP. Сопоставляем имя в захвате на разрешённом интерфейсе с запросом в журнале тестового резолвера. Эта контрольная проба учитывает, что sing-box может отложить внешнее DNS-разрешение до подключения клиента. Захваты на всех выходах запускаем до изменения состояния, сохраняем PCAP, журнал с отметками применения, ответы клиента и сервера. Для проверки утечки DNS используем наблюдаемый тестовый резолвер и уникальное имя, а захват включает DNS наряду с полезным трафиком. Таймаут клиента сам по себе не подтверждает блокировку. Время переключения измеряем отдельно от времени обнаружения отказа. Порог для автоматического обнаружения предстоит определить на этапе измерений стабильности.

Для первого шага TDD проверяем решение контроллера по заданной конфигурации. При совпадении финской маски и отказе FI-1 решение указывает FI-2. При отказе FI-2 оно указывает блокировку с причиной, даже если российская группа по умолчанию жива. Положительный контроль — другое имя по-прежнему использует российский выход.

При подключении к обработке пакетов отдельная обязательная регрессия воспроизводит [обход блокировки по старому FakeIP](../experiments/dns-geo/README.md). После применения решения о блокировке захваты должны подтвердить отсутствие пользовательских пакетов и связанных DNS-запросов на всех внешних выходах при работающем разрешённом контроле. Тест модели сам по себе этого свойства не проверяет.

На ARM64 проверен [первый шаг реализации](../experiments/controller-routing/README.md). Go-команда обрабатывает один домен и снимок состояния за запуск. Таблицы маршрутов, доменные правила sing-box и защищённый выход deny заранее настроены на стенде. Управление общей конфигурацией относится к следующим шагам.

## Постоянная служба контроллера

Служба читает файл со снимком доступности при запуске и затем периодически. Для каждой группы ожидаемый выход — первое доступное подключение в её порядке либо `deny`, когда вся группа недоступна. При запуске и после перезапуска служба сверяет состояние с работающим sing-box. Изменение доступности должно применяться без команды с доменным именем. Здоровая группа с прежним целевым выходом не должна получать повторную команду переключения.

Принимаем по данным клиента и журнала службы. Один и тот же процесс должен обработать отказ FI-1, полный отказ FI и восстановление. Ошибочный или незавершённый снимок не должен применяться. После восстановления доступа к API служба повторяет неподтверждённое применение. Источник доступности на этом этапе — файл, который обновляется атомарной заменой; измерение потерь входит в следующий этап.

Проверка на ARM64 пройдена: 24 пробы, один процесс на изменениях доступности, успешная синхронизация после перезапуска. В течение прогона селектор RU получил только начальную запись.
