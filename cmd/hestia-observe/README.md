# Наблюдатель качества TCP и UDP

Команда `hestia observe` сравнивает доставку до настроенных IPv4-целей через подключения одной группы. В каждом раунде она одновременно открывает по одному сокету для каждой пары «подключение, цель» и закрепляет его за указанным Linux-интерфейсом до отправки. Запускайте команду в сетевом пространстве, где видны эти интерфейсы и их маршруты. Для разных групп используйте отдельные процессы. Исходный порядок подключений определяет приоритет при старте.

На целевом сервере требуется согласованный TCP- или UDP-отражатель. Содержимое запроса — ASCII-строка `hestia-`, 32 случайные шестнадцатеричные цифры и перевод строки. Для TCP сервер возвращает ту же строку до перевода строки включительно, для UDP — одну датаграмму с точно теми же байтами. Контролируйте доступ к отражателю на своих серверах. Замер RTT включает установление соединения для TCP. Потеря здесь означает неуспешную пробу до отражателя. Для TCP это не измерение процента потерянных IP-пакетов.

## Конфигурация

```json
{
  "group": "FI",
  "connections": [
    {"id": "FI-1", "interface": "fi1"},
    {"id": "FI-2", "interface": "fi2"}
  ],
  "targets": [
    {"address": "203.0.113.77", "port": 19091, "protocol": "udp"},
    {"address": "203.0.113.77", "port": 19091, "protocol": "tcp"}
  ],
  "interval": "10s",
  "timeout": "1s",
  "window": "60m",
  "min_samples": 100,
  "margin_percent": 5
}
```

В примере указаны значения необязательных параметров по умолчанию. Цель задаётся буквальным IPv4-адресом и одним портом для каждого протокола. Пробы отправляются с общим интервалом от 20 мс. Таймаут положительный и не превышает интервал. Слишком длинный раунд пропускает истёкшие слоты расписания. Конфигурация ограничена 32 подключениями, 64 целями, 128 одновременно открываемыми сокетами, 1 МиБ JSON и миллионом индивидуальных измерений на окно.

На Linux выполните:

```sh
hestia observe -config observer.json -check
hestia observe -config observer.json -rounds 3
```

Без `-rounds` наблюдатель работает до SIGTERM или прерывания. Перед первым раундом проверяется наличие каждого интерфейса. Для воспроизведения стенда можно собрать самостоятельную команду из корня проекта через `go build -o /tmp/hestia-observe ./cmd/hestia-observe`. У неё те же параметры.

## Решение и журнал

Каждая JSON-строка относится к одному раунду для ключа «группа, реальный IP, протокол». Поле `latest` показывает случайную метку, результат и RTT успешного ответа для каждой связи. `counts` и `samples` содержат только сопоставимые измерения из окна. Если при привязке сокета, выборе локального маршрута или другой локальной операции возникла ошибка, весь раунд этой цели исключается из статистики. Отменённый раунд ничего не публикует. Таймаут, сброс, отказ в соединении и неподходящий ответ учитываются как неуспешные пробы.

`current` — предыдущее предложение наблюдателя, `recommended` — результат сравнения. До накопления `min_samples` годных раундов сохраняется текущий выход. Затем для смены нужен перевес по доле полученных ответов не менее `margin_percent` процентных пунктов. При равенстве сохраняется текущий выход. Если несколько лучших альтернатив равны, выбирается первая по настроенному порядку. Все счётчики относятся к этому адресу и протоколу. Даже при одновременной недоступности единственной контрольной цели из этого события нельзя вывести отказ всей группы. Порог — параметр первого наблюдательного среза; статистический тест из лабораторного эксперимента здесь не применяется.

Наблюдатель ничего не меняет в sing-box и таблицах маршрутизации. Его `current` характеризует историю предложений самого процесса. Фактический выход пользовательского потока определяется отдельно. После перезапуска история начинается заново.

## Экспериментальное управление исключением UDP

Команда `hestia steer -config observer.json -rules /run/hestia-lab/fi-udp.json` выполняет те же измерения и публикует адресное исключение при измеренном преимуществе второго подключения. Дополнительный параметр `-rounds N` ограничивает длительность теста. Одновременно поддерживаются одна группа, ровно два подключения по порядку предпочтения и одна или несколько целей UDP. Цели TCP служат контролем. Первое подключение — основной путь, второе — путь для новых UDP-потоков к выбранному адресу. Каждое исключение действует на весь UDP к этому IPv4, включая другие порты.

Перед запуском подготовьте отдельный каталог и обычный файл с содержимым `{"version":3,"rules":[]}`. Каталог и файл должны принадлежать пользователю процесса. Записывать в них может только владелец. Все компоненты пути до рабочего каталога должны быть под контролем оператора. Разрешите процессу sing-box проход по этому каталогу и чтение файла. При замене сохраняются права доступа и группа исходного файла. Если измеритель не может сохранить группу, публикация завершается ошибкой. Несколько процессов Гестии в одном каталоге исключены блокировкой. Оператор оставляет команду единственным владельцем содержимого живого файла.

В sing-box заранее объявите локальный rule-set с этим путём в формате source. Правило маршрута должно проверять UDP, разрешённую группу и попадание реального IP в rule-set. Затем оно отправляет поток через второй выход. Обеспечьте приоритет правил явного назначения в другую группу и блокировку недоступных выходов. Команда меняет содержимое выделенного файла. Имена выходов и порядок маршрутов задаёт оператор в сетевом слое.

Каждый отчёт включает `rule_action`. Значения `added` и `removed` подтверждают атомарную замену файла, `unchanged` сохраняет ранее опубликованный набор, `not_applicable` относится к TCP. Ошибка публикации появляется как `error` с причиной и завершает команду с ненулевым кодом. Доставку новых потоков подтверждайте по захватам пакетов. При равенстве, ошибке локальной пробы или нехватке данных сохраняется выбранный путь. Остальные IP остаются в списке при добавлении или удалении одного исключения.

При завершении остаётся последняя опубликованная версия. Для следующего запуска оператор сначала возвращает топологию стенда к проверенному исходному состоянию и устанавливает пустой набор. Если файл уже содержит маршруты, команда отказывается запускаться. Автоматическое восстановление состояния после перезапуска, общий отказ группы и распространение правил из локальной панели требуют отдельной интеграции.

## Экспериментальная смена основного выхода группы

`hestia balance -config observer.json` сравнивает ровно два выхода одной группы по контрольным целям на разных IPv4-адресах. Тег селектора sing-box должен совпадать с `group`, а его состав — с идентификаторами двух подключений и служебным `deny`. До запуска оператор выбирает текущий разрешённый выход группы. Если селектор уже закрыт, команда сохраняет `deny`. Отказ всех проб сам по себе не закрывает группу.

В каждом раунде Гестия читает фактически выбранный выход из API и сопоставляет парные счётчики успешной доставки в скользящем окне. Преимущество над текущим выходом должно составить как минимум `margin_percent` процентных пунктов. Один IP даёт максимум один голос, даже если проверялись и TCP, и UDP. Для смены требуются те же два разных адреса с преимуществом одного кандидата на протяжении `-confirm-rounds` полных последовательных раундов (по умолчанию три). Существенное преимущество текущего пути до другого независимого IP отменяет рекомендацию. Если для одного IP любой из протоколов недоступен на обоих выходах одновременно, этот IP воздерживается целиком. Недостаток измерений или локальная ошибка на любом выходе прерывает серию подтверждений. При равной доставке текущий путь сохраняется. Обратный переход требует тех же доказательств. Адреса разных независимых контрольных сервисов подбирает оператор: несколько IP одного провайдера не доказывают независимость внешней инфраструктуры.

В журнале на каждый полный раунд есть `current` (прочитанный селектор), `recommended`, `applied` (подтверждённое состояние), `reason`, `votes` и исходные измерения. После PUT Гестия повторно читает селектор. При ошибке связи или неожиданных членах селектора команда завершается с ошибкой. Значение `applied: "unknown"` означает, что фактическое состояние нужно уточнить в API. Добавьте `-rounds N`, чтобы ограничить продолжительность испытания.

На время работы процесс занимает исключительную блокировку этой группы в сетевом пространстве API. Команды `guard`, применения снимка и служба `-watch` из этой версии Гестии не смогут записывать в занятый селектор. Для изменения административной доступности сначала остановите `balance`, затем примените нужный снимок. При завершении сохраняется последний применённый выход. Сторонние клиенты управляющего API и старые версии Гестии не соблюдают эту блокировку. Эксперимент предполагает, что Гестия — единственный владелец селектора. Автоматическая обработка меняющегося административного снимка во время балансировки и защита прямых адресных исключений требуют следующей интеграции.
